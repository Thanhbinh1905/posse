# posse v1 spec

Terms are defined in [CONTEXT.md](../CONTEXT.md). The architectural shape is recorded in [ADR 0001](adr/0001-cli-owns-mechanics-on-herdr-without-daemon.md).

## 1. Scope

The User talks to one Lead per Project. The Lead writes Briefs, dispatches Workers, reviews their results and asks the User only for decisions that are the User's. Everything mechanical is done by the `posse` CLI. Posse orchestrates Git repositories and Workspaces only; non-Git directories are edited directly outside Posse. `posse project add --directory` is refused. Legacy Directory Projects remain readable but cannot admit Tasks; their existing Tasks remain readable and can be torn down, without automatic conversion to Git. PR delivery uses forge CI at the exact `gated_sha`; local delivery records the Task tip at Merge and fast-forwards without automated verification, an accepted tradeoff that leaves checking to the User. Both modes refuse `branch_moved`. Legacy command Gate config is ignored with a warning, and `posse config set`/`unset` reject its removed keys.

In v1:

- Runtime: Herdr only (protocol 22 or newer).
- Workers: any agent kind Herdr recognizes. Built-in kind defaults exist for `claude`, `codex` and `pi`; other kinds run with User-supplied kind config.
- Task types: change, research, review (a review is a Research Task on a Change Task's branch).
- Merge Modes: `local`, `pr`.
- Implementation: Go, shipped as one static binary `posse` ([ADR 0002](adr/0002-go-single-binary.md)).

Out of v1: other runtimes, remote machines, coordination across Projects, quota-based routing, per-Worker-type Identity, `paths` matching in Dispatch Rules. Capacity queue admission, caller-driven refill, queued cancellation and restart recovery, typed local Task prerequisites, and GitHub ticket blocker checks are implemented as described in [ADR 0010](adr/0010-posse-queues-tasks-and-dependencies.md). A Task remains queued with a visible wait reason until its prerequisites, ticket blockers and Worker capacity permit normal spawn-intent dispatch. If a prerequisite fails, is lost or is torn down without satisfying its milestone, reconciliation raises a Decision on the queued Task to cancel it or drop that prerequisite and run. Applying the latter records a new plan revision before dispatch. Core users should check ticket blockers manually while GitHub cannot provide a complete result.

### 1.1 Workflow boundary

Posse is a thin dispatch-control layer, not a required development lifecycle. It has three frames: **Plan -> tickets**, **Implement** (one Worker per ticket, category or pattern in its own Sandbox), and **Review**. **Ship** is Git delivery afterward: publish/PR, CI and merge, not a fourth frame or production rollout.

The default direct path is one unconfigured `pi` or `claude` Worker that discovers, plans and codes by itself. No workflow stages or bundles are required. PR delivery relies on forge CI at `gated_sha`; local delivery is a fast-forward without automated verification. Selected review policy and merge authority still apply. The three non-disableable core guardrails are Task isolation and Task-scoped Teardown, ship authority (Workers never merge or force-push; merge follows `autonomy.merge` or User approval), and satisfaction of the selected review mode.

Optional workflow profiles belong in User config (dotfiles), overridable per Project and frozen into each admitted Task that selects one. They are not Worker Profiles. Define ordered stages under `[workflows.feature]`; each stage specifies `name`, `frame`, `gate`, `task_type`, `workers` and optional opaque `skills`. Project config replaces a named profile as a whole. A Task Brief with `workflow: <name>` and no run starts a new run with a per-Project ID such as `w1`; the run freezes the resolved profile digest. Later stage Tasks select that frozen run with `workflow_run: w1` and `stage: <stage name>`. `workflow_run` and `stage` must be supplied together, and `workflow` may be included only if it matches the run's frozen profile. Stage identity is the run, stage name and stage index, recorded in each admitted Task plan. A stage can contain multiple Tasks, including repeated Task types; Task type never identifies the stage. Admission refuses a Task whose stage is not the run's current approved stage. `task_type = "none"` is a Git-mechanics stage and admits no Worker Task. Preview a configured profile with `posse workflow show <name> [--project <name>]`. Invalid profiles are refused with the config file and key before Task admission. A run is bound to the profile bytes, source and digest frozen when it is created. Later stage Tasks, advancement and status use that frozen profile, even if its config is edited, renamed or its source file is deleted; changes affect new runs only. Status notes when the current config digest differs, for information only. There is no profile migration; start a new run to adopt an edited profile. An omitted `workflow:` and `workflow_run:` keep the direct path and freeze no profile.

Advance a run explicitly with `posse workflow advance <run> --to <next-stage> --user-approved "<User's words>"`. The next stage must be the next stage in the frozen profile; skipping and reordering are refused. The command records an answered User Decision bound to the run, from-stage, to-stage and the result identities of every current-stage Task. Change results use gated or private-candidate head SHAs; Research and Review results use the Report digest recorded by their done Signal. A Task without a done result blocks advancement unless the User's quoted decision explicitly abandons it with `--abandon <task>`; abandoned Tasks are recorded in that Decision. A User quote is required. The Lead never dispatches the next stage automatically. Several independent runs of the same profile can be active in one Project.

The current position and history are recoverable from admitted Task plans and Decisions in SQLite and snapshots. Inspect them with `posse workflow status [<run>]`; status reports whether a `none` stage has completed mechanically without changing run position. A `none` stage completes when every Change Task in the run is merged or torn down; this does not grant merge authority. A profile ending at that stage is complete. All other stage transitions require a User Decision. A ready check or Report is not stage approval, and merge Autonomy grants no stage-transition authority. Bounded validation/fix operations inside an approved stage are not transitions. AFK/autonomous progression is deferred and out of scope. Skill fields remain opaque placeholders; skill-set design is deferred. [ADR 0027](adr/0027-thin-core-and-user-owned-workflow-profiles.md) records the profile-format sketch and the whole-profile Project override rule.

The optional feature flow is Discover (2-4 parallel Research Workers chosen by the Lead; cross-model check only on User request) -> Plan (critique, optional arena) -> Spec -> Tickets (grouped by category) -> Build -> Review -> Deliver. The Bug variant is Diagnose -> Build -> Review -> Deliver. Profiles map stages to the three frames and Git delivery, using existing Task types.

Status: the direct path and workflow-profile configuration, preview, validation, admission freezing and user-approved run Decisions are implemented. Section 25 records the full-pipeline delivery lanes (single-repository and per-Member, PR and local delivery) and the remaining production-readiness gaps.

### Glossary and upgrade

[CONTEXT.md](../CONTEXT.md) is the canonical glossary. Worker (formerly Rider) names a delegated agent; Change Task (formerly Ship Task) changes the Project; Research Task (formerly Scout Task) produces a Report. The Pool (formerly Remuda) holds reusable Sandboxes (formerly Mounts). A Sandbox is a per-Task git worktree with per-Task process containment, not a security sandbox; a Workspace Sandbox contains selected Members' worktrees. Watch (formerly Lookout) observes and delivers Notices. Merge (formerly Land) integrates a change according to Merge Mode (formerly Landing Mode); Orphan (formerly Leftover) is work beyond the merged revision.

[ADR 0026](adr/0026-functional-vocabulary.md) records the full command, flag and config mapping. Old input is rejected with its replacement, not accepted as an alias. Existing 0.14 homes upgrade automatically, including config, Task types/states and Notice kinds. IDs, open PRs, immutable evidence and existing worktree locations remain intact. Existing preference files remain data sources. New Projects use the layout below; legacy Pool directories stay in place.

`posse merge <task>` prepares integration without merging. `posse merge <task> --execute` integrates the checked revision, with the same freshness, Review and User approval or Autonomy requirements.

## 2. Components

```text
 User ──chat──► Lead (agent in a Herdr pane)
                  │ calls
                  ▼
 ┌──────────────────────── posse CLI (Go, TOON) ─────────────────────────┐
 │ config · dispatch · state machine · reconcile · merging · notices     │
 │ herdr adapter (the only module that talks to Herdr)                   │
 └──────┬───────────────────────────┬──────────────────────────┬─────────┘
        │ ~/.posse/posse.db         │ Herdr socket API         │ git, gh            
        │ (SQLite WAL)              ▼                          │
        │               Herdr server ── plugin event hook ──► posse _ingest
        │                           │
        │                           ▼
        │          Worker panes (one tab of the Lead's workspace + worktree per Task)
        │                           │ calls
        └────────── posse signal ◄──┘
```

- **`posse` CLI**: every command is short-lived. Each call opens the DB, runs a cheap reconcile for the Project it touches, does its work and exits.
- **Herdr adapter**: the single module that calls Herdr. It checks protocol compatibility once per process and maps Herdr errors to `posse` error codes.
- **Herdr plugin** (`posse-herdr`): a manifest whose `[[events]]` hooks run `posse _ingest` for `pane.agent_status_changed`, `pane.exited`, `pane.closed` and `pane.focused`. It holds no state and never runs long.
- **Lead instructions**: composed once for `posse lead` and Lead startup/restart. Bundled workflow guidance and User/Project preferences precede generated runtime obligations; Identity applies to User communication only.
- **Worker protocol**: generated by `posse start` and prepended to every Brief, followed by the frozen Worker preferences.
- **Worker guard**: a `PreToolUse` hook (Claude Code, Codex) and a pi extension, installed by `posse setup`, that run `posse _guard` before every shell command an agent runs (section 13).

## 3. Home layout

`POSSE_HOME` defaults to `~/.posse`. Nothing is written into Project repositories.

```text
~/.posse/
  config.toml                 global config
  projects.md                 generated fleet view for the User; never edited
  posse.db                    all Projects' state
  preferences/
    lead.md                   User Lead preferences (optional)
    worker.md                  User Worker preferences (optional)
  playbook/                   deprecated, still-read compatibility paths
    lead.md
    worker.md
  pool/<name>/sandbox-<n>/      the Project's Pool (section 12)
  scratch/<name>/<task-id>/      temporary files owned by one Task
  projects/<name>/
    config.toml               Project override
    preferences/
      lead.md                 Project Lead preferences (optional)
      worker.md                Project Worker preferences (optional)
    playbook/                 deprecated, still-read compatibility paths
      lead.md
      worker.md
    tasks/<task-id>/
      brief.md                as written by the Lead
      launch.md               Worker protocol + Brief, as delivered
      report.md               Research/Review Report (copied in by posse)
      findings.toon           latest Worker findings, when any
      discard/*.bundle        approved discarded branch tips, until artifact retention expires
```

`projects.md` is regenerated after every state-changing command. It starts with `<!-- generated by posse; edit config.toml instead -->` and has one section per Project: name, path, kind, effective Merge Mode, Autonomy, Lead status, open Tasks by state, open Notices, last activity.

**Preferences (ADR 0013).** The optional Markdown files above are empty by default. For each role, Posse loads User sources before Project sources with visible path headers; a Project preference can refine or replace default/User workflow advice. New files under `preferences/` load after their legacy `playbook/` counterpart. Legacy content is never moved or overwritten implicitly. Preferences can change judgment-only workflow advice, but cannot grant authority, bypass evidence or override generated runtime obligations. Worker preferences remain subordinate to the Brief and Worker protocol. A Workspace Project uses its Project layer for the whole Workspace. `posse preferences show [--project <name>]` prints effective content and sources; `posse preferences path <lead|worker> [--project <name>]` prints canonical and legacy paths; `posse preferences set <lead|worker> --file <file> [--project <name>]` writes the canonical path atomically. `posse preferences move <lead|worker> [--project <name>]` explicitly moves a legacy file and refuses to overwrite an existing destination. A Lead write requires `--user-approved "<User's words>"` after explicit User consent, which Posse records; Workers cannot write preferences. Without `--project`, the current registered Project is selected when applicable, otherwise the User layer is used. Formerly: `posse playbook show|path|set`; those commands now fail and name `posse preferences` as their replacement. `posse doctor` warns when effective preference content exceeds approximately 4 KiB. There is no preference-specific hard limit; Lead startup still refuses complete instructions above the existing 30,000-byte budget without truncation.

## 4. Configuration

TOML. The effective config of a Project is the global file with the Project file merged over it: scalars and tables override key by key; `[[dispatch]]` lists concatenate with Project rules first. Review modes `none`, `quick` and `full-pipeline` are selectable; update migrates stored review `local` to `quick`, while new config and Briefs reject `local`. VP-B custody and the VP-C/VP-D delivery lanes are implemented; `full-pipeline` is not production-ready until the remaining section 25 integration gaps close. Planned workflow-profile overrides replace a named profile as a whole (ADR 0027), not by concatenating stages.

Rules:

- **Identity affects presentation, not authority or machine identity.** The Lead's name, persona and form of address shape messages to the User only. `identity.lead.language` also selects neutral prose for Briefs, `posse send` instructions, reviews, decisions, Reports, commit messages, Signal notes and summaries, and other evidence; the default is English. User quotations remain exact. Code identifiers, machine keys, Task IDs, issue numbers, branch refs, CLI commands, config keys and file paths remain unchanged, and the Lead's persona stays out of artifacts. Changing name, persona or form of address leaves artifacts unchanged; changing language changes prose only.
- `autonomy` is valid only in a Project file. In the global file it is a config error.
- A Brief may tighten Merge Mode (`local` < `pr`), review (`none` < `quick` < `full-pipeline`, target modes in section 25) or Autonomy. A scoped User choice recorded by `posse start --user-approved "<User's words>"` may lighten only the Brief's explicit delivery/review preferences. It does not grant review-decision, merge, discard or executable authority; Autonomy still only tightens.
- `posse` validates the effective config on every call and refuses with `config_invalid` naming the file, key and reason.
- The built-in kind defaults above can be overridden but not removed; an unknown kind with no `[kinds.<kind>]` table runs with no extra args, `steer = false`, and no interrupt key sequence. `kinds.<kind>.disabled = true` prevents selecting that kind for new Worker dispatch only. It does not remove the kind's launch configuration, block an existing Lead, or affect historical Task readers and frozen relaunches.
- `defaults.max_workers` and `defaults.recovery_attempts` must stay positive. `pool.keep_idle = 0` is valid and retains no idle Sandboxes.
- The Lead workspace label is `Lead:<project>`. New Workers in every Project kind open as unfocused `<name>` tabs in the Lead workspace, with pane identity and tree `posse_row` metadata. Git worktree registration and locking remain unchanged. Existing linked-child Tasks retain their workspace label and linked-child Teardown behavior until completion; recovery and relaunch open them as Lead tabs. Posse never renames a User tab or workspace ([ADR 0013](adr/0013-all-workers-open-as-lead-tabs.md)).
- A Profile's `model` and `effort` reach the agent only through the kind's `model_args` and `effort_args` templates; a kind without a template for a set value is a `config_invalid` error naming the Profile.
- `defaults.review`, `repositories.<member>.review`, `[pool] setup`, `[autonomy]`, kind argument templates (`auto_approve_args`, `model_args`, `effort_args`, `resume_args`, `system_prompt_args`, `lead_args`), kind trust preparation (`prepare`), `lead_auto_approve`, and Profile `kind`, `args` and `attribution` are User-only. `posse config set|unset` requires a registered Lead to pass `--user-approved "<User's words>"` with a non-blank quote. The Lead records the quote, key, action, set value and Project ID in `config_approvals` (global changes are attributed to its Project). A Worker cannot write any key, even with the flag. Pane bindings in the current process and its ancestors recognize registered native Worker and Lead children. An unbound pane or recognized agent environment/process is not the User and cannot write protected settings or answer Decisions. A plain User shell needs no quote; an unbound Herdr pane must first be observed without an agent. Missing or unavailable pane evidence does not prove it is a shell.
- These checks are cooperative same-user safeguards, not authentication. Environment/process hints and a consent quote can be forged by a process with the User's OS permissions; absence of a binding does not prove a human is present. The quote records provenance, not authenticated consent. Isolated test homes do not inherit parent actor hints across their home boundary.
- `posse config show --effective` includes effective values and per-key `sources`: built-in defaults, global config or Project config. Project scalar aliases resolve to canonical keys, concatenated Dispatch Rules list both contributing files, and derived yolo grants name the yolo source. `posse doctor` shows the selected implicit-dispatch policy and disabled kinds, plus separate active Worker, tracked native-child and parked-resource counts per Project. The native-child count is the Project's registered and running research attempts (section 26); it never includes unregistered harness subprocesses. Parked resources are held Sandboxes whose Tasks are outside active execution states.
- Config is written through `posse config set|unset` and `posse lowkey on|off`, which validate against the schema, write atomically and keep comments. `posse config schema` prints every key with its type, allowed values, default, meaning and whether it is `user_only`.
- Claude, codex and OpenCode Leads get their kind's `auto_approve_args` by default, including after restart. Set `kinds.<kind>.lead_auto_approve = false` to keep that harness's approval prompts; Profile `args` may still add flags. This changes only harness permissions, not Posse autonomy: review and merging decisions remain governed by `[autonomy]`. Pi is unchanged because it has no permission system. A Lead also gets `lead_args`: codex's default `workspace-write` sandbox cannot write the posse home (SQLite in WAL mode needs write access even to read), the Sandboxes or the agents' trust files, so it also runs with `--sandbox danger-full-access`.
- Agent attribution is off by default. Claude Leads and Workers start with `--settings '{"attribution":{"commit":"","pr":""},"includeCoAuthoredBy":false}'` placed before Profile `args`, so a Profile's own `--settings` replaces it. Every push of a Task branch (`posse publish`, candidate promotion and legacy Merge pushes) first reads the trailers of commits above the Task base and `origin/<target>` and refuses with `agent_attribution_refused`, listing each commit, when a `Co-authored-by`, `Assisted-by` or `Generated-by` trailer names an agent (Claude, Codex, Copilot, Gemini and similar, or an Anthropic or OpenAI email domain). Posse never rewrites history; the Worker rewords its commits. A Profile with `attribution = true` (User-only) keeps Claude's attribution and skips the check for Tasks admitted on it.
- `notice_delivery = "watch"` requires `background_commands = true` for kinds other than Claude. A Claude Lead uses one receipt-backed background Bash Watch in its local interactive session; the command waits without model turns and returns its batch when a Notice arrives.
- `[lowkey] lead = true` enables lowkey mode for the Lead (default `false`). `posse lowkey on|off|status` persists the Project setting from a Project checkout, or the global setting elsewhere. It is a reporting and Lead presentation preference, not an autonomy grant, and Leads may toggle it. Every `posse` and `posse watch` response carries its current state and reporting rule, so a running Lead switches without restarting. In a Pi Lead, lowkey hides expanded thinking and collapsed `Thinking...` labels, all built-in and custom tool-execution rows (call and result), and assistant text from steps that call tools, including existing rows. The User's request and final reply remain visible; replies after tools stream normally, while first-step text waits until Pi knows it is not a tool preamble. These presentation filters preserve reasoning, tool calls and text in model context, session storage and exports. They leave the thinking level and Pi's `hideThinkingBlock` setting unchanged. While lowkey is on and a run is active, the Pi Lead replaces its stock working row with a one-row Slab animation above the composer; when the run settles or lowkey turns off, it restores the stock row. Lowkey off restores the hidden rows. The generated Pi Lead extension offers `/lowkey` to toggle and `/lowkey on|off|status` to persist or inspect the same setting without a transcript row; failed writes leave the choice unchanged. A Claude Code Lead uses a process-local function-hooks plugin when `posse up` starts it, with `CLAUDE_CODE_ENABLE_FUNCTION_HOOKS=1` and `--plugin-dir`; Posse does not alter the User's Claude settings. Its `/lowkey [on|off|status]` reads and writes the same Project `lowkey.lead` preference as the CLI and Pi extension, falling back to the global preference when the Project key is absent. Claude Code's tool calls, results, folded tool groups and assistant text from steps that call tools draw at zero height; the User's messages and final replies stay visible. Posse -> Lead Notice envelopes draw at zero height only when an exact matching Posse delivery record exists, not merely when User text contains `[posse |` (section 9). A one-row Slab animation replaces the stock spinner while working. Toggling redraws existing rows, and `claude --continue` reclassifies stored tool-step text. Hidden content remains in model context, session storage and exports. The function-hook API is early access: unavailable seams fall back to stock rendering; if the Notice records directory is absent, only Notice hiding falls back to stock while tools and the Slab remain lowkey. `posse doctor` warns when the installed Claude Code version has not been verified.

## 5. State (SQLite)

The schema sketch below uses current domain names. Published SQL identifiers remain unchanged for compatibility, including `mounts`, `mount_id`, `landing_mode`, `autonomy_land`, `landed_ref`, `lookout_*`, `completed_rider_busy` and `ship_task_id`; see ADR 0026.

WAL mode, `synchronous = NORMAL`, `busy_timeout = 5000`. Commits do not fsync; the WAL is synced at checkpoints. A process crash loses nothing, and the database stays consistent after any crash, but an OS crash or power loss can roll back the last commits. After such a rollback, Task and Project snapshots may be newer than the database, interrupted intents are recovered again and the lost detector may fire again; `posse recover --rebuild` restores state from the snapshots. Opening a store whose applied migrations and checksums match the build skips the migration lock. Every state transition is one transaction that checks the expected prior state (compare and set) and inserts a `transitions` row.

## 6. Task lifecycle

```text
queued ─► spawning ─► working ─┬─► done ─► merging ─► merged ─► torn-down      (change)
                     │     └──► reported ─────────────► torn-down     (research, review)
                     ├─► needs-decision ─► working   (after posse send or Worker `working` Signal)
                     ├─► blocked ─► working          (Herdr: approval dialog)
                     ├─► stalled ─► working          (progress resumes, a Signal, or relaunch)
                     └─► failed
   done ─► working                                   (Lead sends a fix, Worker Signals `working`, or watcher observes a new Worker turn)
   merging ─► working                                (Lead sends a follow-up, Worker Signals `working`, or watcher observes a new Worker turn)
   spawning, working, needs-decision, blocked, stalled, failed, lost ─► merged (forge reports the PR merged)
   spawning, working, needs-decision, blocked, stalled ─► lost   (Worker gone, not resumable)
```

| Transition | Source | Trigger |
|---|---|---|
| queued → spawning | cli | capacity, typed local prerequisites and native ticket blockers permit caller-driven scheduler refill; the claim and normal start intent are atomic |
| queued → torn-down | cli | `posse teardown <task>` cancels before Worker dispatch, or the User applies `cancel` on a failed-prerequisite Decision |
| queued → queued | cli | the User applies `drop-prerequisite-and-run`; Posse records a new admitted-plan revision without that edge, then retries normal dispatch |
| spawning → working | cli | agent started and brief prompt accepted |
| working → done / needs-decision / failed | worker | `posse signal` |
| working ↔ blocked | herdr | agent status `blocked`, then any non-blocked status |
| working → stalled | cli | stall rule (section 10) |
| stalled → working | cli / worker | new output or worktree change, `posse relaunch`, or any Worker Signal (`working` records source `worker` and its reason) |
| needs-decision → working | lead / worker | `posse send` starts durable submission, or Worker records a `working` Signal |
| done → working | lead | `posse send` starts durable submission to a `done` Change Task; clears `gated_sha` |
| done → working | worker | direct User follow-up via `working` Signal; cancels pending Merge, clears the recorded merge head and any `merge_ready` Decision, raises `worker_resumed` quoting the reason; refuses once merge has started |
| done → merging | cli | `posse merge` started (merge head recorded, PR opened or ready to merge) |
| merging → working | lead | `posse send` starts durable submission to a merging Change Task; clears `gated_sha` and keeps its branch and PR |
| merging → working | worker | direct User follow-up via `working` Signal; cancels pending Merge, clears the recorded merge head and any `merge_ready` Decision, raises `worker_resumed` quoting the reason; refuses once merge has started |
| done / merging → working | watcher | after the completed turn ends (`idle` or `done`), Herdr reports a new `working` turn and the Task repository (HEAD and tree) differs from the fingerprint recorded at turn end, observed while that turn is `working` or when it ends; cancels pending pre-merge Merge, clears Task and unmerged Member merge heads, keeps branch and PR, raises `worker_resumed`; leaves the Task merging if merge has started |
| any non-merged PR Task → merged | cli | forge reports the Task's verified PR head merged; records the merge commit without passing through `done` |
| done → reported | cli | research/review: Report copied in; legacy Directory Tasks: saved output evidence remains readable without Merge |
| spawning (with a pane), working, needs-decision, blocked, stalled → lost | cli | reconcile: pane gone and no resumable session, unless an admitted Teardown intent owns the Task transition |
| merged / reported → torn-down | cli | `posse teardown` |
| lost / failed / stalled → working | lead | `posse relaunch` (section 17) |
| spawning → failed | cli | reconcile: a `start` intent older than 5 minutes with no pane; its Sandbox is released |
| spawning, working, needs-decision, blocked, stalled, done, merging, failed, lost, reported → torn-down | user | `posse teardown --discard --user-approved "<quote>"`, stops only the verified current Worker instance before discard |
| merged → torn-down | user | only for an answered unrecoverable-Orphan Decision; the User discards the unmerged Orphan, not the merged Task |

A Worker shell that exits closes its pane: Herdr emits `pane.exited` and the pane id stops resolving.

Live states: queued, spawning, working, needs-decision, blocked, stalled, done, merging. Queued Tasks consume no Worker slot or Sandbox.

An admitted Teardown intent, including approved discard, owns the Task transition while it is active. Reconcile checks for that intent in the same transaction as a possible `lost` transition, so closing the pane cannot emit `task_lost` or create a recovery Decision during Teardown. Teardown clears the intent on completion or failure; if the Task remains live after failure, a later reconcile can detect a real loss.

`done` and `merging` are never marked `lost`: their work is committed and the Worker is no longer needed. If their pane disappears, reconcile records a `worker_exited` Notice once and leaves the state alone.

Every Signal is one transaction: the `signals` row, the resulting transition(s) (including `done → reported` for research and review) and the Notice commit together. A `done` Signal is rejected in that transaction while any message is `queued`, `claimed` or `interrupting`; no Signal, transition or Notice is recorded, and the Worker receives a `queued_instructions_pending` error. The Worker lets the turn end so Posse can deliver the instruction, applies it, then retries `done`. A message still `submitting` remains governed by the uncertain-delivery protocol below because Herdr may already have accepted it. When a Task enters `reported`, `failed`, `lost`, `merged` or `torn-down`, queued and claimed messages are atomically marked `undeliverable`; one `queued_message_undeliverable` Notice names their IDs and gives a supported resend step. Migration 26 also repairs existing orphaned queues on terminal Tasks.

## 7. Reconcile

Runs during Project preparation (all Projects for `posse list --all`), using one `session.snapshot` call. The complete runtime pass has a 3 second budget, including generation persistence and stall evaluation. Each admitted Task and Project observation gets a fresh bounded context and a SQLite lock wait of at most 250 ms. Unchanged observations skip the write; conditional updates avoid repeating a write when another process records the same observation first. Work that cannot fit is deferred; later passes prefer stale Task observations instead of reusing expired contexts. Reconcile attributes each Task's failures before combining them, so a timeout from one Task does not hide failures from others in the same pass; remaining work is deferred to the next pass.

A reconcile that loses a compare-and-set race on a Task skips that Task (another process already moved it); it never fails the command. One Project's failure (missing repository, invalid config) is reported for that Project and does not stop commands for other Projects. When reconciliation for a read-mostly command hits only transient contention, `posse`, `list`, `show`, `lead`, `project show`, `pool` and `peek` display the last recorded state with a deferral message. Mixed or persistent failures remain visible; commands that require successful maintenance return retryable `store_busy`. The Lead Watch logs and retries pure transient contention in preparation and Project-watch work without exiting or raising a Notice; mixed failures still raise a Notice containing their non-contention causes. Sandbox-state and repository-fetch flock acquisition stop after 3 seconds, even if the holder is stopped, and never steal or unlink its lock.

`posse signal` validates and atomically records its own Task's Signal, transition and Notice before any whole-Project preparation. A `done` attempt first checks for queued, claimed or interrupting instructions before copying a Report, then repeats the check inside the Signal transaction to close the race with concurrent queue insertion or delivery. Subsequent Project maintenance, Notice delivery and snapshot regeneration are best-effort within a separate 3 second budget; failures do not reject the committed Signal. Non-contention failures emit diagnostics; when an error aggregate also contains transient store contention, only its non-contention causes are shown. Pure transient store contention is deferred silently to the Worker; the Watch logs the deferral and retries maintenance. Contention in the Signal's own transaction remains a retryable failure.

For each live Task:

0. **`spawning` with no pane id yet**: skip; spawn owns it until it records the pane.

1. **Pane present and the agent is the foreground process**: refresh `agent_session` only from a plain session ID or an absolute path inside that harness's session directory; map Herdr status (`blocked` → blocked; leaving `blocked` → working).
2. **Pane id missing**: look for a pane whose `label` equals `pane_label` (labels survive a Herdr restart; pane ids may too). If found, adopt its new pane id.
3. **Pane present but the agent exited**: if `agent_session` is known and Herdr native resume is enabled, leave it to Herdr (resume happens on client attach) and mark nothing; after 2 minutes without an agent **and** no resumable session (no `agent_session`, or native resume disabled), mark `lost`.
4. **No pane and no label match**: mark `lost`. The worktree and branch are never touched.

For a `done` or `merging` Change Task, the done Signal arms its current Worker turn. The watcher does not reopen the Task while that turn remains `working`, so the Signal's closing reply cannot undo completion. An observed `idle` or `done` status ends that turn; a later `working` status identifies new input and immediately reopens the Task. The boundary is keyed by completion transition, pane and server generation. A new turn that leaves HEAD and the working tree unchanged, such as a background-task wake that only acknowledges a result, keeps the done Signal valid. The turn-end fingerprint is read before the Herdr snapshot that reports the turn end, so a following turn's change cannot become the baseline. A turn that changes either reopens the Task and queues an instruction to signal done again. A turn can commit after its last observed `working` status, so its end compares the repository again with a read taken after the snapshot that reports it. The `working` status of a Herdr status event counts on its own, since a short turn can end before the event's reconcile snapshot. A new completion or Worker identity starts a fresh boundary. Posse instruction delivery already reopens the Task before submission, so it produces no duplicate watcher transition. The reopen, merge-head invalidation and `worker_resumed` Lead Notice commit atomically. Merge refuses until a fresh Worker done Signal. A forge-reported merge remains authoritative under ADR 0011.

Herdr idle is never evidence of completion. Only a Worker Signal moves a Task to `done`.

**Agent observation.** Each pass records the live Task's observed agent status (`working`, `idle`, `done`, `blocked`, `unknown`, `no_agent`, or `no_pane` while a missing pane is inside its absence grace) and when Posse first observed it; Herdr `idle` and `done` count as one turn-ended observation. `posse`, `posse list` and `posse show` display it as `agent`, beside the authoritative `state`, for example `agent: idle 7h12m` or `agent: no pane`. An idle or done age comes from `idle_since`, the `worker_idle` clock. When a `working` Task has been idle for `idle_after`, the row also carries `agent_mismatch`. Herdr `done` means the agent ended a turn; it never becomes or replaces the Task state. Both fields are added to TOON and JSON output; existing fields are unchanged.

The Lead is reconciled the same way through `lead_pane_id` and `lead_label`. A snapshot from a different Herdr server generation cannot update pane identities or stalls. Launch-capable Project commands and plugin events check the live server: a changed generation runs bounded recovery inline before reconciliation. A delayed snapshot from the old server is discarded and retried. `lead`, `show`, `ack` and `watch` observe state without relaunching Workers, retrying launch Briefs or waiting for an active recovery claim; a pending generation leaves pane identities untouched.

## 8. Event ingest

`posse _ingest` reads `HERDR_PLUGIN_EVENT_JSON`, writes one `events` row, and for panes that belong to a Task or a Lead does the follow-ups below. Calling back into Herdr from inside a plugin hook is safe: verified on Herdr 0.9.0, a hook's `pane list` returned in about 3 ms and its `agent prompt` reached the target pane in about 300 ms. Follow-ups never hold a SQLite transaction open across a Herdr call.

- `pane.agent_status_changed`: apply the blocked mapping from section 7; if a Worker ends a turn, inspect the end of its output for a known model error for that harness before delivering queued `messages`; a Pi stream disconnect gets at most three `continue` nudges with exponential backoff, while a provider refusal is never retried. Each episode and retry is persisted in Task history. Automatic nudges use the existing focused-pane guard; unsafe or exhausted episodes raise a specific Notice. If the pane is a Worker becoming idle, done or working and it has queued `messages`, deliver eligible messages; if the pane is a Lead going idle or done, run Notice delivery.
- `pane.exited` / `pane.closed`: run reconcile for that Task.
- `pane.focused`: retry queued Worker messages and run Notice delivery after focus changes.
- Every call also evaluates stalls for that Project (section 10).

It exits 0 even on internal errors (logged to the `events` row) so Herdr never retries or blocks. Missed events are harmless: reconcile is the source of truth.

## 9. Notices and waking the Lead

Notice kinds: `task_done`, `worker_resumed` (a Worker reopened its Task after a direct User follow-up or a new turn and must signal completion again), `needs_decision`, `task_failed`, `worker_blocked`, `worker_exited`, `task_lost`, `stalled`, `message_delivery_uncertain`, `notice_delivery_uncertain`, `teardown_escaped_processes` (Task-marked processes outside the Sandbox survived a completed Teardown), `queued_message_undeliverable` (terminal Task transition stranded queued messages), `model_stream_error` (bounded automatic recovery exhausted or was withheld), `model_refused` (provider refusal, never retried), `merge_ready` (a `local` Task is ready to merge, or a PR is ready to merge), the PR Notices of section 14 (`pr_opened`, `pr_checks_failed`, `pr_changes_requested`, `pr_conflict`, `pr_merged`, `pr_closed`, `pr_watch_failing`, `review_policy_violation`), `root_behind` when a new upstream head cannot be synced safely, the validation Notices of section 25 (`ci_fix_queued`, `ci_fix_exhausted`, `ci_rerun_requested`, `head_discontinuity`, `review_round_done`, `review_round_due`, `review_regression`, `review_cap_reached`), plus coalesced `root_fetch_failing` after repeated origin-fetch failures.

Not Notices: ordinary `working`/`idle` flips, `working` Signals, Herdr `done` without a Signal. A Worker `working` Signal that reopens a Task is the `worker_resumed` exception.

A Decision is a question only the User answers. Posse raises one from `merge_ready` under `autonomy.merge=ask`, review findings under `autonomy.review=ask`, failed/lost Tasks, or `worker_exited` when a Worker exits after reporting `done` or `merging`. `posse ask <task> "<question>" --option <choice> --option <choice>` raises a Worker question. `posse decisions` lists pending questions; `--all` includes answered and obsolete ones. `posse decide <id> <option> --user-approved "<User's words>"` records an answer once and raises a `decision_answered` Notice. `posse apply <id>` carries out answered `merge_ready`, `worker_exited`, `recovery`, `review`, `orphan` and `pr_closed` Decisions: `merge_ready` and `worker_exited` can discard with recorded User approval, and `worker_exited` can relaunch; Sandbox recovery relaunches or tears down with recorded discard approval, legacy Directory Task recovery preserves its source and supports Teardown; review queues the User's chosen response for the reviewed Change Task or the Worker that reported findings (ignore takes no Worker action); discard removes the Orphan ref or tears down a closed Task with its recorded User quote; open-task prints the command to start a new Change Task with `posse start --brief <file> [--name <display-name>] --from-orphan <id>`; the new Task replays only the diff from the merged head to the saved snapshot onto its selected base branch, without replaying squash-merged commits; reopen-relaunch reopens the PR and relaunches its Worker. The User's shell needs no approval flag: the typed option is its quote. When a Task Merges, relaunches or tears down before a Decision is answered, the pending Decision becomes obsolete with a reason, never an answer. Notice evaluation advances a per-Project cursor so unrelated and already evaluated Notices are not rescanned.

Store callers use `DB.RaiseDecision(ctx, store.DecisionRequest{ProjectID, TaskID, Kind, Origin, Question, Options})`. `Kind` is explicit: `merge_ready`, `recovery`, `worker_exited`, `review`, `worker_question`, `orphan` or `pr_closed`. `Origin` is only a stable Project-unique idempotency key (for example `orphan:<branch>`); reuse with a different kind is refused. `DB.AnswerDecision(ctx, projectID, id, option, userQuote)` atomically records the answer and Notice. Neither call performs the chosen action.

Delivery, run after any Notice is created and on the triggers in section 8:

1. If no Notice is undelivered, stop.
2. If a delivery happened in the last 20 seconds, stop (the next trigger batches it).
3. `notification.show` once per batch with the count, and set the Project workspace token `posse=<n>` for the sidebar.
4. If the Lead's kind has `notice_delivery = "codex-queue"` and Herdr reports its session: run `codex queue --thread <session> --message <wake>` and mark those Notices delivered. codex holds the message until its current turn ends and never touches the composer, so this works while the pane is focused or busy. On failure, continue with step 5.
5. If the Lead's agent status is `idle` or `done` **and** the Lead pane is not focused: `agent.prompt` the Lead with the same line and mark those Notices delivered.
6. Otherwise leave the Notices undelivered.

Delivery contract: `posse send` and Notice wakes use `[posse | <origin> -> <recipient> <task> | <type> #<ids>]` followed by `body: <JSON string>`. For example, an instruction is labeled `[posse | Lead -> Worker t12 | instruction #7]`; the `body:` value remains the original message as one JSON-quoted inline string; routine messages do not get separate Markdown files. Long Research and Review results remain Report files. Only the header is routing metadata. JSON quoting makes newlines, control characters and forged headers in a Lead instruction or Notice digest reversible body data, not new metadata. Message bodies remain unchanged in storage. Non-Pi harnesses see the textual envelope; Pi Notice wakes have `customType: "posse-notices"` and structured `details.origin: "posse"`, so the UI can show a compact header without marking the wake as User chat. A text prefix alone is not an authentication mechanism; never classify User input as a Notice by its words. A Claude Lead records the exact prompt before a typed Notice delivery; the lowkey renderer requires both a complete valid envelope and its matching record. A verbatim copy of a still-recorded Notice is indistinguishable from the original in Claude Code's drawing API and will also hide. This does not change Notice kinds or acknowledgment.

Worker instruction delivery atomically changes the message to `submitting` and reopens a `needs-decision` Task or a done/merging Change Task immediately before `agent.prompt`. A Change fix also clears `gated_sha`. The transaction commits before the instruction becomes visible, so an immediate Worker Signal sees the authorized state and no late delivery transition overwrites it. When the Worker is idle, Posse waits for the instruction to start a new turn. If none starts while Claude Code's `[Pasted text #N]` placeholder is visible, Posse presses Enter again rather than retyping the text; a placeholder that survives these retries makes the result ambiguous. Steering a working Worker has no such confirmation. If Herdr's result is ambiguous, Posse raises one `message_delivery_uncertain` Notice immediately; after a crash, recovery raises the same Notice when the submission claim expires. The Notice identifies the Task and message, includes the instruction, and directs the Lead to inspect the Worker before sending a replacement. `posse show <task> --full` also exposes uncertain instructions. Posse never retries a `submitting` message automatically, so a crash before Herdr accepts the prompt can leave it unsent. Once its claim expires, the uncertain row and Notice remain intact but stop blocking fresh submissions. Migration 21 makes legacy `claimed` messages uncertain rather than retryable. `posse show <task>` lists queued, claimed, `undeliverable` and `withdrawn` messages; undeliverable rows remain inspectable after the terminal-state Notice, and withdrawn rows remain inspectable after withdrawal. Queue insertion and submission both verify that the Task can still receive instructions, closing races with terminal transitions.

`posse watch` blocks until an undelivered Notice exists. Its legacy path prints the digest and marks Notices delivered. The Pi and OpenCode adapters use `watch --handoff --destination <adapter:session>` instead: Posse records a stable batch ID, exact Notice IDs, destination, Herdr generation, owner token and lease before printing. Printing changes the receipt to `printed`, not delivered. The adapter queries its persisted session before injection and reports `accepted`, `rejected` or `uncertain` through the receipt operation. Acceptance marks the batch delivered. A known rejection releases the same exact IDs for retry under the same stable batch ID. A Pi follow-up remains printed while queued and is reconciled at `agent_settled`, after its session entry is persisted. An ambiguous or unsupported session query holds the batch, creates a `notice_delivery_uncertain` Notice and prevents blind retry. A destination may hold at most two active receipts, bounding one submitted batch plus one coalesced successor; additional batches remain unclaimed until a slot opens. A receipt lease prevents concurrent owners of the same batch; after expiry, a retry to the same destination retains the batch identity and exact IDs, even when the Lead already acknowledged a Notice in that printed batch. Acceptance preserves those acknowledgments. A replacement session cannot claim another session's printed or uncertain batch: it holds the batch for receipt reconciliation. OpenCode checks the prior session history and resolves a recorded receipt as accepted or a confirmed absence as rejected; unsupported or ambiguous history remains uncertain. Pi accepts a matching stable receipt already present in its current session and surfaces uncertainty when it cannot confirm one. Receipt resolution is scoped to the active Project. Project snapshots preserve receipts, Notice state, ownership and leases for rebuild, including the receipt claim on an acknowledged printed or uncertain Notice. Receipt snapshots are associated with Project snapshots by stable Project UUID, so stale names and roots, or an old-name snapshot left by a Project rename, do not prevent rebuild. Rebuild refuses a receipt snapshot whose UUID matches no recovered Project. When receipt and Project snapshots contain the same Notice, the newer captured state wins for delivery and acknowledgment timestamps, and an accepted receipt keeps its Notice delivered. This is not an exactly-once guarantee: an adapter or receiver must use stable IDs to avoid repeating a recorded effect. Posse never replays a held or uncertain batch automatically. Only a confirmed rejection retries the same batch ID. A prompt-only Lead remains delayed while its pane is focused. See [the harness matrix](proof/140-observation-continuity.md).

`posse ack` and `posse watch --ack <ids>` commit only the requested acknowledgements without first running unrelated Project maintenance; selected completed Tasks still follow the `auto_teardown` policy. Unrelated automatic Teardown cannot prevent the acknowledgement commit. Watch reports the newly acknowledged count to stderr immediately after the acknowledgement transaction and includes it in its next result, so later maintenance failures or stops cannot obscure the outcome. A Lead may acknowledge a Notice while its matching receipt is printed and the adapter is still completing the turn; later receipt acceptance preserves that acknowledgement, while a confirmed rejection reopens the Notice. If Watch maintenance fails, it creates a separate retryable `pr_watch_failing` Notice and delivers it instead of aborting before the acknowledgement. Retrying an already acknowledged id is safe. A `watch` Lead (claude) keeps exactly one receipt-backed `posse watch --json --quiet-routine --handoff --destination "claude:$CLAUDE_CODE_SESSION_ID"` running as a background Bash command without a timeout. In the supported local interactive session, it waits without model turns. When Claude Code reports task completion, the Lead reads the named output file to retrieve the JSON batch, handles only that batch, acknowledges its exact IDs so its receipt is accepted, then starts exactly one replacement Watch. It must not start another Watch before the current one returns or retry an uncertain receipt blindly. Unattended and cloud Claude sessions enforce background-task deadlines and are not this Lead runtime. Legacy Stop-hook processes remain supported for sessions already launched with that hook, but new Claude Leads do not install or depend on it. Custom non-Claude `watch` kinds retain their background-command path. While a live Lead-side watch for that Project exists, Posse leaves its Notices undelivered for that watch even when the Lead pane is idle and unfocused; the detached `--poll-only` Project watch is not a Lead-side watch. Posse types a Notice into an idle, unfocused Lead pane only when no Lead-side watch process is live, including after it exits or crashes. Process liveness is checked on each delivery attempt rather than stored as a claim, so a dead watch cannot block the fallback. A `pi-extension` Lead (pi) is started with a posse-generated extension that uses the handoff receipt, acknowledges safe `pr_opened` Notices without a turn when lowkey is on, and queues remaining batches as `posse-notices` custom messages with `pi.sendMessage(..., {triggerTurn: true, deliverAs: "followUp"})`. Its receipt query searches the Pi session entries for the stable delivery or batch ID before injection. A busy-session follow-up stays printed while queued; at `agent_settled`, the extension accepts it only after the matching custom-message entry is persisted, otherwise it surfaces uncertainty. The Pi extension hides the custom message while lowkey is on and shows it otherwise, and applies the watch's lowkey state to the Pi transcript without restarting. A process-wide coordinator gives one active session generation ownership of the watch child and timer across `/reload`, `/new`, `/resume`, `/fork` and shutdown; stale callbacks cannot clear or re-arm replacement state. Accepted-but-unconsumed batches retain their delivery IDs across extension reload. A replacement reconciles a matching session receipt or surfaces the delivery, batch and Notice IDs for explicit resolution. Child spawn and send failures retry with exponential backoff for at most five attempts, then raise one `delivery-error` message and stop retrying until a new session. A confirmed rejection retries the same stable batch ID. An `opencode-plugin` Lead uses a process-local plugin appended through `OPENCODE_CONFIG_CONTENT`, preserving existing inline and file-based plugin config. It appends `lead.md` through `experimental.chat.system.transform` on every model turn and uses the handoff receipt. After a `session.idle` event, it submits actionable batches through `session.prompt` rather than writing to the TUI composer, then queries the session messages for the stable delivery or batch ID before reporting a receipt. While that prompt runs, it starts another Watch to persist at most one successor batch; the successor is submitted only after `session.idle`. The bounded receipt count limits active delivery and coalescing, and plugin shutdown retires its owned child processes and makes in-flight callbacks inert. A reload recovers printed batches by stable ID and checks session history before resending. If a replacement session finds an older printed batch, it checks the named prior session history and resolves a recorded receipt as accepted or a confirmed absence as rejected; unsupported history stays uncertain. OpenCode displays these turns in its transcript even in lowkey mode. ADR 0005 records the harness research behind these modes.

With lowkey mode on, typed and queued wake messages carry bounded, one-line Notice summaries and ids (for example `[posse | Posse -> Lead t12,t9 | notice #7,8]` with a quoted digest body), the current state and the reporting rule. The Lead does not run `posse` merely to learn what arrived. It messages the User only for `needs_decision`, `message_delivery_uncertain`, `notice_delivery_uncertain`, `teardown_escaped_processes` (Task-marked processes outside the Sandbox survived a completed Teardown), `merge_ready` under `autonomy.merge=ask`, failed/lost, `pr_closed`, `review_policy_violation`, persistent `pr_watch_failing` or `root_fetch_failing`, and completed outcomes (`task_done` after review, `pr_merged`). Routine Notices (`pr_opened`, working notes, first `pr_watch_failing`, restarts) are acknowledged silently or grouped in one short line. Lowkey mode off retains the existing reporting behavior. This applies to claude, codex and pi Leads.

Notices stay open until the Lead runs `posse ack <id...|all>`, except an active `root_fetch_failing` Notice is acknowledged when every affected repository recovers. `posse --full` lists open Notices and the full dashboard; `posse --json` retains the complete structured dashboard. Plain `posse` shows active Task ids and states, undelivered Notice count and the next action.

## 10. Stall detection

A Task in `working` is stalled when all hold for `stall_after`:

- Herdr status is `working`.
- The hash of the last 200 lines of `pane.read --source recent-unwrapped` is unchanged.
- The worktree `HEAD` and `git status --porcelain` output are unchanged.

`last_output_hash` and `last_progress_at` are updated whenever an evaluation sees a change, and reset whenever a Task enters `working` or an evaluation is skipped because the Task is not `working` in Herdr. Resetting the stall clock does not clear the separate idle-without-Signal clock. A `stalled` Task whose output or worktree changes returns to `working`. Evaluation runs on every `posse` call and ingest for the Project, and every 60 seconds inside `posse watch`. A stall creates a `stalled` Notice; nothing is killed automatically.

**Idle without a Signal.** A Task in `working` whose agent Herdr reports `idle` or `done` for `idle_after` with no new Signal creates one `worker_idle` Notice per idle episode, keyed by launch and idle start, so a Worker that resumes and goes idle again raises a new one (the state stays `working`; the Lead decides: `posse peek`, `posse send`, or `posse relaunch`). This catches an agent resumed after a restart, or one that simply stopped without reporting. A Claude Code Worker that ends its turn while a background shell it started is still running is not idle, because the shell's completion wakes it. Herdr reports such a pane as `idle` with no field for the job, so Posse reads the pane's process tree (`pane.process_info`, then `ps`): a descendant of the agent that leads its own process group is a background job, and the idle clock stays unset until none remains. MCP servers and hooks stay in the agent's group and do not count. If detection fails, the Worker is treated as idle. A recognized Pi model-error result requires a standalone `Error:` line or an unprefixed `stream error:` line, a known provider signature and Pi's fixed `/bug` help line; only terminal footer content may follow, including Pi's visible `~/` working-directory line. Matching text inside Pi's bordered tool-result panels, including `$ command` shell output, is ignored, so copied tool output cannot trigger recovery. A pane tail may start inside an earlier tool panel; an unmatched horizontal rule immediately before the error closes that truncated panel rather than treating the error as tool output. A recognized model-error episode suppresses this delayed generic Notice while a retry is pending, in favor of immediate bounded recovery or a specific model-error Notice. Pi stream-disconnect retries are limited to three per episode with 250 ms, 500 ms and 1 s backoff; a repeated screen on a new failed turn consumes the same episode budget after Herdr reports the Worker working again, even if normal reconciliation already recorded idle. Duplicate idle events before that transition are ignored. An active episode with no pending attempt retains the delayed `worker_idle` fallback if its end-of-turn hook is missed. Before submission, Posse rechecks the Task state, launch, pane ownership, episode, queued messages and focus/block safety. A `needs-decision` or terminal Signal blocks any pending episode. A charged attempt still incomplete after its backoff deadline plus a five-second submission lease is marked interrupted and produces a specific Notice rather than being replayed with uncertain delivery. The episode, attempts and outcome appear in `posse show` and its full Task signals. Refusals are never retried. No automatic prompt is sent to a focused or blocked Worker, and a queued Lead instruction takes precedence ([ADR 0015](adr/0015-bounded-model-error-recovery.md)).

## 11. Dispatch

`posse dispatch --brief <file> [--name <display-name>] [--profile <name>]` previews a Profile and a safe Task Name. When `--name` is omitted, dispatch and `start` derive a short name from the title, falling back to `task` when a localized title cannot produce a safe ASCII name. `posse start --brief <file> [--name <display-name>] [--profile <name>]` starts the Task. An explicit name is independent of the title, lowercase kebab-case, at most 24 characters and cannot look like a Task ID (`t<n>`). Names may repeat; name/title lookup refuses ambiguity, while `t<n>` remains unambiguous. New Task branches use `posse/t<n>` independently of display names ([ADR 0023](adr/0023-task-branches-are-independent-of-display-names.md)); historical `short_name` and `branch` values remain unchanged. Unsafe names or an existing branch ref fail before Task creation:

1. `--profile` given: use it if it exists, else `profile_unknown`.
2. Otherwise, if any rule has an exact `type` match, consider only those rules. If none match, consider rules with no `type`; their `when` text is descriptive and does not filter structurally.
3. When exact-type rules contain exactly one rule with no `when`, use it as the default for that Task type despite any typed `when` alternatives. Untyped rules, including global rules merged behind project rules, do not compete when an exact-type rule exists. The resolver does not evaluate `when`; the Lead can select a conditional alternative with `--profile` when its judgment applies.
4. Otherwise, exactly one matching rule with no `when`: use it.
5. Otherwise refuse with `profile_required`, listing the matching rules' `when` text and Profiles, so the Lead chooses by judgment.
6. No rule matches: use `dispatch.default.use` when configured.
7. With no Dispatch Rules at all and no default, inherit according to `defaults.dispatch_inheritance`:
   - `kind` (default): use the running Lead's kind with no model or effort arguments, preserving current behavior.
   - `lead_profile`: use the configured `lead.profiles.<kind>` Profile for the running Lead kind, including its model and effort; if none is configured, use that kind without model or effort.

Configured but unmatched rules still require a Profile. A selected Profile whose kind is disabled fails with `kind_disabled`; Posse never substitutes another kind or downgrades its model.

The Task records the Profile and the rule used. Kind inheritance stores `implicit:<kind>` as the Profile reference and `implicit: lead kind` as the rule. Lead Profile inheritance stores the named Profile when configured and uses `implicit: lead profile` as the rule. These markers let historical readers and frozen relaunches retain their original launch even after the kind is disabled. This writes no config; explicit Profiles and Dispatch Rules retain precedence. `posse dispatch` and `posse start` show the configured model and effort plus `model_known`, derived only when the launch arguments unambiguously select the configured model. An empty or ambiguous model remains unknown; Posse does not guess provider identity.

`posse dispatch --brief <file> [--name <display-name>] [--profile <name>]` prints the same resolution without spawning; if Profile selection is ambiguous, `profile_required` includes the Task Name and candidate Profiles in help. [ADR 0022](adr/0022-compatible-dispatch-and-capacity.md) records the compatibility and visibility decisions.

`posse stats` summarizes Tasks created in the last 30 days per Profile, using the Task record, its transitions and the recorded session usage; `--json` output carries `window_days` and a `profiles` list. Each row has `tasks`, `finished`, `landed`, `landed_rate`, `median_done_seconds`, `tokens_per_landed` and `relaunches`. A Task is finished once it is merged, reported, failed, lost or torn down, and landed once it merged or its Report was accepted. `landed_rate` is landed over finished Tasks; Tasks still in flight, and queued Tasks, are not finished. `median_done_seconds` runs from creation to the first `done` Signal; `tokens_per_landed` averages input, output and cache tokens over landed Tasks with known usage. Both are `null` without data. `relaunches` sums launches beyond the first. `posse dispatch` adds the same row as `profile_stats` for the resolved Profile, and when `profile_required` lists candidates its help gains one `stats <profile>: ...` line per candidate. Stats are informational: they never alter Dispatch Rules, Profile resolution or `posse start`, and these outputs only gain fields.

## 12. Pool

Each Project has a Pool of reusable worktrees (Sandboxes) under `~/.posse/pool/<project>/sandbox-<n>`, created with `git worktree add --detach --lock --reason "posse: held by t<n>"` from the Project root. A Sandbox is held by exactly one Task from spawn to Teardown. The point of reuse is warmth: dependencies, build caches and other ignored files survive between Tasks.

**Acquire** (in `posse start`):

1. Lock the lowest-numbered `idle` repository Sandbox before atomically claiming it as `held` for the Task; if none exists, claim the next path and create its checkout with Git's atomic `--lock`. A stale Posse lock can be replaced only after checking that its former Task no longer holds the Sandbox; foreign locks are never replaced.
2. `git fetch origin` in the Project root when an `origin` remote exists (skip otherwise). Reconcile restores a missing lock on every held repository Sandbox, including those owned by failed or lost Tasks, and raises a `sandbox_missing` Notice instead of rebuilding a vanished held checkout. When the checkout returns, it records a separate `sandbox_recovered` Notice without acknowledging the original; a later disappearance creates a new `sandbox_missing` Notice.
3. In the Sandbox: `git checkout --detach refs/remotes/origin/<default>` (or `refs/heads/<default>` without a remote), `git reset --hard`, then `git clean -fd` (`warm`) or `git clean -fdx` (`pristine`).
4. Verify `git status --porcelain` is empty; otherwise mark the Sandbox `broken`, create a `sandbox_broken` Notice, and try the next Sandbox.
5. Create the Task branch, then run `[pool] setup` commands in the Sandbox; a failing setup fails the spawn (`sandbox_setup_failed`) and releases the Sandbox.

**Release** (in `posse teardown`, and when a spawn fails before the agent starts):

1. Normal Teardown stops processes carrying the Task's inherited `POSSE_TASK_ID` marker and the Task's Linux cgroup, when available: SIGTERM, grace period, then SIGKILL through retained pidfds. Marker scanning catches Task-launched processes that Herdr started outside the Worker pane's cgroup, but a marker alone never authorizes a process in an unrelated pane or the Worker foreground. Teardown retains exact process instances, checks Herdr pane ownership before signaling the Worker foreground or shell, and verifies the shell's recorded executable image. It verifies processes in the Task's held or releasing Sandbox and validated scratch root. Never signal an unretained process or one outside the Task containment. Approved discard stops only the verified Worker instance and retained descendants, closes its verified panes, then refuses Sandbox release while residual Sandbox or scratch processes remain.
2. Detach at the last fetched default-branch ref, `git reset --hard`, make untracked paths writable inside the Sandbox, clean per `[pool] clean`, then mark it `releasing` before unlocking the repository Sandbox. Teardown never fetches; it uses the last fetched default ref or the local default branch if no remote-tracking ref exists, and the next Sandbox acquisition refreshes origin first. Finalize it as `idle` after unlock. Reconcile completes an interrupted `releasing` Sandbox without making it reusable before cleanup; an interrupted held Sandbox remains locked.

A Sandbox is never released while its Task holds unmerged work, except through an approved discard. A Change Task whose branch has no commits beyond its base and whose Sandbox is clean holds none: its Worker finishes with `posse signal done --no-change "<evidence>"`, and `posse teardown` releases it without `--discard`. `posse merge` refuses it with `merge_refused` and names `posse teardown`, and `posse show` suggests teardown instead of merge, in every delivery mode. On Linux with a delegated user cgroup v2 subtree, each Worker's pane shell is moved into a Task-specific cgroup recorded on the Task. Cgroup membership proves Task ownership. Marker-only processes are retained for signaling only while they reference the held Sandbox or Task scratch; other marked processes without independent Task ownership are preserved but do not block release unless they remain as a Task-marked foreground in the Task workspace or still reference the Sandbox. Teardown lists such a surviving process in `escaped_processes` and raises a `teardown_escaped_processes` Notice with its PID and command, so a double-forked daemon that left the Sandbox does not outlive Teardown unreported. Teardown stops cgroup members and descendants and additional processes carrying the Task's exact inherited `POSSE_TASK_ID` marker. When user cgroups are unavailable, Posse uses the marker and retained Linux pidfds. Each Worker also receives `TMPDIR`, `GOTMPDIR`, `TMP`, `TEMP` and `POSSE_TASK_TEMP` set to `~/.posse/scratch/<project>/<task-id>/`. The Worker protocol directs all temporary files, fixtures, test homes and Task-specific caches there; `--findings` and `--report` files may come from that Task's scratch or its worktree. Worker commands use one Posse-owned `GOCACHE` at `POSSE_HOME/cache/worker-go-build`, shared across Tasks; `GOMODCACHE` remains the User's shared module cache. Teardown preserves the Report or Orphan, then removes Task scratch before releasing the Sandbox. A cleanup failure leaves the Sandbox held and raises a `teardown_blocked` Notice with residual PIDs, commands and listening ports where available, alongside `teardown_incomplete`. The Notice tells the User to stop the listed processes or move their cwd and open files outside the Sandbox, then retry Teardown. Global temporary storage and other Tasks' scratch are never deleted or claimed as Posse-owned; processes launched by a Worker remain inside its process containment even if they use those directories.

Teardown preserves a recognized shared daemon when its parent chain has left the Task's marker/cgroup ancestry: SSH ControlMaster/ControlPersist, Gradle and Kotlin daemons, `gopls -remote=auto`, sccache, tmux servers and screen servers. A shared daemon may outlive Teardown, but any live process that still references the Sandbox through its current directory, an open file or a mapped file blocks release. Teardown keeps the Sandbox held, reports the residual PID and command in a `teardown_blocked` Notice with a remedy, and succeeds on retry after the process exits or closes its references. Ordinary Task dev servers, browser profiles and test helpers remain Task-owned and are stopped.

A workspace Project's Sandboxes differ as section 24 describes: a Sandbox is a folder that mirrors the workspace root, with one warm worktree per member.

Posse stores canonical resource leases in the shared database. Path scopes resolve existing symlink components and conflict on equality or ancestor/descendant overlap, regardless of Project registration. Git-ref scopes use the canonical Git common directory and fully qualified ref; conflicting ref hierarchies serialize while independent branches remain available. Every held or releasing Sandbox is reconciled into a path lease. A quarantined (`broken`) Sandbox holds no lease: breaking it releases the lease in the same transaction, so a Task that falls back to another Sandbox holds exactly one. Leases have no expiry: a crashed executor leaves its claim in place until intent recovery or explicit custody reconciliation proves the effect is settled. Project snapshots preserve leases across database rebuilds. `posse pool` displays active resource scopes and owners across Projects. After inspecting the scope and confirming the owner stopped, the User can run `posse pool reconcile-resource <lease-id> --user-approved "<User's words>"`; it refuses a live owner, active intent or Sandbox lease.

The `sandbox_broken` Notice states the failure cause and both recovery commands. **Repair**: `posse pool repair <sandbox-number>` is an explicit recovery for one broken single-repository Sandbox; it is separate from `pool prune`. The path must belong to the Project's managed Pool, the Sandbox must have no live process references, and any prior Task must be torn down with no active intent. Git metadata must resolve to the Project repository; repair may re-register that verified worktree and releases only a stale Posse lock owned by the completed Task. Before resetting, repair copies tracked, untracked and ignored work into that Task's attachments and records tracked deletions in `saved-work.json`; if preservation conflicts or no completed Task can own dirty work, the Sandbox stays broken. It applies the configured warm or pristine clean policy, verifies a clean worktree and released lock, then marks the Sandbox idle in the database. It never signals processes, discards unpreserved changes, prunes branches or removes the Sandbox. Foreign locks and corrupt or foreign Git metadata remain quarantined for manual recovery. Workspace Sandboxes are not supported by this command.

**Prune**: `posse pool prune [--yes]` is a dry run by default and lists reclaimable items with byte sizes. It removes idle Sandboxes beyond `keep_idle` (highest numbers first), safe quarantined `broken` Sandboxes, stale Git worktree registrations beneath this Project's Pool and its Workspace member repositories, orphaned or terminal Task scratch, local branches whose merged content or approved discard tip is captured, and expired Report bundles and Task attachments. Scratch candidates use current Task ownership, not a cached Task list. Before scratch removal, prune serializes with Task creation, relaunch and scratch acquisition, rechecks the Task state, active intent and Sandbox, then stops and verifies processes using that validated Task scratch root. A concurrent owner or unverified process state leaves scratch intact and returns a retryable error. Global temporary storage and other Tasks' scratch are not claimed. A recorded `MERGED` observation permits removing a `pr` branch, or one of a Task admitted under the removed `no-mistakes` mode, only at its exact observed head; advanced branch tips are preserved. Branches with an active Task operation, a held or releasing Sandbox, or a live worktree checkout are excluded and rechecked when `--yes` applies the plan. It never removes held Sandboxes or unmerged branches. Repeated runs are safe. Pane results use `orphan_panes`, distinct from saved Orphan work. Each prune row reports `applied`; if a later removal or orphan-pane check fails, the result includes applied rows, available pane-close results and a structured error, then exits non-zero. Workspace Sandboxes are removed member by member. `[retention] task_artifacts` defaults to `2160h` (90 days) and controls Report, attachment and approved discard-tip bundle retention after Teardown. `posse pool` (no subcommand) lists the Project's Sandboxes with state, Task and path, plus active resource lease IDs, scopes, owners and custody across registered Projects. `posse clean [--dry-run|--yes]` is a dry run by default across registered Projects for the User, or the current Project for its Lead. It lists finished Tasks, per-Task scratch and Sandbox byte sizes, process PIDs and commands, and whether a Sandbox is held. `--yes` stops and verifies eligible finished Tasks before Teardown and reclaims their Task scratch and safe held Sandboxes; blocked cleanup is reported per Task without discarding unmerged work. `posse doctor` reports total POSSE_HOME disk use, per-Project scratch, Pool and artifact sizes, per-Task scratch sizes, and residual processes for non-active Tasks, including listening ports where available. It warns when the User's shared Go build cache reaches 8 GiB or the Posse Worker cache reaches `worker_go_cache.max_size`. The User cache is diagnostic only and Posse never deletes it. Every Project watch and every successful Task Teardown run the shared Worker `GOCACHE` trim, at most once per `[worker_go_cache] interval` (default `1h`) across all Projects. When usage has reached `max_size` (default `8GiB`), the trim removes the least-recently-used regular files until usage is below `max_size`, skipping files used within `min_age` (default `6h`, at least `2h`). Go refreshes a cache entry's mtime whenever it uses one more than an hour old, so entries that active Workers use are never removed, and each file's mtime is rechecked just before removal. The trim therefore runs while Workers build and needs no idle period. It preserves Go's root `trim.txt` metadata and bucket directories, never changes `GOMODCACHE`, and never trims any other cache. `[worker_go_cache]` is valid only in the User config because the cache spans Projects. If entries used within `min_age` keep usage above `max_size`, `posse doctor` recommends raising `max_size` or lowering `min_age`.

## 13. Brief and Worker protocol

Brief file, written by the Lead anywhere and copied into the home by `posse start`:

```markdown
---
type: change                  # change | research | review
title: Fix flaky login test
done_when: login spec passes 20 consecutive runs in CI mode
merge_mode: pr            # optional; lighter delivery needs scoped User choice
# review: quick             # target mode (section 25); lighter review needs scoped User choice
# base: staging              # optional branch to start the Task from
# target: staging            # optional PR/MR target; workspace may use {backend: staging}
# review_of: t12            # review only
# supersedes: t12           # Change only; requires a User-approved Review-cap rethink
# report_kind: spec         # Research only: spec | tickets
# repos: [backend, worker]  # workspace Projects: the members to check out (section 24)
# root_context: read-only   # workspace Projects: explicitly include bounded shared-root context
ticket: 12                  # optional: the one issue this Change Task should close
# issues: [12]              # legacy singleton alias for ticket:
refs: [18]                  # optional: issues this Task refers to without closing
# Workspace Projects scope issue references to a member: ticket: worker#12
# Issue references accept 12, "#12" and worker#12; quote "#12", since an unquoted # starts a YAML comment
autonomy: { merge: ask }     # optional, tighten only
---
<body: goal, context, constraints, User's intent in their words>
```

Brief frontmatter is a flat `key: value` subset of YAML. `done_when` also accepts a block list of items, which Posse joins with `; ` into one criterion; every other field rejects a YAML list with `YAML lists are unsupported`, whatever the item text. Use inline `[a, b]` lists where a field takes several values.

```yaml
done_when:
  - tests pass
  - "Root cause at foo_test.go:178 is identified"
```

A Change Brief may use `supersedes: t12` only after the prior Change Task's User-approved Review-cap `rethink`; the new Task inherits its Finding Ledger as visible, non-blocking entries and suppresses repeat reports. A Change Brief may name one closing issue with `ticket: 12`; a standalone Change Task may omit it. During compatibility, `issues: [12]` is accepted as the same singleton, and if both fields appear they must name the same issue. New Change Briefs reject multiple `issues` before a Sandbox is acquired. Existing multi-issue Tasks remain historical and their Briefs are not rewritten. Workspace Projects qualify the ticket and each `refs` entry with its owning member, such as `ticket: worker#12` and `refs: [worker#18]`. A ticket cannot also appear in `refs`. `ticket` closes only that issue when a PR/MR Merges; `refs` never closes issues. `posse dispatch` warns when a listed issue does not exist or is already closed, and says when it cannot verify one. `posse show` and `posse list --full` display the ticket and references.

`report_kind` is valid only on a Research Brief and accepts `spec` or `tickets`. Every new Research Task's Report and saved attachments are sealed at Teardown in `report-manifest.json`; its SHA-256 digest and manifest are stored in the Task snapshot. A legacy Research without a recorded Sandbox cannot be resealed or accepted. Missing, escaping, non-regular or changed attachments make Teardown or later acceptance fail closed. The bundle cannot be silently replaced. `posse accept <task>` records User acceptance only for a torn-down `spec` or `tickets` Report whose current digest has an independent Report-review pass. A Lead must supply `--user-approved "<User's exact words>"`; a direct User command does not need the flag. `autonomy.review`, a done Signal and Notice acknowledgement never count as acceptance. Ordinary Research Reports remain readable and do not require acceptance. Until independent Report-review results can be recorded, publication-bound acceptance remains unavailable rather than bypassing the review gate.

**Admitted execution plan.** New Tasks resolve the existing Brief contract through `internal/taskplan` before Project preparation can recover Workers or allocate Task resources. The versioned plan freezes the outcome (`change` for Change, `report` for Research/Review), Worker executor, execution mode (Sandbox), repository/Workspace scope, selected Members, base/target branches, current review and Merge Mode, Autonomy values with their Brief/config sources, managed scratch/output paths, resolved Profile/kind launch settings, and effective artifact prose language. Unsupported combinations fail before Task, intent, scratch, Sandbox, branch or pane allocation. The `root_context` Brief field selects bounded read-only shared-root context for a workspace Task; absent selection means no shared-root copy for new Tasks. The optional `review:` field selects `none`, `quick` or `full-pipeline` under the target contract in section 25; it is distinct from `autonomy.review`, which grants authority to decide findings, not evidence. Version-2 plans freeze each Member's effective review policy and source, resolving its override before the Brief. Tightening is checked against each selected Member. Version-1 plans retain their frozen legacy behavior and expose `review_evidence: legacy-evidence` in `show` and Worker `status`; they acquire no new evidence guarantee. Explicit legacy values in new config or Briefs are refused. Without a scoped User choice, preference requests retain tightening-only behavior. `start --user-approved` records the exact quote, caller role, selected Brief digest and explicit delivery/review/base/target fields in the admitted plan, persisted with its revision and snapshots. The flag cannot authorize fields supplied only by Brief prose, grant Autonomy or change Sandbox setup or launch commands. Empty quotes and choices without explicit preference fields are refused. Repository and workspace Tasks run in Sandboxes. There is no general workflow DSL or provider identity inference. Version-4 plans freeze any selected workflow profile's content, stage/order, gates, Task types, Worker bounds, source and digest; relaunch does not reread them. Unconfigured direct Tasks need no profile.

Selected inputs retain their exact bytes and SHA-256 digests: the Brief, existing Worker preference sources, embedded Posse skills, normalized consumed launch settings and, for Codex, only the consumed `developer_instructions` field. Other Profiles, unused configuration fields and unrelated forge comments are not copied. Stored Brief readers use the admitted bytes, so editing a source or `brief.md` cannot change a Task's closing issue. Sequence allocation, binding managed paths, storing revision 1 and recording the `start` intent share one transaction. Existing Tasks without a plan remain legacy, including live Tasks and historical multi-issue Briefs.

`posse status` takes no Task id and reads only the calling Worker's recorded Task and admitted plan (or `admission: legacy`). It opens SQLite read-only and never loads current config, migrates, calls Herdr, recovers Workers, synchronizes repositories or performs cleanup. `posse show <task> --full` exposes the plan to the Lead through the existing inspection path.

`posse start`:

1. Validates an optional `--name`, then the Brief. An explicit Task Name is safe lowercase kebab-case, at most 24 characters, and cannot be a Task ID; it need not match the title. When omitted, Posse derives a short display name from the title or uses `task` when no safe ASCII name can be formed. Repeated names are allowed, but lookup by a repeated name or title returns `task_ambiguous`; `t<n>` is the stable selector. For Change Tasks, the title uses conventional-commit form `type[(scope)][!]: description` (for example, `feat(app): enable outcome-first runs`) and becomes the initial forge pull request title unchanged, without an id or slug prefix; a Lead may set a later title with `posse retitle` (section 14).
2. Checks `max_workers` (`worker_limit`). A Worker slot is held by every `spawning`, `working`, `needs-decision`, `blocked` or `stalled` Task and by every Change Task in `done` or `merging`, because its Worker stays live and can return to `working` for CI fixes, merge-target syncs and Lead instructions. A slot is released only when the Task leaves those states (merged, torn down, failed or lost), so a follow-up never exceeds `max_workers` and queued refill never takes a slot a PR follow-up needs. The cost is that Change Tasks awaiting merge delay queued Tasks.
3. Resolves the Profile.
4. Chooses the next unused Task sequence, skipping existing Task history and `tasks/t<n>/` directories, and checks the Task-bound branch `posse/t<n>` against Task history, local refs and origin refs in the repository or selected workspace Members. A collision returns `branch_exists` before Task creation; a concurrent sequence change refuses admission and can be retried. Unrelated workspace Member failures or collisions do not block admission. It validates explicit `base:` and `target:` branches on origin without fetching, resolves config and selected-Member overrides, and freezes each target name and explicit base commit on the Task's plan; a base may be another published Task branch to form a stack, and base and target remain independent. The Task's `seq`, stored `branch` and `start` intent are committed together; the stored branch must match its allocated `seq`. It acquires a Sandbox (section 12), checks out `posse/t<n>` with `git checkout -b` (never `-B`) from the pinned explicit base commit or fresh default branch (review: from the reviewed Task's branch), and opens the Sandbox with `tab.create` in the Lead workspace (`cwd` = Sandbox, `label` = Task Name, `focus=false`, `POSSE_WORKER_HOME` set). Posse reports pane `display_agent` using the resolved harness, then labels the pane with its Task identity ([ADR 0013](adr/0013-all-workers-open-as-lead-tabs.md)). The Lead's workspace comes from a fresh snapshot: the one holding the Lead's labeled pane, or the recorded one if it is still labeled `Lead:<project>`; otherwise `lead_missing`. It does not create a top-level Worker workspace or another Git checkout. The Worker tab cwd remains the Sandbox path.
5. Runs the kind's `prepare` step, if any (below).
6. Labels the root pane `posse:<project>:t<seq>`, writes `brief.md` and `launch.md`, then starts the agent with `agent.start` (name `posse-<project>-t<seq>-<launch>`, cut to 32 chars and never derived from Identity, where `<launch>` counts launches of this Task so a relaunch never collides with a name Herdr has not released yet; args = kind `auto_approve_args` + `model_args`/`effort_args` filled from the Profile + Profile `args`, preceded for Claude by the attribution-off `--settings` unless the Profile sets `attribution = true`). The canonical pane label and all internal identifiers remain unchanged. `launches` and its Launch Identity Record (Task id, launch number, Profile name, configured model value and whether that value is determinable) are committed together before each `agent.start`; relaunches append records and never replace earlier identities.
7. Codex and OpenCode receive `Read <launch.md path> and follow it.` as an opening argument in `agent.start`; these are the existing opening-argument paths. Claude and Pi first become interactively ready, then receive the instruction through a focused-safe typed prompt because Herdr keeps an opening-argument start pending for the first turn, which prevents steering. Focus does not delay launch. After Herdr observes the first turn working, the Task becomes `working`. Relaunch uses the same per-kind delivery paths with `relaunch.md`. If recovery of an interrupted Claude or Pi start cannot type the prompt because its pane is focused, the Task remains `spawning` for a later retry; Posse raises a `spawn_waiting` Notice if that recovery remains unresolved past the launch retry window. A failed spawn with a written Brief keeps its initialized Sandbox for `posse relaunch` on the same branch.
8. Refreshes the Worker's pane metadata after launch and relaunch. `display_agent` is set to the resolved harness (`pi`, `codex` or `claude`) before `agent.start` and the detected harness afterward, never the unique internal agent name. Herdr's grouped Agents panel renders flat rows in workspace order. Worker tabs use tree `posse_row` tokens to appear under the Lead; reconciliation restores tab labels and metadata after launch, relaunch, Teardown and recovery. Priority sorting and custom agent views remain User choices. Existing linked-child Workers keep `posse_row` empty until teardown. The Lead (`Lead:shop`) and Worker rows render with the harness on the next line. `identity.worker.display_prefix` is deprecated and has no effect. The full Task title, display name and Sandbox path are submitted as the pane title, but Herdr truncates long titles and token values. Metadata tokens `posse_title`, `posse_name` and `posse_branch` preserve the title, display name and actual Task branch within Herdr's limits; `posse_sandbox` holds only the Sandbox basename to avoid a misleading mid-path truncation. The full Sandbox path remains in the pane cwd and Task record. This does not change pane cwd, the canonical pane label (`posse:<project>:t<seq>`), agent name or Task ID.
9. Displays the Task Name in `posse`, `posse list` and `posse show`; Notice rows and wake bodies lead with the full Task title. Tasks without a recorded name display their title. `posse start` reports the Task-bound branch, and `posse show --full` preserves noncanonical historical branch values. Internal Task IDs remain available for commands and canonical pane labels.

**Independent Review identity** (the existing Local Review rule; `quick` is the review-policy rename). A local Review Task is a fresh Task and starts a new agent session, not the Change Task's session. Before launch, Posse compares the Review Profile name and configured model value with every recorded launch of the reviewed Change Task. Both must differ from every author launch. An absent/unconfigured model, an additional model-setting argument, an argument Posse cannot classify for that harness, a missing author launch record, or a same-Profile/model match refuses the Review launch with the compared identities and reason. Posse parses the argument vector for the launch being recorded, including rendered resume arguments; a model-setting override or unclassified argument records the model as unknown. Profile changes on a Change Task retain earlier launch records. `posse show <review>` reports the comparison; `posse show <task> --full` lists its Launch Identity Records. Posse does not infer provider identity from harness names.

**Review verdicts** ([ADR 0020](adr/0020-review-verdicts-bind-completed-revisions.md)). A normal Review Task is admitted only for a Change Task that is `done` or `merging`; otherwise `review_target_incomplete`. The initial `full-pipeline` path also admits independent review of a submitted unpublished private candidate without that PR/done precondition (25.1). Admission resolves the bound candidate (the Change branch tip on the existing path) to a full commit SHA, per repository for a Project (named by the Project) or per changed Member for a workspace, and stores it in `review_targets` in the same transaction that creates the Task. Targets are insert-only. A Reviewer cannot choose a branch or SHA, and a Review Task created before this record existed has no target and cannot record a verdict (`review_target_unbound`).

A Review Worker reports `posse signal done "<summary>" --report <file> --verdict pass|changes_requested|inconclusive`. `--verdict` is refused on every other Signal and Task type. A missing `--verdict` still reports the Report but records no verdict; an unknown value is refused before anything is recorded. Posse refuses the Signal when the Reviewer's worktree does not contain every bound commit. In the Signal transaction it writes the verdict with the SHA-256 of the copied `report.md`, a copy of the bound targets and the Reviewer's current Launch Identity Record, all read from Posse's records. A Task accepts one done Signal, and `review_verdicts` holds one row per Task, so a duplicate completion cannot add or replace a verdict. Rebuild from Task snapshots restores targets and verdicts.

A verdict qualifies the Change Task only while its targets equal the Change branch tips resolved now, so a changed candidate has no current pass and an old pass is never rebound to new commits. Only `pass` is a passing independent verdict (loop carries and User dispositions are separate evidence in 25.8); a missing verdict, `changes_requested`, `inconclusive` or a pass whose Reviewer launch no longer differs from every author launch does not. With selected review policy `quick` (the migrated name for `local`), `posse merge` refuses with `review_required` until a current qualifying pass exists. `posse show <review>` reports the verdict, targets, Report digest, Reviewer launch and whether it is current. Research Report review is not part of this record.

With the Review Loop enabled for the Change Task (section 25), each Review Task is a numbered Review Round with a bound delta scope, requires `--findings`, and Posse derives its verdict from the Finding Ledger.

**Selected review policy (D02).** Current review modes are `none`, `quick` and `full-pipeline` (section 25). The `local` -> `quick` config migration runs automatically; `full-pipeline` can be selected and frozen; single-repository and workspace Member lanes, with PR or local delivery, have ordered private validation and internal promotion, but the policy remains not production-ready (25.1). `defaults.review` defaults to `none`; `repositories.<member>.review` overrides it for a workspace Member. Both are User-only and frozen at admission. `none` requires no independent-review record, but fast-forward checks, required forge checks and merge-authority checks remain. `quick` preserves the former `local` policy: a separate identity-eligible Review Task must cover the exact current branch commit (per changed Member), with the loop evidence extensions of 25.8. Publication may precede quick review; Merge may not. `full-pipeline` additionally requires private exact-head review -> test (intent proof) -> docs -> lint validation before public publication. `posse publish` from the Task Sandbox submits a private candidate; from its checkout it promotes only a fully validated candidate. Posse checks evidence before opening Merge, after recording `gated_sha` before `done -> merging`, and immediately before each merge. A missing, stale, failed or identity-ineligible verdict causes no merge effect. Neither `autonomy.review = "lead"` nor `autonomy.yolo` supplies or bypasses evidence. Tasks admitted under the removed `no-mistakes` review keep their stored receipts as history (below). No risk classifier, Merge risk flags or risk-assessment records exist. The publish `--risk` field is PR documentation, not a review-policy override.

**PR and pipeline-owned candidate evidence (D03).** For PR/MR Merge the candidate is the gated PR head, not an independently advancing Sandbox tip. Full-pipeline validation first binds the unpublished private candidate; after promotion its validated SHA must equal this PR head. `posse merge` checks the selected evidence at the recorded merge head before `done -> merging`. `posse merge --execute` reads the forge head, which must equal `gated_sha` (`branch_moved` otherwise). Under the merge lock it then requires the newest PR observation to be green at that head (`checks_not_green` otherwise) and rechecks the selected evidence at that head, immediately before the forge merge pinned with `--match-head-commit`/`--sha`. A green observation or verdict for an older or different head never qualifies. `quick` requires a D01 pass whose target is that exact commit, or the review evidence specified in 25.8. `full-pipeline` also requires all applicable local stages on that commit before publication and matching forge CI after publication; the forge CI check is not a substitute for the publication barrier. Workspace Member PRs recheck the selected Member policy under the merge lock before each Member merge; exact Member vectors belong to D04. PR Merge recovery has no merge effect to repeat: an interrupted `merge --execute` intent is settled, and the next PR observation records any merge that happened.

`no-mistakes` review receipts recorded before the removal (25.17) stay in the insert-only `review_receipts` table with Posse's SHA-256 of the exact receipt bytes, kept in Task snapshots and listed by `posse show` as `review_receipts`. Posse no longer queries `no-mistakes axi receipt` or records new receipts; a still-live Task with a frozen `no-mistakes` review refuses Merge with `no_mistakes_removed`.

When the forge reports a merge, Posse evaluates the selected evidence at the merged head. If it is missing, the Task still Merges ([ADR 0011](adr/0011-a-merged-pull-request-merges-its-task.md)), no pass or receipt is recorded, and a `review_policy_violation` Notice names the head and the evidence error.

Explicit legacy `always`, `on_risk` and `never` config values fail even when a newer layer overrides them. The error names the file/key and requires an explicit User selection of a supported review mode, or unsetting the key to inherit the default. New config and Briefs reject `local` with `quick` as its replacement; stored config is migrated automatically on update. Use `posse config set <key> <policy>` or `posse config unset <key>`, adding `--project <name>` for Project config and the recorded User quote from a Lead. Historical plans keep their frozen behavior: version-1 legacy policies retain their old evidence rules, while version-2/3 `local` plans continue to require the same independent review. Their visible legacy status is not conditional review or a new policy selection.

A Review launch refuses session selectors in Profile arguments and any launch argument Posse cannot classify. On relaunch, only one explicit `{session}` selector in the kind's resume arguments may select the Review Task's own recorded session; extra selectors, model overrides and unclassified arguments are refused. This does not detect an agent switching sessions after launch.

A Launch Identity Record proves only the Profile and model value configured for that launch. It does not attest runtime model identity, detect an in-session switch, or prove that differently named configurations use distinct underlying models. No provider attestation or sandbox is added.

**Prepare steps.** A fresh worktree is a folder the agent has never seen, and some agents stop at an interactive trust dialog before reading anything; auto-approve flags do not skip it (Claude Code shows "Do you trust this folder?" even with `--dangerously-skip-permissions`). Built-in steps:

- `claude-trust`: before launch, set `hasTrustDialogAccepted` on the Sandbox's entry and on the primary checkout's entry in `${CLAUDE_CONFIG_DIR:-~}/.claude.json`. Only keys that are absent are set: a recorded `false` anywhere is never overwritten, and the Sandbox's own recorded import answers are kept. Carry the external `CLAUDE.md` import approval to the Sandbox only when the primary checkout already has it. Running Claude processes rewrite this file, so write it with a temp file and rename, then re-read and retry (up to 3 times) until the entries are present.
- `codex-trust`: append a `[projects."<sandbox>"]` block with `trust_level = "trusted"` to `${CODEX_HOME:-~/.codex}/config.toml` as text when no block for that path exists. The rest of the file, including comments and order, is never rewritten.

A kind without a prepare step that still stops at a dialog surfaces as `blocked` with a `worker_blocked` Notice.

`launch.md` = Worker protocol + Brief body + the effective Worker preferences. At dispatch, Posse copies legacy and canonical User sources first and then legacy and canonical Project sources, with source headers, into `launch.md`. This snapshot does not change when source files are edited; `posse relaunch` rereads the existing `launch.md`, so the admitted Worker instructions survive relaunch. Workspace Tasks use the Workspace Project preferences, not a member-specific layer. Preferences are supplemental and cannot override the Brief, protocol or runtime boundaries. The protocol says:

- Work only inside this Task's admitted execution root. Read Project context as needed and write only in the admitted Sandbox worktree.
- Run any Herdr or posse experiment against an isolated Herdr server and a `POSSE_HOME` under a temp dir (unset every `HERDR_*` variable, then point `XDG_CONFIG_HOME` and `POSSE_HOME` there); never touch panes, tabs or workspaces you did not create.
- For Sandbox execution, commit on your branch. Under `full-pipeline`, `posse publish` from the Task Sandbox submits the committed head as a private candidate without pushing or opening a PR (25.1). Run Review -> test -> docs -> lint in that checkout, then run `posse publish` there to promote the validated candidate before signaling done (with the PR URL for single-repository PR delivery). A workspace Worker adds `--repo <member>` to every publish and validate command and promotes each changed full-pipeline Member before signaling done. Local delivery promotion fast-forwards only the Task branch; Merge integrates it. The policy is not production-ready (25.1). The existing publish-before-done protocol below describes `none`/`quick`, not permission to bypass the barrier. Validation must be able to review a submitted unpublished candidate without requiring an already published PR or done Signal. For a repository `pr` Change Task using `none` or `quick`, run `posse publish "<summary>" [--verify "<command> -> <result>"] [--proof "<markdown>"] [--risk "<markdown>"]` to push only your Task branch and open or adopt its PR, then report the URL with `posse signal done "<summary>" --pr <url>`. For a workspace using `none` or `quick`, add `--repo <member>` for every changed PR member and report done without `--pr`; Posse verifies each recorded member PR. Supply verification commands and results, screenshots/images for UI proof or test/log evidence otherwise, and risk plus rollback details. Never push directly, force-push, delete branches, change the default branch, or merge. In `local` mode, do not push or open a PR.
- Report with `posse signal`:
  - `posse signal working "<note>"` for rare progress notes.
  - `posse signal needs-decision "<question>" [--findings <file>]` when you need an answer. For Sandbox Tasks, store `--findings` and `--report` files in the Worker's worktree or that Task's scratch directory; Other paths are refused.
  - `posse signal done "<summary>"` for Change Tasks. Sandbox execution requires commits ahead of base and a clean worktree; Repository `pr` mode requires `--pr <url>`. For workspace Change Tasks, Posse checks every changed PR member's recorded URL. Each PR's source repository, Task branch, target branch, open state, remote head and local commit must match.
  - `posse signal done "<summary>" --report <file-in-worktree-or-task-scratch>` for Research and Review. Non-ignored untracked and edited Member files, plus committed changes beyond each selected Member's Task base, are preserved beside `report.md` at their worktree-relative paths during Teardown. Legacy workspace Tasks also preserve unrequested Member commits and shared-root changes against their acquisition snapshot. New workspace Tasks do not copy shared-root files unless `root_context: read-only` is selected; the bounded copy is read-only and changes are rejected at completion. Later changes to the live Project do not alter a legacy baseline; unchanged Project copies and `.git` metadata are not attached. If a required baseline or Git enumeration fails, a repair-or-discard Decision blocks Teardown and keeps the Sandbox. Repeatable `--attach <file-or-directory>` includes ignored Member evidence or unchanged shared-root files available in an explicitly selected read-only context or a legacy Sandbox at Signal time. The Report should reference saved paths; `posse show <task>` lists attachments.
  - A `done` Signal is refused while queued, claimed or interrupting Lead instructions remain undelivered. Let the turn end so Posse can deliver them, apply them, then retry `posse signal done`.
  - `posse signal done "<summary>" --report <file> --verdict pass|changes_requested|inconclusive` for review only; Posse binds the verdict to the Review Task's recorded Change revision and Reviewer launch.
  - `posse signal failed "<why>"`.
- Answers and new instructions arrive as normal prompts.
- Waiting: for kinds with `background_commands`, run long commands (full test suites, e2e, builds) as background commands and never poll them; do other work or end the turn. For every kind: never end a turn while a detached command (shell `&`, `nohup`, `setsid`, a polling loop) runs, because nothing wakes the Worker when it finishes; wait in the foreground or, for kinds with `background_commands`, use a background command the harness tracks. Do not wait for PR CI after `posse signal done`, because posse watches the PR and the Lead sends fix instructions.

`posse signal` finds its Task from `HERDR_PANE_ID` (matching only Tasks that are not torn down), falling back to a Sandbox path for legacy execution. Lead-only commands run only from the Lead's pane: inside Herdr, a missing `HERDR_PANE_ID`, a pane that is not the Project's recorded Lead pane, or a cwd inside any Sandbox refuses with `lead_only`.

**Worker isolation** ([ADR 0007](adr/0007-isolate-workers-from-the-user-session.md)). Herdr gives every pane the full API of the User's session and has no per-pane scope, so posse enforces the protocol's isolation rule itself:

- **Worker mode.** A process is a Worker of a posse home when it or any process it descends from was started with `POSSE_WORKER_HOME` naming that home or runs inside one of its Sandboxes, or when its `HERDR_PANE_ID` is a Task's pane there. Ancestors are read from `/proc` (Linux; elsewhere only the process itself is checked), so `env -u`, `cd` and subshells do not shed the identity. Against that home a Worker may run only `posse brief`, `posse signal`, `posse publish`, `posse validate`, `posse _context` and `posse config show|schema`; every other command refuses with `worker_forbidden` before doing anything. A Worker experimenting under another `POSSE_HOME` is not a Worker of it. Only a working `pr` Change Worker (or the Worker of a workspace Task with a PR-mode member named by `--repo`) may use `posse publish`; it takes no refspec or merge flags and pushes only that repository's recorded Task branch without force.
- **Worker guard.** `posse _guard` reads a `PreToolUse` hook payload (`tool_input.command`, a string or an argv array, and `cwd`). Outside a Worker it exits 0. In a Worker it parses the command as bash and follows `export`, `unset`, `cd`, `env [-i] [-u NAME] [-C DIR] [-S STRING] [NAME=VALUE]`, inline assignments, wrappers (`command`, `exec`, `nohup`, `time`, `timeout`, `nice`, `setsid`, `sudo`, `doas`, `stdbuf`, `xargs`, `flock`, `watch`, `script -c`, `find -exec`), `sh -c`, `eval`, `source`, shell script files and executables with a shell shebang (read up to 1 MiB, six levels deep), heredocs, here-strings and piped stdin. It resolves the Herdr socket each `herdr` call reaches the way the herdr CLI does (`HERDR_SOCKET_PATH`, then `HERDR_CONFIG_PATH`, `XDG_CONFIG_HOME`, `HOME`, `HERDR_SESSION`). A `herdr` call aimed at the session the Worker runs in is refused unless it only reads: `--help` or `--version` before `--`, `status`, `api schema|snapshot`, or a `list`, `get`, `read`, `status`, `explain` or `wait-output` subcommand. An unknown target (`--session`, `--remote`, an unresolvable expansion or a conditional socket assignment) is refused too. Socket identity checks catch existing hard-link aliases; direct `ln` attempts to alias the session socket are refused. Code posse cannot follow is refused when it mentions `herdr`, `herdr.sock`, `HERDR_SOCKET_PATH` or `HERDR_BIN_PATH`, unless its environment resolves Herdr to another socket and the code does not name the Worker's socket. Interpreter code is refused only when it can reach Herdr: it names `herdr.sock`, `HERDR_SOCKET_PATH`, `HERDR_BIN_PATH` or the Worker's socket, or it can start a process (for example `subprocess`, `os.system`, `child_process`, `system(...)`, `exec`, `spawn`, Perl, Ruby or PHP backquotes, or an awk pipe) and names `herdr` as a command word or executable path. An inline edit of source that imports the `herdr` package or quotes `herdr` as data is allowed. Python in interactive mode or with a startup override keeps the stricter mention rule because it can run code the command does not show. An unresolved or dynamically assembled socket target is refused as unknown, never treated as proof of isolation. Ordinary command data, such as an `rg` pattern or file path, does not trigger Herdr detection by itself. The only interpreter exceptions are narrowly matched, single-purpose Python inspections invoked with exactly `-c <literal-program>` and no extra arguments, redirected or piped stdin, or interpreter startup overrides (`PYTHONINSPECT`, `PYTHONSTARTUP`, `PYTHONPATH`, `PYTHONHOME` or `PYTHONUSERBASE`): `print(<literal>)`, `Path(<literal>).read_text()`, `importlib.metadata.version(<literal>)` and `sys.version` queries in a simple `print` expression. Other Python modes and interpreter programs follow the interpreter rule above. The mention rule covers (python, node, deno, bun, perl, ruby, php, lua, awk and others; inline code, script files, heredocs, stdin), socket tools (`socat`, `nc`, `ncat`, `curl`, `websocat`), non-literal program names and unparseable commands. A recognized posse executable other than the one running the guard (`posse*`, renamed Go builds identified by build metadata, `go run ./cmd/posse`) is refused when its `POSSE_HOME` is the Worker's home. The demonstrated shell scripts and Make recipes written by redirection and run in the same command are refused when the command visibly names Herdr. The guard also refuses a Worker's direct `git push`; use `posse publish` for the recorded Task branch. A refusal exits 2 with the reason on stderr, which Claude Code and Codex show the agent; the pi extension returns it as `block`.
- Herdr's own agent integrations talk to the socket directly and are unaffected.
- The boundary is in ADR 0007: the guard sees only supported agent shell-tool calls. It is not a sandbox for compiled code, computed or encoded generated code, socket paths computed at runtime, or foreign binaries without recognizable build metadata. The tested redirection-and-execution cases are blocked when they visibly name Herdr, but arbitrary generated code cannot be inspected before execution. Older builds can bypass schema protections when run outside the hook; durable isolation needs server and filesystem permissions.

## 14. Merge

The `full-pipeline` contract requires a publication barrier before every push, including legacy Merge publication/retry paths and target/CI repairs (25.1, 25.14). Every full-pipeline delivery lane implements this barrier: single-repository and per-Member, PR and local delivery (25.1). The existing Merge checks below remain necessary but do not retroactively validate an earlier push. The User decides entry to Deliver in a configured workflow; `autonomy.merge` or explicit merge approval separately controls the merge effect.

`posse merge <task>` for a `done` change Task:

| Mode | `posse merge` does | Merge step |
|---|---|---|
| `local` | require a clean Sandbox; record the branch tip as `gated_sha`; check fast-forward onto the Task's frozen target branch; no automated verification runs and the User is responsible for checking the change; Task → merging; Notice `merge_ready` | `posse merge <task> --execute` fast-forwards the frozen target branch to exactly `gated_sha`: `git merge --ff-only <gated_sha>` in the root checkout if it is on the target branch and clean, `git fetch . <gated_sha>:refs/heads/<target>` if the target branch is not checked out, else `merge_target_busy`. If the branch tip is no longer `gated_sha`, refuse with `branch_moved` (help: run `posse merge` again) |
| `pr` | verify the Worker-reported open PR and remote head; with `defaults.require_current_target`, fetch the frozen target and require its tip to be an ancestor of the PR head before recording `gated_sha`; verify target freshness again before accepting CI evidence; Task → merging and emit `pr_opened`. Legacy completed Tasks without a PR URL still push and open a PR at Merge. A stale branch queues a Worker instruction and does not acquire gated evidence. | `posse merge <task> --execute` uses the repository's forge CLI, pins the gated head SHA, and, with `defaults.require_current_target`, refreshes the frozen target under the repository sync lock and refuses with `pr_branch_behind` naming the missing target commit unless the target tip is an ancestor of the gated head |

- `posse publish [--repo <member>] [--refresh] "<summary>" [--verify "<command> -> <result>"]... [--proof "<markdown>"]... [--risk "<markdown>"]...` validates a clean, committed PR-mode Sandbox on its own Task branch. Under `none` and `quick`, it pushes only that ref without force and creates or refreshes the forge PR/MR using the Task's saved PR title, or the Brief title when no override is set. Under `full-pipeline`, publishing from the Task Sandbox records the submitted head in private candidate custody without pushing or opening a PR; publishing from the private candidate checkout promotes it only after Review, test, docs and lint results qualify. It covers single-repository and per-Member lanes with PR or local delivery; local delivery promotion fast-forwards only the Task branch and opens no PR. The policy is not production-ready. `posse retitle <task> "<conventional title>"` is Lead-only, validates conventional-commit form, and saves a Task-level title override; the Worker's next publish applies it to the PR/MR. A direct forge title edit is overwritten by publish unless the Lead records that title with `posse retitle`. Repeated `--verify`, `--proof` and `--risk` values are retained in order; verification values render as separate checked items, while proof and risk values are separated by blank lines. Every new body uses the shared seven-section template, in order: `Summary` from the supplied summary; `Issue Link` with `Closes #N` only for the canonical ticket and `Refs #N` for references; `Changes` from `git log <base>..HEAD`; `Verification`, rendering each supplied line as a checked `<command> -> <result>` item or `- [ ] Not run; reason: not supplied`; `Proof`, using supplied Markdown or `_No proof supplied._`; `Risk And Rollback`, using supplied Markdown or `Risk: not stated` plus `Rollback: revert this PR`; and a `Documentation` checklist that checks its documentation item when Task changes touch `docs/` or Markdown, reStructuredText, AsciiDoc or README files, and checks the agent-guidance item when an `AGENTS.md` or `CLAUDE.md` file changes. Posse wraps the template in start/end markers containing a per-Task/member cryptographically random token persisted with the PR/MR URL in SQLite and the Task snapshot. A refresh replaces only one complete span whose markers contain that exact stored token; duplicate or incomplete matching markers conflict without edits, and all other marker-like text remains human-authored content. The selected Task or Brief title is the PR/MR title; the forge request uses the Task's frozen target branch, defaulting to the Project/member default when none is configured or requested. On the `none` and `quick` path, before pushing, publish persists the origin's current Task ref under the Task and member, then associates it with the open request when the forge reports that head; this durable retry evidence is not a verified PR head. If an existing request reports that pre-push SHA or a previously verified Task head, Posse polls with exponential backoff for up to 30 seconds; another SHA fails with non-retryable `branch_moved`. If the forge still reports the prior SHA at timeout, publish returns retryable `pr_head_lag_timeout` before editing request metadata. An existing PR/MR is validated against its repository, source branch, target, state and pushed head before metadata changes. If the Task branch already has an open PR/MR in the Project targeting a different branch, publish refuses with `pr_target_mismatch` instead of opening a second request; retarget or close the existing request before retrying. An unmarked legacy Posse description is not changed unless `--refresh` is supplied; explicit refresh preserves the entire existing description byte-for-byte and appends a tokenized Posse section. If a PR/MR has a tokenized Posse section but its token is absent from SQLite, publish returns a retryable `pr_body_marker_missing` error without forge edits; `posse recover --rebuild` restores the token from the Task snapshot before retrying. If the snapshot also lacks the token, restore a POSSE_HOME backup rather than editing the PR/MR markers. An unstructured human description or ambiguous matching markers are reported as conflicts and left unchanged. Metadata updates are safe to retry after interruption. `.github/pull_request_template.md` presents the same structure for human-created PRs. Workspace issue references are emitted only in the PR/MR for their named member. `posse signal done --pr` repeats URL and head checks, refuses a current head with recorded failed required checks, and binds completion to the current Worker turn; the Lead verifies again before starting the watch. A workspace Worker adds `--repo <member>` to publish each changed PR member; `posse signal done` checks each recorded member PR without `--pr`. The Worker never merges. Forge CI verifies the published PR head; private candidate submission does not push. Every full-pipeline lane promotes only after native validation and the barrier in 25.1.
- - A non-fast-forwardable `local` Task refuses with `needs_rebase`; the check uses the frozen target branch.
- `--execute` requires `autonomy.merge = "auto"` or `--user-approved "<User's words>"`, stored in `approvals`. Otherwise `merge_approval_required`, checked before any state change or Notice. A PR/MR merge also requires the selected review evidence at `gated_sha` (D03) and the latest observation for that request to match `gated_sha`, have checks `SUCCESS`, a review other than `CHANGES_REQUESTED` or `REVIEW_REQUIRED`, and mergeability `MERGEABLE`; otherwise refuse with `checks_not_green` and wait for `merge_ready`. Target freshness is checked only when `defaults.require_current_target = true` (User-only, default `false`). When it is off, a green, `MERGEABLE` PR merges while behind its target, clean-but-behind PRs receive no instruction and no merge queue is used; a PR the forge reports `CONFLICTING` emits `pr_conflict`, and its done or merging Worker is queued an instruction to merge `origin/<target>`, resolve conflicts, republish and signal done again. When it is on, Posse checks target freshness before recording the merge head and again before accepting final CI evidence. During a PR watch it refreshes the frozen target before and after the forge observation; a target advance during CI marks that observation `STALE`, not green evidence, and obsoletes any pending `merge_ready` Decision. If the target tip is missing from the PR head, the Task enters its target's FIFO merge queue, keyed by Project, Member and frozen target and ordered by done Signal, and only the queue head's Worker receives an instruction to merge `origin/<target>` into the Task branch, resolve conflicts, republish through the Task's delivery mode and signal done again. This covers clean-but-behind and conflicting branches and does not require the Lead to notice or send a follow-up. Other queued Tasks stay `done` or `merging` with no Worker turn or CI rerun until promoted; `posse merge` on one refuses with `pr_branch_behind` naming its position and the head. The head keeps its place while its instruction is in flight. It is dequeued when its PR merges, when its fresh head fails required checks (re-entering at the back after a later done Signal or green checks), or when its Task leaves `done` and `merging` without an in-flight instruction; the next entry is then promoted. `posse`, `posse list` and `posse show` report `merge_queue` positions. The queue is recorded in [ADR 0031](adr/0031-serialize-target-updates-through-a-merge-queue.md). No-mistakes recovery uses `--skip=rebase` after the Worker has merged the target so a pushed branch is not rebased. Before merging, Posse refreshes the Task's frozen target under the repository sync lock and names the missing commit in `pr_branch_behind`; it never merges a gated head without the current target tip. When that instruction is queued or already delivered, `pr_branch_behind` says so, including on a later `--execute` that finds the Task reopened without a gated head; the Lead waits for the Worker's done Signal instead of sending a duplicate. A Task state change by another actor during Merge, such as a Worker starting a queued fix turn, returns retryable `task_state_changed` naming the public Task ID. The forge merge remains pinned to `gated_sha`. Local fast-forward merges claim the target Git ref and, when the Project root checkout is the target worktree, its canonical path; the claims remain until the merge effect is reconciled. These checks apply with User approval and `autonomy.merge = "auto"` alike. The current-target requirement is recorded in [ADR 0019](adr/0019-pr-merges-require-current-target.md); lease scope and recovery are recorded in [ADR 0021](adr/0021-canonical-resource-leases.md).
- Git refs are always passed fully qualified from the Task's recorded branch (`refs/heads/<branch>`); new Tasks use `refs/heads/posse/t<n>`. This prevents a tag of the same name from being merged.
- `merging → merged` is observed by reconcile: the local merge result, or the PR watch below.

**Project watch.** When a Project has an active Lead workspace, `posse up` starts one detached `posse watch --poll-only` process with the Project's `POSSE_HOME`. It has no Herdr pane, does not open a login shell, and uses a per-Project file lock plus a random token and PID recorded in SQLite to prevent duplicate watches. It retains the configured Herdr session, socket, binary/config and Git SSH settings while dropping Worker-pane context, intent hooks and Git worktree selectors. It reconciles PRs and tears down merged Tasks. A bounded foreground `posse watch --poll-only --timeout <ms>` run is a User wait, not a managed child. Supervision only adopts managed pollers with a complete private identity; it verifies the executable and reaps an unbound indefinite poll-only process running inside this Project as leaked compatibility state. When no extension or live Lead Watch owns Notice delivery, it may deliver Notices through the configured Lead path; it never acknowledges them. Process identity includes the executable file identity; a heartbeat is refreshed every five seconds. A live watch that fails to make heartbeat progress through the recovery grace raises one `pr_watch_failing` Notice for that stale episode before repair. A missing process is repaired without treating a reboot as an unhealthy heartbeat episode. Stale watches receive SIGTERM and must exit gracefully; supervision never SIGKILLs a watch during Project maintenance. Project maintenance commands, Herdr events, harness hooks and extensions supervise active Project watches. A Pi or OpenCode handoff ensures the independent Project observer is running before its receiver wait, but does not perform observer maintenance inline; adapters own receipt delivery and re-arming. `posse doctor` reports their health, and `posse watch --repair` repairs one without restarting the Lead or Workers. Supervision continues when `defaults.auto_recover=false` but never starts a watch for a Project marked down. Legacy labelled Watch tabs in the Project workspace are closed during `posse up` and recovery. A 0.14 label is matched only to its recorded pane; unrelated workspaces stay untouched, and an agent occupying a former Watch pane blocks the upgrade. Watch reconcile and watch failures retain the existing visible `pr_watch_failing` behavior; Watch logs and retries transient store contention on the next poll without a Notice. A foreground command that defers reconciliation because its bounded SQLite budget is exhausted continues from durable state and warns that output may be stale. [ADR 0025](adr/0025-hidden-supervised-project-watches.md) amends ADR 0001 and narrows ADR 0005's detached-Watch restriction.

**Watch repair.** From the Project folder, the User can run `posse watch --repair` to restore only its watch, including while `defaults.auto_recover=false`. It verifies the existing active Lead workspace and one matching process; it updates only watch runtime state and never calls `recoverProject`, changes config, restarts the Lead or starts Workers. Repeating the command is a no-op when the watch is healthy. `posse doctor` reports each active Project's watch PID, executable identity, heartbeat and log path.

**PR/MR watch.** Every Task with a `pr_url` is watched in every state until the forge reports it merged or closed, including `working`, `needs-decision`, `blocked`, `stalled`, `failed` and `lost`. A merged head is trusted when it remains on the Sandbox's Task branch or was recorded by `posse publish`, and a merged request must target the Task/member's frozen branch. With `defaults.require_current_target`, open requests are revalidated against that target before recording CI; a target advance during the forge query marks checks `STALE` and cannot emit `merge_ready`. A `merge_ready` Notice is emitted only while the Task is `done` or `merging`, once per Member head and completion transition. For a done or merging Task, Posse queues the Worker once per completion to merge the target and republish; workspace instructions name the affected Member. An invalid PR URL that points at an issue raises one `pr_closed` Decision to replace the URL or discard the Task. Other persistent PR failures produce a deduplicated `pr_watch_failing` Notice after three consecutive failures at the affected scope, name the reason and retry on the next tick. A failed observation never silently drops the Task. The forge is selected from the request's repository. Watch and doctor use a two-second forge-auth probe timeout; Watch timeouts are not cached, while foreground timeout results are negatively cached for five seconds. Host-level forge-discovery failures and missing GraphQL repository data are recorded once at Project scope; request-specific failures are recorded with the affected Task and Member. Watch polls each Member independently with a durable claim and at most one active forge query per Member. A stalled Member query or fetch does not delay healthy Members' next poll cycle. Watch runs checkout sync and merged-Task Teardown alongside PR polling; a newly merged Task triggers Teardown independently of the checkout join, and a phase failure does not suppress the others. GitHub and GitLab adapters read request state, merge commit, head SHA, mergeability, reviews or approvals, and required checks from each Member's forge. Reconcile polls when the Project's last poll is older than `defaults.pr_poll` (default `2m`); `posse watch` polls at that interval. Pollers atomically claim the Project and each workspace Member's poll in SQLite; duplicate pollers skip active claims, and abandoned claims expire. Each observed change is recorded in `pr_observations` and produces at most one Notice per change:

| Observed | Notice | Task effect |
|---|---|---|
| PR reported by the Worker (or created by legacy `posse merge`) | `pr_opened` | stays `merging` |
| required checks fail on the current head | `pr_checks_failed`, with failing check names and log URLs | stays `merging`; the Lead may `posse send` a fix (Task → `working`) |
| all required checks pass on a head containing the current target tip (when `defaults.require_current_target` is on), reviews allow merging, and Task is `done` or `merging` | `merge_ready` | state unchanged |
| review requests changes | `pr_changes_requested`, with the review summary | stays `merging` |
| `defaults.require_current_target` off: PR conflicts with its target | `pr_conflict`; no `merge_ready` | stays `done` or `merging`; Posse queues the Worker to merge `origin/<target>`, resolve conflicts, republish and report done again, without the merge queue |
| `defaults.require_current_target` on: target tip is missing from the PR head, whether mergeable or conflicting | no stale `merge_ready`; conflict still emits `pr_conflict` | stays `done` or `merging` and enters the target's merge queue; Posse queues the head's Worker to merge `origin/<target>`, resolve conflicts, republish and report done again; never rebase a pushed PR branch |
| merged (by posse, by the User on the forge, or by anyone) | `pr_merged`, plus `review_policy_violation` when the merged head lacks the selected evidence | any non-merged state → `merged`; `merged_ref` is the merge commit; the Worker is interrupted during Teardown |
| closed without merging | `pr_closed` | keeps its state and branch; raises a `pr_closed` Decision to reopen and relaunch or discard; polling stops for this PR |

**PR stewardship.** Every recorded PR/MR has one `deliveries` record per Task and member. The Lead is its operational steward; its authors are the Task's recorded launches (`task_launch_identities`), so stewardship and authorship stay separate. `posse publish` records a delivery with origin `publish`; a PR URL recorded before deliveries existed, or by another path, becomes a `legacy` delivery on migration or on its first steward command. The existing PR watch, its Notices and `posse merge` remain canonical; a delivery adds no second watch. The Lead (or the User) may perform only these forge operations without the Worker, each recorded in `delivery_operations` with actor, Lead pane, PR head, subject and outcome:

| Command | Effect | Guard |
|---|---|---|
| `posse pr inspect <task> [--repo <member>]` | none; prints the delivery, authors, current observation, failed checks with run/job ids and the latest operations | forces a PR poll; when the watch cannot confirm the state from the forge during the call, it refuses with retryable `forge_unavailable` naming the last observation instead of presenting cached state as current |
| `posse pr reply <task> --body <text>` | posts one PR/MR comment ending in a hidden `posse:steward-operation:<id>` marker | requires a current open observation; the same text is posted at most once per delivery (`pr_reply_duplicate`). A reply is not a review pass or a User answer |
| `posse pr refresh <task>` | sets the saved or Brief title and rewrites Posse's Validation block inside its tokenized span | requires a current open observation; other PR/MR text is unchanged; already-current metadata is recorded without an edit |
| `posse pr rerun <task> --run <id>` (GitHub) or `--job <id>` (GitLab) | reruns the failed jobs of an existing CI run (`gh run rerun --failed`, `glab ci retry`) | the id must be a failed check on the current observed head, the run must have completed on that head, and each run is rerun at most twice per head (`pr_rerun_limit`); it never starts a workflow, dispatches a new one or changes code |

A forge error after an effect was requested records the operation `uncertain` and returns retryable `forge_outcome_unknown`. A `pending` operation older than two minutes belongs to an interrupted command and is treated the same way. The next attempt of the same operation first observes the forge: a reply is found by its marker, a GitHub rerun by a later run attempt or a running status, a GitLab rerun by a newer job of the same name in the pipeline. An effect that took place is recorded `succeeded` and is not repeated; an absent one is recorded `failed` and may be attempted again within its limit. When the forge cannot be read, the command refuses without acting. Stewardship grants no merge, approval, branch, push, workflow or secret authority: merging still requires `posse merge` with its approval and evidence, and code changes still go through a Worker. The decision is recorded in [ADR 0032](adr/0032-the-lead-stewards-pr-deliveries.md).

A plain `posse send` attempts a PR refresh within the existing reconciliation budget. If refresh completes and reports a merged PR, `send` refuses with `pr_merged` and the Task Merges. If refresh times out or errors, send proceeds using the last persisted observation. `send --queue` and `send --interrupt` skip PR refresh; interruption is independent of forge latency and store maintenance. A merging Change Task accepts a follow-up `posse send <task> <message>` even before `pr_checks_failed`, `pr_changes_requested` or `pr_conflict`. When durable submission begins, the Task returns to `working`, clears `gated_sha`, and keeps its branch and PR; after the next done Signal, the Lead runs `posse merge` again. If a `merge --execute` intent is still running, `posse send` refuses with `intent_active` and help rather than interrupting the merge.

The forge is selected from the repository's `origin` host (`github.com`, `gitlab.com`, or a configured enterprise host); `defaults.forge` overrides it per Project, and `repositories.<repository>.forge` overrides it per member repository. The auth probe allows two seconds, so normal self-hosted forge latency does not count as a timeout. GitLab merge uses `glab mr merge --sha <gated_sha> --auto-merge=false` with squash or merge-commit. GitLab rejects `merge_method = "rebase"` before pushing or merging, since server-side rebase changes the pushed source branch; use squash or merge. A new commit pushed after a fix resets the check status to pending, so a later failure or pass on the new head produces a fresh Notice. `posse show <task>` includes a `pr{url,state,checks,review,mergeable,updated}` row, and home shows the PR state in the Task row. Project-level, per-Task and workspace Member PR-watch failures raise `pr_watch_failing` only after three consecutive failures at that scope; a successful poll resets the streak. Task streaks are keyed by Task and Member, so another Task's success does not reset them. An acknowledged persistent Task failure is reminded after 24 hours, then after 48 hours and at most every seven days; project- and Member-scoped Notices remain deduplicated until recovery. A retryable `pr_forge_probe_timeout` is not cached by Watch; it contributes to the applicable streak and is retried at the next PR poll.

**Keeping the Project checkout current.** The User never has to leave the Lead to `git pull`. After any Merge (a local merge, or `pr_merged` from the PR watch), and during reconcile when the last fetch of the Project is older than `defaults.pr_poll`, posse fetches only the frozen target branch into `refs/remotes/origin/<target>` with tags disabled, then brings the local default branch up by fast-forward only. Sync holds the canonical Project-root path plus the local and remote default-ref leases; an overlapping writer causes a visible skipped checkout instead of an unsafe Git effect. A failed fetch is not evidence that origin is ahead: it never raises `root_behind`. Failures are counted consecutively per repository; after three, one Project-level `root_fetch_failing` Notice coalesces the failing repositories. A successful fetch resets that repository's streak, updates the Notice to retain only still-failing repositories, and acknowledges it when none remain above the threshold.

- the root checkout is on the default branch with no tracked local changes: `git merge --ff-only refs/remotes/origin/<default>`. Untracked and ignored files do not block the fast-forward unless an incoming path overlaps them;
- when that root checkout is on the default branch, a tracked local change blocks the fast-forward even when it does not overlap incoming changes. An untracked or ignored path that an incoming change would overwrite also blocks it. In either case, posse leaves the checkout untouched and names the blocking paths in the `root_behind` Notice;
- the default branch is not checked out: `git fetch origin <default>:refs/heads/<default>` (no `+`, so it can only fast-forward);
- after a PR/MR merges into a non-default frozen target, the same safety checks fast-forward that target branch to `origin/<target>`; config changes after Task admission do not change its target;
- when a lower Task's PR/MR merges, an open upper PR/MR targeting the lower Task's branch is retargeted to the lower Task's frozen target. Posse verifies the forge's current target first, so an already-retargeted request is safe; only after verification does it update the upper Task/member target and record the change. Unexpected targets are left untouched and recorded as blocked.
- otherwise (another branch checked out, or local commits that are not on `origin`): posse changes nothing and raises one `root_behind` Notice per new upstream head, saying how many commits behind and why it could not update. `posse sync` retries the same rules once the User is ready.

posse never merges, rebases, stashes or resets in the Project root; the User's own work there is never touched.

Review findings (from a Review Task's Report): with `autonomy.review = "lead"` the Lead decides and reports its decisions to the User as a summary; with `ask` the Lead asks the User. This controls disposition only, not required evidence or merge authority.

Never allowed under any Autonomy: force-push, deleting a branch or worktree that has not Merged, touching secrets, acting outside the Brief.

## 15. Teardown

`posse teardown <task>`:

- For Sandbox Tasks, ordinary `posse teardown` releases only `merged` and `reported`; discard of unmerged `spawning`, `working`, `needs-decision`, `blocked`, `stalled`, `done`, `merging`, `failed`, `lost` or `reported` work requires `--discard --user-approved "<quote>"`. `merged` Tasks cannot be discarded through this command or a recovery Decision. An answered unrecoverable-Orphan Decision may discard only its unmerged Orphan during normal merged Teardown.
- A Lead can cancel working or needs-decision Tasks with `posse teardown <task> --discard --user-approved "<User's words>"`. Before approval or signals, bind the current Worker launch and its proved descendants to process-start identities and Linux pidfds. Interrupt with SIGINT, then terminate with SIGTERM and, if needed, SIGKILL. Never signal a replacement or newly observed process. Unverifiable identity or missing pidfd capability refuses and preserves the Sandbox. Persist bindings in the intent so crash recovery cannot retarget another instance.
- Before pane or Sandbox teardown, validate every recorded unmerged PR or Member MR against its forge. A preflight `MERGED` result refuses before approval is recorded; `CLOSED` is accepted; `OPEN` is closed through the forge and freshly read again. A later `MERGED` result also refuses before pane closure. Record the verified closure observation. Any lookup, close or verification failure keeps the Sandbox held and leaves panes open. A merged Task's merged PR is not a discard target when an unrecoverable-Orphan Decision disposes of separate unsaved work.
- Herdr 0.9.1 has no atomic pane-close precondition. Approved discard rechecks the server generation, pane topology, launch name, retained shell identity and shell-only foreground immediately before `pane.close`; a mismatch refuses and preserves the replacement. Stale lifecycle authority is cleared with its source and sequence only after rechecking the foreground. It never closes whole tabs or workspace groups. Normal Teardown still requires natural pane removal and refuses a surviving pane with `herdr_conditional_close_unavailable`. The check-to-signal and natural pane-removal races remain because Herdr cannot condition signaling or closing on a verified process instance. Process-presence scans are also non-atomic with Git reset: a process can attach to the Sandbox after the final scan and before reset. Posse has no host-level process/path fencing operation to eliminate that race. A stale linked workspace may also reappear after server restart; recovery refuses to reuse its Sandbox until the stale shell pane is inspected and removed. Eliminating these limitations requires Herdr conditional-close/process-generation APIs and host-level path fencing. Teardown never uses `worktree.remove`, which would delete the Sandbox.
- Deletes a merged local branch only when it is an ancestor of the Task's frozen target branch or its recorded PR head is merged and the branch tip still matches that head (including squash/rebase merges). If a PR branch advanced after merge, preserve that follow-up work. An approved discard removes the branch only at the SHA recorded with the approval.
- Releases the Sandbox (section 12). Before resetting a discarded Task's Sandbox, record its branch tip SHA in the `approvals` row, so the discarded commits stay recoverable by SHA until Git garbage-collects them.
- For normal Teardown, stops and verifies Task-owned processes. For approved discard, persist the User quote and instance bindings in the intent, close and verify recorded unmerged PRs, then stop the retained Worker. Capture its final branch tips after shutdown, including commits completed during interruption, before closing its verified panes. Refuse while residual Sandbox or scratch processes remain; keep the Sandbox held and make discard retryable. Preserve a Report and its attachments; for Research Tasks, write an immutable `report-manifest.json` and persist its exact digest before releasing the Sandbox. Capture each approved discard tip as a Git bundle under Task artifacts, delete Task scratch, then release its Sandbox. A PR lookup, close, verification, process, scratch, or discard-capture failure keeps the Sandbox held. Teardown removes a merged branch only when its merged head is confirmed or its exact `MERGED` PR observation matches; it preserves advanced branch tips. Bundles and Reports expire under `[retention] task_artifacts`.
- Is idempotent: every step tolerates having already happened (tab or pane gone, branch gone, Sandbox already idle, scratch already removed), so rerunning `posse teardown` after a crash finishes the job.
- Retry only retryable failures. Deterministic refusals (for example, a merged PR, invalid approval or changed Task/Worker identity) are non-retryable; correct the cause or obtain a fresh User Decision before trying again.

**Which panes are the Task's.** From one fresh snapshot, the Task's tabs are those holding a pane labeled with the Task's `pane_label`. A pane belongs to the Task when it carries that label, or it is an unlabeled pane in one of the Task's tabs **and** its cwd (symlinks resolved) is inside the Task's Sandbox. A linked Worker child is recognized by both its worktree checkout path and a labeled Task pane. A live agent in a candidate must be one of the Task's launches (`agentName`). Recorded pane, tab and workspace ids are never trusted alone: Herdr renumbers them when it restores a session and reuses workspace ids. Any other pane in the Task's tabs is a **foreign pane** (for example one the User split off to look around); panes in other tabs, including the Lead's and sibling Workers', are neither.

**Closing.** Before normal shutdown, record Task and foreign panes from a fresh snapshot. Verify Herdr ownership and retain process-start identities and Linux pidfds for exact processes reported by `pane.process_info` and their current descendants proved by live parent chains; recheck Herdr ownership after each process-info call. Normal Teardown may also signal only retained process instances proven to belong to the recorded Task cgroup or carry its unique inherited marker. A CWD scan can detect processes but cannot authorize them. Approved discard retains its stricter rule: it stops only the verified Worker instance and retained descendants, then refuses while residual Sandbox or scratch processes remain. Before signaling a retained shell, recheck its pane and foreground ownership and compare its executable image with the Task's recorded shell identity; if a foreign occupant or replacement image appears, refuse the signal and preserve the Task, branch and held Sandbox. This check cannot make signaling atomic: a replacement after recheck may still be affected as the shell exits and Herdr removes its pane. Process lists may gain or lose short-lived children: verify retained instances individually and tolerate an instance that has exited. Never signal a newly observed PID based only on its path, parent chain or process group. Without independent Task marker or cgroup proof, a process first seen during cleanup may be tracked only for natural-exit waiting when its parent chain reaches an exact retained process or it shares a process group led by or containing one. If it remains in the Sandbox after 300 ms, or another live PID appears, refuse before Sandbox release. Approved discard stops only its retained Worker instances, verifies the exact shell/pane immediately before closing it, then verifies no process remains in the held/releasing Sandbox or validated Task scratch; it never signals residual processes. If pane or process verification fails, keep the Task and Sandbox held and create a `teardown_incomplete` Notice. Before applying a `pr_closed` Decision, poll the forge again and proceed only if the PR remains `CLOSED` and the Task remains unmerged. Preserve Reports and attachments before removing scratch. Release the Sandbox only after verification. If process identity or pidfd capability cannot be proved, preserve the Sandbox; other platforms report exact process-instance signaling as unsupported. Herdr 0.9.1 accepts only target IDs for close, so approved discard uses a final identity check followed by individual `pane.close`; normal Teardown sends no close RPCs. The check-to-signal and natural pane-removal races remain until Herdr provides conditional-close/process-generation APIs. A stale linked workspace may reappear after server restart; recovery refuses to reuse its Sandbox until its shell pane is inspected and removed.

**Automatic Teardown.** A merged PR triggers automatic Teardown regardless of `auto_teardown`. Concurrent attempts do not raise a `teardown_incomplete` Notice for an active Teardown intent. A CLI reconciling while another process tears down a merged Task waits for the intent to finish, then reports `teardown_in_progress` if it still runs instead of presenting a half-torn-down Task as ready. Local `merge --execute` succeeds only when Teardown completes; it accepts a Task already in `torn-down` without repeating Teardown, and returns an error if a competing attempt ends while the Task remains `merged`. After interrupting the Worker, Posse snapshots commits beyond the merged head and tracked or non-ignored untracked edits as one commit on `<task-branch>-orphan`, then releases the Sandbox and raises an `orphan` Decision: open a new Task from that branch or discard it. Ignored artifacts are not snapshotted. Task-owned processes stop before the snapshot. Committed member work not merged into that Member's frozen target branch is also an Orphan, even if its worktree is clean. An unrecoverable Orphan snapshot or Report-attachment preservation failure raises an `orphan` Decision to repair the Sandbox or approve discarding its work. Applying the approved discard completes Teardown and obsoletes that Decision. A failed attempt raises one `teardown_incomplete` reason and is retried on each reconcile tick even if that Notice remains unacknowledged. The Task never returns to `working`. With `auto_teardown = "finished"` (default), posse tears down other Tasks by itself as soon as they are `merged`, or `reported` and the Lead has acked its `task_done` Notice (the Report lives on in the home). `merged` limits it to merged Tasks; `never` leaves every Teardown to the Lead. Unmerged Tasks are never torn down automatically: their work and Worker may still be present. The Lead may cancel a live Worker only with the User's explicit discard approval and verified exact-instance shutdown. `posse doctor` reports the bytes used under POSSE_HOME, including scratch, Pool, Project artifacts and state, the User's shared Go cache without deleting it, and the managed Worker cache.

**Orphan panes.** Reconcile also looks for panes labeled `posse:<project>:t<n>` whose Task is `torn-down` or unknown to the DB. Those of a `torn-down` Task pass the same ownership checks and are closed automatically. Unknown ones are never closed automatically: they raise one `orphan_pane` Notice, and `posse pool prune [--yes]` (a dry run without `--yes`) closes them after the ownership checks.

- Keeps `brief.md`, `launch.md`, `report.md` and all DB rows.

## 16. Lead lifecycle

`posse up [--<kind>] [--replace] [--name <n>] [--yes]` from a shell pane inside a registered Project, a Git repository, or a folder whose direct subfolders are repositories, inside Herdr (`HERDR_ENV=1`, else `not_in_herdr`); never from inside a Sandbox (`lead_only`):

Lead startup and automatic Lead recovery share a per-Project claim, so only one can start or replace a Lead at a time. A competing `posse up` fails with retryable `lead_starting` and identifies the holder, PID, claim time and two-minute expiry. `--replace` does not preempt recovery: the current start may already be changing the Lead pane or starting an agent, and there is no safe cancellation fence. Claims are released by their owner, transient SQLite contention during release is retried, and claims held by a dead process can be reclaimed immediately on procfs systems; otherwise stale claims become reclaimable after two minutes.

1. Registers the Project if needed: it detects the folder's shape (section 24), prints what it found and asks one `[Y/n]` in the terminal before saving. Without a terminal it refuses with `confirmation_required` (help: `posse up --yes`); `--yes` saves without asking; `n` refuses with `registration_declined`. The question comes after the kind, config and Herdr checks, so a refusal for another reason never asks first.
2. Chooses the kind: a `--<kind>` flag (`--claude`, `--codex`, `--pi`, one flag per kind Herdr recognizes; at most one), else the Project's `lead.kind`, else the global `lead.kind`, else the sole available kind (Herdr manifests first, configured kinds on PATH as fallback). With zero or several, return `lead_kind_required` listing available kinds. Output includes `kind` and `kind_source`; the automatic selection is not saved to config. The Profile is `lead.profiles.<kind>` when set, else the bare kind with no model or effort args.
3. If a live Lead exists: without `--replace`, refuse with `lead_running` (naming its kind and pane; help: `posse up --replace`). With `--replace`, stop its agent, keep its pane open as a shell, and clear its Lead label and metadata. The Lead holds no state, so only its conversation is lost; the output says so.
4. Make the calling pane the Lead pane and label it `posse:<project>:lead`. Clear that label from every other pane.
5. `agent.start` requires an available shell, but `posse up` is still running in the caller pane. One composer builds the complete Lead instructions for both `posse lead` and startup/restart: bundled default workflow guidance, User and Project preferences with source headers, then generated runtime obligations. The same composed text is printed and injected; preferences may change default workflow advice but cannot grant authority or override runtime obligations. Before writing or constructing system-prompt arguments, startup checks the complete injected instruction, including preferences and workspace guidance, against a 7,500-token budget measured as 4 bytes per token (30,000 bytes), not a model tokenizer. Oversized instructions fail with a stable error that names their byte size; Posse does not truncate them or start the agent. After printing its result, the CLI replaces itself with the configured agent process and its full arguments: the kind's `auto_approve_args` when `lead_auto_approve` is true, its `lead_args`, the Lead instructions through `system_prompt_args` when the kind has them, and the Lead Profile's arguments. `lead_auto_approve` defaults to true for claude, codex and OpenCode; set it false per kind to preserve approval prompts. Pi has no permission system. Restart uses this same launch path. A `pi-extension` kind also gets `--extension <home>/projects/<p>/lead-pi-extension.ts`, regenerated on every start. OpenCode gets a regenerated Lead-only plugin at `<home>/projects/<p>/lead-opencode-plugin.js`, injected through the process's `OPENCODE_CONFIG_CONTENT`; no User config file or global plugin is changed. Its `--prompt` opening turn creates a session for the plugin without typing into the pane (verified with OpenCode 1.18.32 TUI and isolated session storage). Herdr has no `agent.start` environment parameter, so a restarted Lead exports the inline config in its own shell before starting OpenCode. A `codex-queue` kind also gets an opening prompt as its start argument, because codex creates the session that `codex queue` needs only on its first turn. Herdr detects and tracks that process; a short detached Posse finalizer assigns the canonical name `posse-<project>-lead-<lead_launches>`, delivers the fallback `Run \`posse lead\` and follow it.` prompt for a kind without `system_prompt_args`, and redelivers eligible Notices.
6. Record the calling pane and its workspace as the Project Lead location.

A registered workspace Lead uses the saved Member list and does not rescan Member repositories during startup. Registered Project startup reconciles local Task and Sandbox state without fetching Git data, invoking forge CLIs or checking GitHub for an update. An interactive `posse up` from a versioned binary offers an update only from a fresh local cache; `posse update --check` performs the explicit release lookup. Interrupted PR-creation recovery stays durable until the Lead agent runs, then Watch retries it. Sandbox Teardown resets to the last fetched default-branch ref without fetching; acquisition refreshes origin before starting new work. Watch performs checkout and PR maintenance in the background. `posse project show` reports each Member's last checkout status, check time and reason, including an offline or otherwise unreachable Member. `posse project scan` is the explicit operation that refreshes workspace membership and saved repository facts.

There is at most one Lead per Project. Its pane title is `Lead: <project>` and its sidebar token is `posse_row=Lead:<project>`; `display_agent` shows the resolved harness before startup and the detected harness afterward, including recovery and reconciliation of existing sessions. Identity does not affect these fields. The Lead rebuilds its picture from `posse` after any restart.

**First outcome.** The Lead chooses the lightest workflow that can verify the outcome. A clear implementation request can go straight to one Change Brief; Research Tasks, specifications, tickets and separate review Tasks are optional, not prerequisites. Before writing a Brief, startup instructions and `posse lead` guide the Lead to discuss substantive intent, scope, trade-offs and acceptance only when an unresolved choice could change the work, following User and Project preferences. The Lead investigates repository facts before asking, bundles consequential questions, treats tentative ideas as suggestions rather than permission, and resolves mechanics silently. One-off permission never becomes standing Autonomy. Before the first Start, the Lead briefly states the deliverable, verification, permitted effects and return conditions. Identity, Profiles, Dispatch Rules, timing and Pool tuning remain optional and are not prerequisites to the first outcome; the Lead offers personalization at most once afterward, using conversation history, and follows the User's language when `identity.lead.language` is unset. An explicit language, including `en`, wins; the schema default remains unchanged.

**Readiness.** Effective config and read-only checks produce an ordered `readiness` list: `forge_auth` for missing or unverifiable PR forge authentication, informational `autonomy_ask`, then `machine_setup` for pending setup changes. Each gap has a stable code, consequence, key, `user_only`, fix and informational marker; startup context and status (including compact output) recompute the projection on every read and omit it when no gaps remain. Readiness never probes forge CLIs or resolves workspace remotes: it uses fresh cached auth results and reports unresolved forge/auth state as informational. Explicit `posse doctor` performs live forge checks, deduplicated by host and concurrent, with the shared two-second forge-probe timeout; results are cached for five seconds by effective config and CLI environment. Explicit `defaults.forge` and `repositories.<member>.forge` skip auto-detection. Doctor keeps its legacy checks, ordering, help and exit behavior and reports current authentication state. There is no first-run flag or new table. Readiness does not grant authority or hide decisions in lowkey mode.

**Stopping an agent.** Herdr has no call that stops an agent, so posse reads `pane.process_info` and, when the foreground process group is not the pane's shell, sends that group SIGTERM, waits up to 5 seconds for the shell to return to the foreground, then sends SIGKILL and waits 2 more seconds. If the agent is still running, the command fails with a retryable `agent_stop_failed`. `relaunch` uses this; the Lead paths (`up --replace`, the Lead restart in `recover`) stop the Lead with keys and its exit command so its pane stays a shell.

`posse project add [--name <n>]` registers the current repository or workspace folder the same way, without the question and without starting a Lead, so setup can configure it first. `posse project scan [<name>]` re-detects a workspace Project's members.

`posse project remove <name> [--yes]` unregisters a Project registered by mistake. It is a dry run without `--yes`. Only a Project that never had a Task or a Sandbox can be removed (`project_not_empty` otherwise), and not while its Lead is live (`lead_running`). It deletes the Project's rows and `~/.posse/projects/<name>/`, and never touches the repository.

`posse lead` prints the exact composed instruction text injected at Lead startup: bundled default workflow guidance, layered User and Project preferences, then runtime obligations generated from the current Project and harness. A clear implementation may go directly to one Change; Research Tasks, specifications, tickets and separate review Tasks are optional. Preferences may change workflow advice, but cannot grant authority, bypass evidence or override runtime obligations. The generated text scopes name, persona and form of address to User messages; `identity.lead.language` selects neutral prose for Briefs, `posse send` instructions, reviews, decisions, Reports, commit messages, Signal notes and summaries, and other evidence, with English as the default. User words are quoted verbatim only as intent, machine identifiers remain unchanged, and the Lead persona stays out of artifacts. Runtime obligations preserve the Lead delegation rule until its execution path changes, User-only Decisions and settings, Worker Signal completion, approval for Merge/discard, command mechanics, Notice handling, and safe recovery. `posse dispatch` generates a safe Task Name; `posse start --brief <file> [--name <short>] [--queue]` accepts it or creates one when omitted. At capacity, `--queue` durably admits a Task in `queued` without a Sandbox, pane or branch; inspect its wait reason with `posse show` and cancel it with `posse teardown`. `after: [t12:landed, t14:accepted]` adds typed local prerequisites, validated atomically and reported as queued wait reasons. Review readiness uses `review_of`. Ticketed Change Tasks query paginated native GitHub `blocked_by` relationships before starting; open blockers and incomplete or unavailable responses prevent dispatch with a visible wait reason. Ready queued Tasks are claimed and launched by caller-driven scheduler refill through existing CLI, plugin and Watch reconciliation; capacity is reserved atomically and the admitted plan is reused. Each launch runs in its own detached session (log: `projects/<name>/launch.log`), so interrupting the command that triggered refill does not interrupt the start. A start that still fails records its reason, shown by `posse list` and `posse show`; when no Worker received its Brief, Posse stops the pane's shell under Teardown's ownership checks, closes the pane and releases the Sandbox. `posse show <task> --full` renders frozen plan inputs as text. The name is display-only; the stored branch is `posse/t<seq>`. Preferences cannot enable unsupported Review or Git-delivery modes. The Notice rule matches the kind's `notice_delivery`; it includes the lowkey reporting contract and directs the Lead to use its harness delivery mechanism without polling. The command loop describes optional Brief fields `ticket:` and `refs:` for forge issue links: `ticket:` names the one issue a Change Task closes when its PR Merges, and `refs:` adds non-closing references. During compatibility, `issues: [<one issue>]` is accepted as the same ticket; multiple closing issues are rejected. Workspace issue numbers include the owning member name (section 13). It also explains that `posse send --queue` returns a queued result without running maintenance or steering mid-turn; `posse show` reports how long each queued instruction has waited.

`posse down`, run by the User in the Project folder, stops the Project without unregistering it. It refuses with `tasks_open` while a Task is running (`spawning` through `merging`) and with `user_only` from a Worker or a live Lead pane; a Lead pane whose agent has exited is a User shell. It records the Project down first, so the close events it causes do not recover it, then stops the Lead agent, closes the Lead tab (only the Lead pane when a tab holds foreign ones; the caller's own pane stays open, unlabeled) and stops and forgets the Project watch. Watch shutdown is graceful so it cannot interrupt Teardown; retry `posse down` if it is still finishing maintenance. A down Project is never restarted by the startup hook, plugin events or other commands; `posse up` clears it.

A moved repository makes its Project `missing`; `posse project move <name> <new-root>` fixes it, preserving the Project's stable UUID and refreshing its Task snapshots so database rebuilds remain valid.

## 17. Recovery

Work is never lost to a crash: commits live on the recorded Task branch, uncommitted work in the Sandbox, and the Brief in the home. This section makes sure a crash is also **noticed** and **resumable with one command**.

**Relaunch.** `posse relaunch <task> [--profile <name>]` restarts a Worker in the same Sandbox and branch. `--profile` must name a configured Profile, as with `posse start`. A done Task cannot be relaunched; refusal for a done Change Task points to `posse send <task> <message>` for a follow-up:

1. Allowed from `working`, `stalled`, `lost` and `failed` (a `failed` Task only if its Sandbox is still held). Writes a `relaunch` intent.
2. Finds the Task's pane (by id, then label); if none, reopens the Sandbox in a new workspace exactly as `posse start` does and labels the new pane.
3. For admitted Tasks, uses frozen Profile, kind, model/effort, arguments, resume templates and selected skill/instruction inputs without rereading launch configuration. Explicit `--profile`, even with the same name, resolves current launch settings and appends a plan revision before execution effects. The revision links its predecessor's digest and atomically clears Task/member merge-head evidence; prior Signals retain their revision/digest as historical evidence. A failed or interrupted attempt keeps that revision for recovery. Legacy Tasks still resolve their stored Profile from current config. A recorded session resumes only when its owner kind matches the selected harness. If a legacy Task has no recorded owner, its stored (or frozen) Profile kind supplies it; another or unknown owner starts fresh. A kind change runs the selected kind's `prepare` step.
4. Stops any live agent in the pane (see Stopping an agent in section 16), increments `launches`, and starts the agent with full Profile arguments. Each Launch Identity Record binds the attempted launch to its admitted revision (zero for legacy), including failed attempts. For legacy Tasks, a Profile change is recorded only after readiness; admitted Tasks already recorded it with the revision. Missing `brief.md` or `launch.md` files are restored from admitted inputs, not mutable source files.
5. Clears stale Git state in the Sandbox: removes `index.lock` only when no git process runs in the Sandbox, and reports an in-progress merge, rebase or cherry-pick instead of touching it.
6. Prompts one line pointing at a generated `relaunch.md`: re-read `launch.md`; inspect `git status` and `git log`; continue the Task; report with `posse signal`. It includes delivered Lead messages sent after the Brief in order, bounded to the most recent 32 messages and 1,200 bytes per message; later messages supersede earlier ones. Then moves the Task to `working`.

**After a Herdr or machine restart.** Herdr's own resume reruns agents with only their session argument, so Workers lose their auto-approve flags and the Lead loses its instructions. The plugin therefore declares a `[[startup]]` hook that runs `posse recover --all` (by the absolute path recorded at `posse setup`). For every Project it reconciles, relaunches each live Worker through the relaunch path above (with full arguments and `resume_args`), restarts the Lead in its recorded pane (or a new tab if that pane is gone), and delivers one digest Notice to the Lead listing what was recovered. `posse recover [--all]` can also be run by hand. If the startup hook does not run, the next launch-capable Project command (such as `list`) or plugin event detects the changed generation and runs the same recovery inline; concurrent attempts use the recovery claim so they do not relaunch twice. If the previous generation was never recorded, `recover --all` still checks the Watch process and replaces a restored shell-only tab.

**Bounded Worker recovery.** Each Worker has a persistent retry episode. `defaults.recovery_attempts` limits automatic relaunch attempts (default 3); the budget is charged before launch, including attempts interrupted by a crash. Failed attempts wait `defaults.recovery_backoff` (default 5 seconds), doubling up to one minute. Plugin events and launch-capable commands retry only after that delay. `posse up` still starts the Lead while an automatic Worker retry waits for backoff, then settles any interrupted explicit launch intent. A pending or exhausted episode keeps its budget across Herdr generation changes. A completed recovery is trusted only while its Worker pane remains live; a group close can reuse the same recovery generation, so a missing Worker is retried instead of being treated as recovered. Successful Workers are not relaunched again while another Worker retries. Exhaustion raises one `recovery_failed` Notice with the error and an explicit `posse relaunch <task>` escape hatch; acknowledgement does not re-arm it. Successful explicit relaunch resets the episode. `posse show` exposes its status, attempt count, next retry and last error. The Project generation remains pending while Workers retry, then advances even if a Worker exhausted its budget.

**Held recovery.** A Project that is down (section 16) or has `defaults.auto_recover = false` is held: `recover --all` skips it and lists it under `held_projects`, and plugin events and other commands leave its recorded panes untouched instead of recovering it or marking its Workers lost. The User may run `posse watch --repair` in a non-down held Project to restore only its poll-only Watch; it does not release the recovery hold. The next `posse up` in its folder recovers it. When no Lead workspace is left, `posse up` first makes the caller's workspace the Lead workspace, so recovered Workers open beside the new Lead.

**Interrupted commands.** `start`, `merge --execute`, `teardown` and `relaunch` record their progress in `intents` before each step with a side effect. Reconcile finishes or undoes an abandoned intent (older than its command's timeout, with no live process holding it): a `start` without a pane fails the Task and releases its Sandbox; a `merge --execute` whose frozen target branch already contains `gated_sha` moves the Task to `merged`; a `teardown` is simply rerun. Local Merge leases are reconciled only after recovery re-reads the target ref. The intent row is deleted when the command completes, and cannot finish while its resource leases remain unresolved. The passive Project Watch has a narrower boundary: it recovers only interrupted `merge --open-pr` intents after the Lead starts. It leaves `start`, `merge --execute`, workspace merge, `teardown` and `relaunch` to the next normal Project command, so a two-second poll does not take ownership of command-boundary side effects.

**While Herdr is down.** Read-only commands (`posse`, `list`, `show`, `pool`, `config show`) and `posse signal` work from the DB and disk alone and say that Herdr is unavailable; commands that need Herdr fail with a retryable `herdr_unavailable`.

**Losing the database.** Every Task state change writes `~/.posse/projects/<p>/tasks/t<n>/task.toml` atomically (temp file, fsync, rename) with its type, state, branch, Sandbox, Profile, `gated_sha`, pane label, current Worker turn token, Launch Identity Records and admitted plan revision history. Rebuild preserves selected bytes and frozen settings, verifies revision/digest continuity, and leaves legacy Tasks without plans. `~/.posse/projects/<p>/project.toml` records the Project, Sandboxes, resource leases, actionable Decisions and Notices, a bounded tail of historical Decisions and Notices, and the Decision Notice cursor. Task state, Project state, resource lease changes, Decision creation and answers, Notice changes and cursor advancement refresh the snapshots; acknowledged or obsolete history outside the bounded tail is not required for recovery and is omitted from the recovery snapshot. `posse recover --rebuild` (User-only) restores Projects, Tasks, Sandboxes, Decisions, Notices and cursors from the snapshots, along with orphaned Task branches such as `posse/t<n>` and Sandbox directories. It preserves Project stop state and Lead launch counts, matches Projects by their stable UUID (with a legacy name/creation-time fallback), and refuses identity conflicts instead of reassigning Tasks. Project moves preserve the UUID and refresh Task snapshots. If the database file is missing, orphaned WAL/SHM sidecars are preserved under timestamped `.orphaned-*` names before creating a replacement database. For a legacy Workspace without `project.toml`, it uses Members from the newest Task snapshot. Missing or incomplete launch records remain unknown; rebuild never derives them from current config. `posse` backs up the DB once a day with `VACUUM INTO ~/.posse/backup/posse-<date>.db`, keeping 7.

**Durability of files and deliveries.** `brief.md`, `launch.md`, `relaunch.md` and `report.md` are written atomically. A Research's `report-manifest.json` hashes the exact Report and saved attachment bytes and is persisted with the Task digest, Report reviews and any User acceptance in `task.toml` for rebuild. Legacy `posse watch` prints its digest before marking Notices delivered. Receipt-backed handoffs persist the exact batch and owner before printing, and mark it delivered only after the adapter reports acceptance. `watch --handoff` is receiver-only: it performs no Project reconciliation, forge polling, checkout, Teardown or executor recovery; adapters own waiting and re-arming while the Project observer runs independently. A crash after printing leaves the batch recoverable under the same stable ID. Ambiguous outcomes remain held and raise `notice_delivery_uncertain`; Posse makes no exactly-once claim. Receipt state and related Notices are snapshotted under each Project for rebuild.

## 18. Setup, skills and hooks

Once per machine, `install.sh` installs the `posse` binary and runs `posse setup` with the User's go-ahead (`--yes` applies it without asking, no TTY keeps the safe default of not applying, `--no-setup` skips it). `posse setup` needs neither a Herdr pane nor a running Herdr server: it talks to Herdr only through the `herdr` CLI. It is idempotent, prints its plan and what it changed, and records its managed installations in `~/.posse/setup.json`. Posse does not modify the User's Herdr sidebar configuration:

1. Checks prerequisites: `git`, `herdr`; optional `gh`; lists available agent kinds (the kinds `herdr integration status` knows).
2. Installs the Herdr integrations for the kinds it finds (`herdr integration install <kind>`), which Herdr needs to resume their sessions.
3. Links the `posse-herdr` plugin into the User's Herdr (`herdr plugin link`; a running server picks it up immediately).
4. Creates an empty `~/.posse/config.toml` when missing; schema defaults apply without persisting detected kinds, Profiles or Identity preferences. Existing config is preserved.
5. Installs no global skills by default. `posse setup --global-skills` opts into installing them under `~/.agents/skills` and linking them into `~/.claude/skills/`. Existing unchanged Posse-owned copies are detected by their recorded hashes; `posse setup` and `posse doctor` offer `posse setup --remove-global-skills`, which removes only unchanged owned files after the explicit command. Modified and foreign files are preserved.
6. Merges a SessionStart hook running `posse _context` and a PreToolUse hook running `posse _guard` into `~/.claude/settings.json` and `~/.codex/hooks.json`, keeping every existing hook and the file's formatting, written atomically.
7. When pi's agent directory (`${PI_CODING_AGENT_DIR:-~/.pi/agent}`) exists, installs `extensions/posse-worker-guard.ts`, which runs `posse _guard` before every bash tool call.

The Claude Lead plugin is bundled in the binary and written under the Project's Posse home on Lead launch, not installed in the User's Claude settings or loaded for Workers. Its zero-height drawing, restored-row classification, redraw and animation packing are adapted from [firstmate-calm](https://github.com/kunchenguid/firstmate) (MIT, copyright 2026 Kun Chen); the plugin bundles `FIRSTMATE-LICENSE`. Posse's record-backed Notice recognition and Project preference handling are independent. Unit coverage runs through `claude plugin test internal/app/claude_lowkey`; the credentialed live TUI regression is `POSSE_CLAUDE_LOWKEY_LIVE_E2E=1 scripts/claude-lowkey-live-e2e.sh`. It uses an API key or a copied OAuth login in an isolated Claude config, and tests the collapsed `Ran 1 shell command` row on Claude Code 2.1.283.

`posse setup --check --exit-code` exits 3 when required setup would change the machine and 0 when nothing is pending, which is how `install.sh` decides whether to ask. Optional global skills are not pending setup. `--human` only changes the display: a checklist for people instead of TOON (`+` pending, `✓` done, `-` unchanged, `!` manual, `✗` blocked), which `install.sh` shows. `posse setup --uninstall` removes exactly what `setup.json` lists and never touches `~/.posse` data. `posse doctor` reports Posse-owned global skill copies that can be removed, stale optional skills or hooks, a failing plugin hook (from Herdr's plugin log), missing integrations, group-close risks from other repository primaries and unverified Claude Code function-hook versions.

**`posse _context`** prints role context only when the pane is a posse Lead or Worker (which command to run next: `posse lead` or `posse brief`, and the Task id); anywhere else it prints nothing. It runs in under 20 ms. The hook fires on session start, resume and compaction, so an agent never loses its role.

**Skills** are thin: the CLI owns every instruction that must be exact, and the skills point to it.

- `posse` (agent-triggered): what posse is, how to tell the role from the pane (`posse _context`), and where to go next (`posse lead`, `posse brief`, `posse up`, `posse --help`).
- `posse-setup` (User-invoked `/posse-setup`): an optional full tour, beginning with the faster path of `posse up` and a first request. It interviews at three scopes: machine (verifies `posse setup --check` and applies pending changes), global config, then per Project (`posse project add`, `posse config set --project`), and ends with `posse doctor`. It reads `posse config schema`. For User-only keys, outside a Lead pane it gives the User the exact `! posse config set|unset ...` command; inside the Lead conversation it writes only after explicit consent with `--user-approved "<User's words>"`. Workers cannot write config.
- `posse-down` (User-invoked `/posse-down`) guides safe shutdown of a Project Lead and Watch; `posse-update` (User-invoked `/posse-update`) guides update and Lead restart. Shutdown and update installation are User-only; the read-only `posse update --check` may run from a Lead.

Skills and the hook are bundled inside the binary and are versioned with it. Every Claude, Codex and Pi Lead and Worker receives frozen Posse skill content at launch without global or Project-folder writes: Claude gets a process-local plugin directory through `--plugin-dir`, Pi gets exact skill file paths through `--skill`, and Codex receives exact frozen skill paths in `developer_instructions`. For Codex Workers, Posse merges that guidance with existing instructions from `CODEX_HOME/config.toml` and Profile `-c` arguments. The snapshot lives under `POSSE_HOME/projects/<project>/launch-skills/<content-hash>`; later changes to embedded assets create a different snapshot rather than modifying earlier files.

## 19. Updates and releases

**Releases.** Releases are manual: the User chooses whether and when to publish a version. After the intended changes merge on `main`, publish a `vX.Y.Z` tag on a reviewed commit with passing CI. Before 1.0, `fix:` changes imply a patch bump and `feat:` changes imply a minor bump. Pushing a version tag starts `.github/workflows/release.yml`, which runs GoReleaser and publishes Linux and macOS archives for amd64 and arm64 plus `checksums.txt`. Ordinary pushes and merges to `main` run CI only; they do not create tags or release PRs. Branch protection on `main` must require pull-request reviews and the checks `lint`, `test`, `e2e`, `installer`, and `build`, and must prohibit force-push and deletion. Do not apply branch protection from posse.

**`posse update [--check] [--version vX.Y.Z] [--force] [--stop-watches]`**:

Installing requires a User terminal outside Herdr or a live Herdr shell pane with no agent and no Lead or Worker binding. Posse verifies the caller before downloading and installing; an unknown pane or unavailable Herdr state blocks installation.

1. Finds the latest (or requested) release on GitHub; `--check` prints the current and latest version with the changelog summary and stops.
2. Downloads the archive and `checksums.txt` and verifies the SHA-256.
3. Backs up the database with `VACUUM INTO ~/.posse/backup/posse-pre-<version>.db`.
4. Replaces the binary atomically (temp file, then rename). Running `posse` processes keep the old binary until they exit.
5. Runs the new `posse setup` for hooks and integrations, but does not refresh optional global skill copies. If global skills were installed, the User runs `posse setup --global-skills` to refresh those copies.
6. Database migrations run forward only, on the new binary's first command, and the updater's post-install `posse setup` applies them. Every applied migration's SHA-256 is kept in `posse_migration_checksums`. Opening a database refuses `schema_unknown` when it has migrations the build does not know (an older build after an upgrade, or a branch build), and `schema_diverged` when a known migration was applied with different contents. Pending migrations on an existing database are applied only by the installed posse (the `binary` in `setup.json`), and never by a Worker for its own home (`migration_refused`). `POSSE_FORCE_MIGRATION=1` overrides every check but the Worker rule, for the User.
7. Mark migrations that cannot run with live Tasks with `-- posse: requires-no-live-tasks` in the SQL migration. The downloaded binary preflights those migrations before replacement; `posse update` refuses until no Task is live, or until `--force`, saying why. The migration gate enforces the same rule on first open.

`posse update` lets running Project watches and Lead watchers continue by atomically replacing the installed binary and requesting each process to re-exec it. The Watch runtime checks every five seconds whether its spawned executable has changed file identity; it updates its persisted identity and re-execs from that same path with its continuing wait arguments and environment, excluding one-shot acknowledgement and requeue options. A legacy 0.14 `lookout --poll-only` process first migrates to the installed `watch --poll-only` binary. Notice delivery is checked before a Lead Watch re-execs. A legacy Claude Stop hook reports `reason=update` through its async rewake path instead of re-executing after consuming its stdin. `--check` reports live processes without stopping them. `--stop-watches` remains an explicit force-stop: it sends SIGTERM, waits five seconds, then sends SIGKILL to remaining processes. The next Project command repairs a force-stopped watch; a Claude Lead's background Watch continues its wait across update, and the Pi/OpenCode Lead extension restarts its watcher automatically. A Lead-side watch stopped by an update returns `state=stopped` and `reason=update` with restart guidance. Discovery uses `/proc` on Linux and `ps` plus the process's loaded executable on macOS. It verifies the Go build's main package is `github.com/thanhbinh1905/posse/cmd/posse` and rechecks the executable's file identity before signaling, so renamed Posse binaries remain supported while other main packages from the Posse module and unrelated commands are ignored. For the 0.14 vocabulary upgrade, the User must invoke the installed old binary with `posse update --stop-lookouts`, let its post-install `posse setup` complete, refresh global copies with `posse setup --global-skills` if previously installed, and restart every running Lead with `posse up --replace` from a User shell in that Project. Old Pi/OpenCode adapters remain in memory until restart; their exact JSON `lookout --handoff` and `lookout --receipt` protocol remains accepted through a hidden, caller-guarded compatibility path so pending Notices and receipts are not lost. This is not a User alias; other old-name invocations, including `--help`, remain rejected.

**Update notice.** Automatic commands never perform a release lookup: `posse` and `posse doctor` use only a fresh local cache, and a successful unversioned `posse update --check` refreshes it. Cached releases drive `update{current,latest}`, the `help[]` entry and one `update_available` Notice per new version; an interactive `posse up` from a versioned binary also offers the cached release before registering a Project or starting a Lead, defaulting to No. Explicit consent verifies and installs it, then re-executes `up` with the original arguments and environment. `--yes` does not consent to updating; an empty or stale cache, non-interactive and declined offers continue without updating. Lead and Worker turns cannot install an update; a separate User shell pane can.

## 20. CLI

Commands print TOON on stdout when piped (JSON with `--json`), use lowercase snake_case keys and ISO 8601 local timestamps, keep lists compact with `--full` for more, print explicit empty states, and end with `help[]` next steps. On a terminal, `doctor` and `update` use concise human output; `doctor --verbose` expands successful check details. `--format human|toon|json` overrides terminal detection, and `--json` remains an alias for `--format json`. Human details wrap to the terminal width, or `COLUMNS` when set; `NO_COLOR` is honored. Other commands retain their existing renderer. A Task's canonical `id` is `t<n>`, with its display-only Task Name in `name`; commands accept either, and ambiguous names return `task_ambiguous` with candidate IDs in help. The AXI layer (command dispatch, help, structured errors, TOON encoding, session-start hook installation) is an internal package; its TOON encoder is tested against the official conformance fixtures in `toon-format/spec` (`tests/fixtures`).

`posse send` rules: deliver to a focused or unfocused `idle`/`done` Worker now; to a focused or unfocused `working` Worker, submit now only if `kinds.<kind>.steer` is true. For Pi, an `unknown` Herdr status with a standalone `Auto-compacting...` line on the current visible pane is treated as a busy turn. Posse may attempt steering, but any Herdr error after submission begins leaves the message held as uncertain. Historical or quoted mentions do not qualify. `--queue` waits for idle even on a steer-capable kind. Both send-time and background delivery may pass earlier explicit `--queue` messages to steer, while delivery remains FIFO among messages eligible for the current turn. Unknown kinds default to false. Automatic delivery continues to wait while focused. Explicit sends bypass layout focus but not blocked status or unknown live TUI screens; just before prompting, `agent.explain` gates dialogs (which can preserve the prior `done` status). For native reporters that skip screen detection, posse checks the live pane for menu key hints before submission. The send result reason describes the message it just sent, not an older queue head. Message claims refresh while `agent.prompt` is active. `posse send <task> --interrupt <msg>` reserves queued messages, refreshes that reservation while the command is active, sends the kind's abort keys, verifies the turn stopped, delivers the new message, then restores the older queued messages in their original order. It refuses while another message is actively claimed or submitting. Expired uncertain submissions remain held with their Notice, are never replayed, and do not block fresh delivery indefinitely. Once submission begins, any Herdr error, including `agent_not_ready`, leaves the message held as uncertain because the error does not prove the Worker did not receive it; Posse never retries or withdraws that submission automatically. `posse unsend <message-id>` atomically changes only `queued` messages to `withdrawn` without running background delivery during preparation; it refuses claimed, submitting, delivered, already withdrawn and undeliverable messages. `posse show <task>` retains withdrawn message IDs and text for inspection.

A done or merging Change Task accepts a Lead follow-up `posse send <task> <message>` without a failure Notice; delivery returns it to `working` and clears `gated_sha`. A merging Change Task also accepts the message before `pr_checks_failed`, `pr_changes_requested` or `pr_conflict`. After the next done Signal, run `posse merge` again. A running `merge --execute` intent blocks that send with `intent_active`. Sends to `reported`, `merged`, `torn-down`, `failed`, `lost` and `done` non-Change Tasks are refused with the state and a next step. Queue insertion is conditional on the Task still accepting instructions. Queued messages are retried on status or focus changes and reconciliation; when a Task enters `reported`, `failed`, `lost`, `merged` or `torn-down`, queued and claimed messages become terminal `undeliverable` rows and one Notice names each message ID and a follow-up. `posse show <task>` lists queued, claimed, undeliverable and withdrawn messages with their instruction text. Undeliverable and withdrawn rows are marked `history: true` and `blocks_sends: false`; these are not pending deliveries and do not block new sends when the Task accepts instructions. Ambiguous `submitting` messages are not retried and instead raise a Notice after claim expiry; their rows and evidence remain held while fresh messages can proceed. Blocked Workers create a `worker_blocked` Notice and the command points the Lead to `posse peek` and `posse keys`. Every message is stored with its wait-for-idle policy (including across restarts); the response reports `delivered` or `queued` with a reason. Queued messages already in the database before the migration keep wait-for-idle semantics.

`posse interrupt` and `send --interrupt` use `kinds.<kind>.interrupt_keys` for a focused or unfocused busy turn; blocked dialogs are never sent abort keys. Pi auto-compaction is considered busy only when the pane shows its visible `Auto-compacting` indicator. Both commands poll for up to 3 seconds and report interruption only after the busy state ends or the pane disappears. They return `interrupt_unverified` if the sequence was sent but Posse cannot verify the turn stopped. Built-in defaults use `ctrl+c` for Claude Code and `esc` for Codex, Pi and OpenCode; custom kinds must configure their verified key sequence.

## 21. Invariants

Each has an automated test.

1. Work that has not Merged is never deleted without a recorded User approval.
2. Only a Worker Signal moves a Task to `done`; Herdr idle never does.
3. A Task is marked `lost` only when its pane is gone by id and by label, or its agent has been absent for 2 minutes with no resumable session.
4. Automatic input is withheld from focused panes. Explicit Lead commands may type into a focused Worker pane after the blocked-agent and unknown-UI checks.
5. PR merging needs `autonomy.merge = "auto"` or a recorded User approval, plus a latest observation of the gated head with `checks=SUCCESS`, an allowing review and `mergeable=MERGEABLE`.
6. Workers push only through `posse publish` on their own PR-mode Change Task; they cannot force-push, delete branches, change the default branch, or merge.
7. Every state change has a `transitions` row with its source.
8. A Brief cannot loosen Merge Mode or Autonomy.
9. At most one live Lead per Project.
10. A missed Herdr event changes nothing that the next reconcile cannot restore.
11. `--execute` merges exactly the commit recorded as `gated_sha`.
12. A Sandbox is held by at most one Task, and a released Sandbox has a clean worktree and no orphan processes.
13. A Worker cannot run Lead-only commands, from its pane or after leaving it, and cannot run any state-changing command against its own posse home.
14. Identity never reaches an inter-agent artifact: changing every `[identity.*]` value leaves `launch.md`, the Worker protocol, agent names, pane labels, Notices and CLI output unchanged.
15. Every interrupted Task (dead agent, idle agent without a Signal, Herdr or machine restart) produces a Notice and resumes with one command (`posse relaunch`, or `posse recover` after a restart), in the same Sandbox and branch.
16. A multi-step command killed at any step is finished or undone by the next reconcile or by rerunning it.
17. A Task number and its branch are never reused, even after the database is lost.
18. Teardown closes every pane of the Task and no other pane, and verifies both before the Sandbox is reused.
19. Posse Teardown closes only the verified Worker tab, preserving the Lead, siblings and foreign panes; existing linked-child Workers close only their verified child workspace without `close_group`. Closing the Lead workspace can close its Worker tabs; plugin events and reconcile recover saved sessions and raise a Notice (ADR 0013).
20. In a Worker, the guard refuses the demonstrated shell-tool mutations of its Herdr session: direct calls, conditional socket assignments, hard-link aliases, `-- --help` operands, and visible generated shell and Make recipes, while allowing isolated server experiments. The boundary is in ADR 0007.
21. A Worker's descendants are Workers too: removing environment variables or changing directory never lets a Worker change its posse home.
22. This version of posse migrates an existing database only from the installed binary, and refuses a schema it does not know unless the User forces it. Older binaries lack these checks.
23. Posse-managed writers cannot hold equal, ancestor or descendant path scopes at once; conflicting Git common-dir/ref scopes serialize, independent refs do not, and a crash never expires a lease without custody reconciliation.
24. A loop-enabled Change Task never has more verdict-recorded Review Rounds than its frozen `max_rounds` (at most 3), no round creates a finding whose fingerprint is already in its Finding Ledger, and automatic CI fix instructions never exceed their frozen budget.
25. Posse accepts a native research result only from the bound child of a registered read-only attempt; a write-capable, untracked, cancelled or unverified child contributes nothing, and cancellation signals only the recorded process instances.
26. A steward forge operation whose outcome is unknown is observed on the forge before the same operation runs again, so an ambiguous reply or CI rerun is never duplicated; PR stewardship never satisfies merge approval or evidence.

## 23. Open risks

- **Timers need a caller**: stall and idle rules run on `posse` calls, plugin events and inside `posse watch`. A codex or `prompt` Lead that is idle, with silent Workers that emit no Herdr events, gets no Notice until the next call. Revisit with an optional timer if it bites.
- **Focus as the typing guard**: it assumes a User cannot type into an unfocused pane. Herdr's `focused` is layout focus, not client attachment; multi-client setups may break the assumption.
- **The Worker guard is not a sandbox**: it sees supported agent shell-tool commands, not every program's effects. `git rebase -x` and `git submodule foreach` can run arbitrary commands that the guard does not inspect. Generated or compiled code and agents without intact hooks can bypass it. Full Herdr enforcement needs server-side per-pane API permissions.
- **Herdr API churn**: protocol moved from 16 to 22 in months. The adapter is the only place to change; `posse doctor` reports incompatibility.
- **Plugin command limit**: Herdr allows 32 plugin commands in flight; `_ingest` must stay fast (target under 200 ms).

## 24. Workspace Projects

A workspace Project is a folder that is not inside a Git repository and holds several repositories of one stack, recorded in [ADR 0008](adr/0008-workspace-projects-span-member-repositories.md), with Task scope defined by [ADR 0020](adr/0020-selected-workspace-member-scope.md). Its members are the direct subfolders that are the top level of their own repository; hidden folders and linked worktrees (such as those under `.worktrees/`) are skipped. The Lead runs at the workspace root and sees every member.

**Registration.** `posse up` shows the detection before it asks:

```text
detected:
  project: sample-stack
  kind: workspace
  root: /home/user/projects/sample-stack
repos[3]{name,default_branch,remote,merge_mode}:
  backend,main,git.example.com,pr
  worker,main,git.example.com,pr
  e2e-tool,main,none,local
Register /home/user/projects/sample-stack as a workspace Project? [Y/n]
```

Inside one member of an unregistered workspace, `posse up` registers that repository alone and its detection carries a `hint` to run `posse up` in the parent folder instead. Commands resolve their Project from any folder: a repo Project by its Git top level, else the nearest registered workspace that contains the folder, else the Task whose Sandbox contains it. A member name is its folder name made safe (`[a-z0-9_-]`, 32 characters); two folders that map to one name refuse with `repo_name_conflict`.

**Members.** Each member keeps its own default branch (detected like a repo Project's), saved origin host and Merge Mode: `repositories.<repo>.merge_mode`, else `local` without an `origin`, else the Project's `merge_mode`. `defaults.target_branch` selects the optional shared PR/MR target; `repositories.<repo>.target_branch` overrides it for one member. Both are optional and are not User-only keys. `repositories.<member>.review` overrides `defaults.review`; the selected policy is frozen per Member and cannot be lightened by a Brief without recorded User consent. `posse project show` lists the members and their last checkout status; `posse project scan` adds new ones, refreshes their saved repository facts and marks vanished ones `missing`; `posse sync` fast-forwards each member separately, and a `root_behind` Notice names the member. Repeated origin-fetch failures use one Project-level `root_fetch_failing` Notice.

**Briefs.** `repos:` lists the members a Task works on (`[a, b]` or `a, b`). A Change Brief must list at least one; a Research Brief may list none; a Review Brief defaults to the reviewed Task's Members and may name only those. Unselected Members are not mounted or read through the live Project path. `root_context: read-only` explicitly selects a bounded shared-root copy; omitting it gives new Tasks no shared-root copy. A root-only Research may select this context without editable Members. The copy is read-only, changes are rejected at completion, symlinks are refused, and size/count limits apply. `root_context` is invalid for repository Projects. A Brief's `merge_mode` tightens each member separately unless a scoped User choice permits lighter delivery. All Member choices are checked before branch resolution; `pr` without an `origin` remains incompatible even with consent. A repository Change without an origin also requires local delivery. `base:` selects the Task's start branch and `target:` selects the PR/MR target; each may be a scalar for all members or an inline member map such as `{backend: staging, worker: master}`. Either branch may name another published Task branch. A YAML list is not a valid branch selection and returns `brief_invalid` with the required scalar or member-map form. A member-specific target overrides the configured target. Each member's base and frozen target are saved on its Task row; an explicit base stores the admitted commit for subsequent diff, proof and teardown checks, while the plan retains both its branch name and pinned commit. Sandbox acquisition fetches only after admission and refuses if a pinned commit is unavailable rather than substituting a later branch tip. Authorized feature/release targets do not change the repository's default branch.

**Sandboxes.** `~/.posse/pool/<project>/sandbox-<n>` is a folder. Acquire creates or reuses worktrees only for selected Members. New Tasks copy no shared-root files by default; with `root_context: read-only`, Posse copies shared-root files up to 64 MiB and 10,000 entries, skips Member and nested Git repository directories, refuses symlinks, and removes write permissions. Each requested member gets a worktree at its own path in the Sandbox, created on first use with `git worktree add --detach` from the member and kept afterwards, reset like a repo Sandbox and put on the Task's recorded branch from its `base_ref` (or the member default branch when no base was selected). Clean unselected worktrees left by legacy all-Member Sandboxes are drained with `git worktree remove`, never reset; a dirty, attached or unavailable legacy checkout quarantines that Sandbox and acquisition tries another without discarding its data. `[pool] setup` runs at the Sandbox root. The admitted Task plan freezes selected Member and root-context scope. Before a Worker starts, Posse records a per-Task fingerprint snapshot of the Sandbox's shared-root files and each present Member's `HEAD`. Legacy Research/Review Teardown compares selected Members against their Task base and unrequested Members against those captured commits, and compares shared-root files against the snapshot rather than the mutable live Project. New Tasks reject shared-root edits or additions at completion; root-only Research Tasks have no Member worktrees. It enumerates nested Git repositories through Git, recognizes nested repository directory entries, excludes `.git` metadata and ignored untracked files, and refuses Teardown if a required baseline or repository listing is unavailable. New scoped Tasks release by resetting only selected Members and safely removing clean legacy extras without resetting them; legacy-plan Tasks retain their historical all-Member reset after evidence preservation. Both remove shared copies; prune removes each Member worktree with `git worktree remove`, then the folder. A Workspace Project Sandbox opens as a tab of the Lead's workspace, unlike repository Sandboxes, which open as Herdr worktree children. A Workspace Project root is not a Git worktree. `claude-trust` trusts the Sandbox folder after checking each member worktree belongs to its member.

**Worker protocol.** A Worker told directly by the User to continue after a Change Task is `done` or `merging`, or after any Task is `stalled` or `needs-decision`, first records `posse signal working "<reason>"` and waits for success before acting. Every `done` Signal must include the current `--turn` token from `launch.md` or the latest Posse instruction envelope; a successful `working` Signal returns the new token. Posse rejects a completion from a prior launch or instruction turn. This cancels a pending Merge and clears the recorded merge head; if the forge merge has started, Posse refuses and the Worker asks the Lead to resolve it. `launch.md` adds a Workspace section that lists only the selected Member worktrees and states whether bounded shared-root context was selected. New Tasks have no shared-root copy by default. A selected `root_context: read-only` copy cannot be changed; completion checks its files and directories against the acquisition baseline. Legacy Tasks retain the old workspace-wide copy and Report preservation behavior. It also lists which members are on the Task branch with their base, Merge Mode and frozen target branch, and tells the Worker to commit inside each selected Member it changes and leave every other folder unchanged; no unselected Member checkout is provided. Under `full-pipeline`, each changed Member first needs private exact-head validation and its publication barrier (25.1, 25.14); Member evidence cannot be substituted across repositories. Each changed PR member must be published with `posse publish --repo <member> "<summary>" [--verify "<command> -> <result>"] [--proof "<markdown>"] [--risk "<markdown>"]`; verification lists commands and results, proof uses screenshots/images for UI changes or test/log evidence otherwise, and risk includes rollback details. `posse signal done` requires every requested Member clean, at least one with commits ahead of its base, and every changed PR Member to have a validated open PR.

**Merge.** `posse merge <task>` on a `done` Workspace Task handles each changed Member; unchanged Members remain `unchanged`. For `local`, Posse requires a clean worktree and fast-forward, then records the Task branch tip as the merge pin. It runs no verification; the User is responsible for checking local changes before approving the Merge. For `pr`, Posse validates the Worker's PR and remote head, confirms target freshness, records the exact PR head, then starts watching the request. Older completed Tasks without a Member PR still push and open one at Merge. The Task enters `merging` once every changed Member is ready, with one `merge_ready` Notice naming local Members. The persisted Member state `gated` means the merge head is recorded; it does not imply a command check ran. `--execute` (approval rules of section 14) fast-forwards each local Member's frozen target to its recorded head or merges each PR/MR pinned to its recorded head. PR Merge still requires green forge CI at `gated_sha`, the selected review evidence, forge mergeability and existing merge authority. A conflicting Member PR queues its Worker to merge the target. With `defaults.require_current_target`, Merge also requires a fresh target: if the target tip is missing from a PR head, Posse refuses with `pr_branch_behind` and, once the Task heads that Member's merge queue, queues the Worker to merge the target, resolve conflicts, republish and report done. The watch reads each Member through its forge (`gh` or `glab`) and applies the Notices of section 14 with the Member named in the summary and `repo` in the data. The Task becomes `merged`, with `merged_ref` listing `repo@commit` per Member, only when every changed Member has Merged. A moved Member branch (`branch_moved`) sends the Task back to `done` and that Member to `open`; Members already merged stay merged. A Member PR closed without merging raises one `pr_closed` Decision to reopen and relaunch or discard, with its Task and other Members unchanged. A merged Member is recorded as merged even if the Task is `working`, `blocked`, `stalled`, `failed` or `lost`; the Task Merges once every changed Member has Merged. A Worker fix after `posse send` requires recording a new merge head for each Member not already merging through an open PR. Teardown deletes each recorded Task branch when it is merged into the Member's frozen target or matches the exact merged PR head; later branch commits are preserved. For PR/MR delivery, it also deletes the recorded remote Task head only after a fresh forge read confirms the request is merged and the remote ref still equals the merged head; an advanced ref is preserved. `posse teardown --keep-branch` preserves local and remote Task branches. `posse clean --yes` retries this guarded remote cleanup for older torn-down Tasks. An approved discard records every Member's branch tip as `repo=sha` pairs first. Reconcile settles interrupted `merge --workspace` intents by checking whether each recorded local head reached its frozen target.

#### none and quick flow

After a loop-enabled Change signals done, preserve the existing path: freshness -> selected review -> pinned Merge, with PR-watch CI allowed in parallel with review on the published head. Missing reviewer resolution produces a readiness Notice, but never satisfies required `quick` evidence; explicit start reports the identity/Profile error. `none` does not acquire a fictitious review pass. Known blocking findings remain blocking under either mode.

#### full-pipeline flow

1. **Private candidate custody and freshness (VP-B).** For `full-pipeline`, `posse publish` is the submission entry point. It requires the existing clean, committed Task-branch preconditions, records submitted head `S`, frozen target tip `T`, and expected remote Task-branch head, then creates a durable private candidate ref and checkout without pushing or opening a PR. `none` and `quick` keep the existing publish behavior. The validation lane exclusively owns candidate head `H`; a later publish or Signal that finds the author branch moved refuses with both heads and requires resubmission for a fresh candidate. Persisted refs and records let Posse recover the candidate checkout after a crash. Candidate submission fetches the frozen target and merges it into the private candidate when needed (ADR 0019), never rebasing a published lineage. No new daemon or local bare repository is required.
2. **Review.** An independent identity-eligible Reviewer examines `H` through the numbered/delta Review Loop. Missing Profile, failed or inconclusive review blocks. Review fixes are author changes in the candidate lane, not permission to publish; the lifetime cap does not reset for any repair source.
3. **Test (intent proof).** Prove the Brief's intended behavior, using end-user/E2E evidence where applicable, and record commands, results and artifacts. Deterministic test results complement, not replace, intent proof. Inconclusive evidence is not a pass.
4. **Docs.** Update affected owner documentation, perform the no-comments check (remove unnecessary comments; retain necessary rationale), and prepare a complete PR description: intent, changes, verification commands/results, proof, risk and rollback. Record an explicit disposition if owner-doc changes are unnecessary; that does not skip the no-comments or description checks. `review_loop.docs` only controls extra reviewer rubric patterns, not this stage.
5. **Lint.** Run lint after docs so it covers documentation edits. Run the repository's workflow jobs locally where possible, preserving their test/lint ordering dependencies. Record unsupported jobs and environment/secret/event differences explicitly; local equivalence is not a claim that forge CI ran. Any unmet required local validation blocks rather than becoming an implicit pass.
6. **Exact-head publication barrier.** All local stages must qualify on one exact final commit `H`, not merely its ancestors. Any edit/commit during a later stage invalidates earlier local results; return through review -> test -> docs -> lint for the new head (a proved review carry is review-only, 25.8). Finish with a no-edit verification pass. Immediately before promotion, compare author, candidate and expected remote heads, current frozen-target tip and config binding. Moved author/candidate or stale evidence blocks promotion; an advanced target returns to freshness and validation. After validation passes, the internal promotion fast-forwards the Task branch from `S` to `H`, pushes without force, creates or updates the PR/MR, records promotion, and fast-forwards the Worker Sandbox only if it is clean. PR metadata failure after push is retried idempotently without bypassing validation for later code.
7. **Forge CI, then Merge.** After publication, forge CI is the final confirmation for exact published `H`; remote checks cannot run on an unuploaded commit. Pending, absent or unknown checks are not green proof; any no-CI policy must be explicit and trusted. CI code fixes return to private freshness and the entire local validation sequence before republishing. Same-head cancellation reruns use their separate budget and do not authorize code changes. Merge pins the same locally validated and forge-confirmed head containing the current frozen target, with no blocking findings and existing merge approval/Autonomy.

`local-validated` and `forge-ready` are distinct readiness states, neither meaning merged. The private lane does not publish a hidden candidate branch or draft PR before validation. No remote candidate-ref CI scheme is selected here. Fix instructions still queued and undelivered for the same head are coalesced; a new head invalidates its dependent evidence. Full-pipeline validation operates before publication; forge CI verifies the published PR head.

#### Delivery lanes

Every full-pipeline candidate belongs to one delivery lane: the Task's own repository, or one changed workspace Member seen as its own repository, with that Member's worktree, frozen target branch and Merge Mode. Submission, custody, ordered validation, promotion and the Merge barrier resolve the lane first and share one implementation; only the lane's target and publication differ.

| Delivery | Frozen target tip `T` | Expected remote Task head | Promotion | Integration |
|---|---|---|---|---|
| `pr` | origin `refs/heads/<target>` | origin Task branch | fast-forward Task branch, push without force, open/update PR/MR | forge merge pinned to `H` |
| `local` | the Merge target ref (local `refs/heads/<target>`, or `origin/<target>` for a non-default target with an origin) | none; never pushed | fast-forward the author Task branch only; target unchanged | local fast-forward Merge to `H` |

A workspace Worker submits, validates and promotes each changed full-pipeline Member with `--repo <member>`. One Review Round covers every Member candidate, and every Member needs its own test/docs/lint results. Review evidence comes from one qualifying pass that names every current Member head exactly (or a subset of the heads it named); a head outside that pass needs a proved carry or exact-head User disposition, and passes from different rounds are never combined. Members are promoted independently. The workspace done Signal and Merge require every changed full-pipeline Member's Task branch to equal its promoted candidate, against its current target. A Member already integrated under this barrier is not rechecked: one recorded merged, or a PR Member whose forge PR merged at exactly its validated head before the PR poll recorded it, which lets one Merge run merge every PR Member. A local lane's gated head must also equal its candidate, since local Merge fast-forwards to the gated head. Quick Members of the same workspace keep their own exact-head review check. Merge checks this before `done -> merging`, so a Member edited after validation blocks every Member before any integration. Unchanged Members need no candidate. PR and forge CI do not apply to local delivery; it never claims remote CI passed.

#### Local workflow execution

The User-only `full_pipeline.run_workflows` setting defaults to `false` and is frozen into the admitted plan. Enabling it authorizes workflow shell commands for that Task; changing the setting later does not change an existing plan. When enabled, lint inspects `.github/workflows/*.yml` and `*.yaml`, and executes only `pull_request` workflows on Linux `ubuntu-latest`, `ubuntu-22.04` or `ubuntu-24.04` runners. Jobs requiring other runners, secrets or expressions, matrix/strategy expansion, dependencies, conditions, containers, services, environments, unsupported properties/actions/shells, or unenforced timeout semantics are recorded as not applicable. A supported job is not run when the frozen opt-in is false; that blocks lint. Parse errors and supported command failures also block lint and publication. Per-workflow, per-job and per-step statuses, reasons and bounded command output are stored in the candidate-bound lint coverage. No workflow files is reported explicitly.

Local execution does not reproduce GitHub permissions, runner images, services, secrets, event payloads or forge checks. It is local CI-equivalent evidence, not a claim that forge CI ran.

### 25.2 Rounds

A **Review Round** is a Review Task of a loop-enabled Change Task. Round numbers are assigned at admission, starting at 1. A round that records a verdict (`pass`, `changes_requested` or `inconclusive`) consumes the cap. A round whose Review Task ends `failed`, `lost` or is discarded without a verdict is `void`: it stays visible, does not consume the cap, and its number is reused by the next admission.

Admission (through `posse review start <change>` or a Brief with `review_of:`) refuses:

- `review_round_active` while another round of the same Change Task is live;
- `review_round_unchanged` when the Change head equals the last reviewed head, or a carry already covers it;
- `review_round_cap` when the verdict-recorded rounds equal the frozen `max_rounds`. Under an admitted `full-pipeline` plan, Review fix and CI fix rounds count toward the same cap.

CI fixes, review fixes and target merges are author changes, never rounds. They enter the next round's delta.

**Cap.** Posse raises `review_cap_reached` and one User-only `review_cap` Decision (origin `review_cap:<change>:<head>`) when round `max_rounds` records a verdict other than `pass`, or when author changes appear after the last allowed round (for example a CI fix after a final pass). Options:

| Option | `posse apply` effect |
|---|---|
| `accept-head` | Records a `review_dispositions` row binding the current Change head with the User quote. Open blocking findings become `accepted`, and open non-blocking ones become `deferred` pending follow-up issues. Satisfies the review component for that exact head only, with visible User acceptance rather than a clean pass; it never substitutes for full-pipeline test/docs/lint or CI evidence. |
| `final-fix` | Queues one fix round (25.5) for the open blocking patterns; the next done Signal raises a new `review_cap` Decision for the resulting head. |
| `rethink` | Prints the command to start a new Change Task with `supersedes: <change>`. The new Task gets a fresh cap and inherits the ledger's findings as `inherited` entries so they are not reported again. The old Task follows the normal discard or Orphan path. |
| `discard` | Tears down with the recorded discard approval. |

Autonomy never answers a `review_cap` Decision.

Under `full-pipeline`, a spent cap also blocks republication: a CI repair that exhausts it queues no further fix, and publishing or recording a later stage for an unreviewed candidate is refused with `review_cap_reached` until the User's Decision is applied.

### 25.3 Scope

Every round binds, at admission and per repository (per changed Member for a workspace): `scope_base` (round 1: `merge-base(H, origin/<target>)`, later: the head reviewed by the previous verdict-recorded round `R`), `head` (`H`, the submitted private candidate in `full-pipeline`, otherwise the Change branch tip, also written to `review_targets`), `target_commit` (`T = merge-base(H, origin/<target>)` after fetching the frozen target), `baseline_tree`, `delta_sha256` and `scope_kind` (`full`, `delta` or `full_fallback`). `<target>` is always the Task's or Member's frozen target branch, never the repository default.

- Round 1: `baseline_tree` is the tree of `scope_base`; the scope is the full candidate.
- Later rounds: if `R` contains `T`, `baseline_tree` is `R`'s tree. Otherwise Posse runs `git merge-tree --write-tree R T` and uses the resulting tree, conflict markers included, and records the conflicted paths. The scope is `git diff <baseline_tree> <H tree>`. A clean merge of the target adds nothing, and a conflict resolution shows exactly as the resolved hunks.
- If `R` is not an ancestor of `H`, the scope is `full_fallback` (the round 1 rule). It still consumes a round, and the ledger still deduplicates.

Posse copies each `guidance` path from `origin/<target>` (never from the Change branch) into `review/guidance/`, and writes into the Review Task directory `review/round.json` (bindings, round number, remaining rounds), `review/delta.patch` (the scope), `review/cumulative.patch` (merge base to `H`, context only), `review/conflicts.txt`, and `review/ledger.md` (every ledger finding with its ID, pattern, state and fingerprint, plus the patterns claimed fixed since `R`). `launch.md` names these files and the rules below. The Reviewer works in a checkout of `H` and may read anything.

A finding is **in scope** when its excerpt overlaps an added or changed line of `delta.patch`, or when it names a `cause` hunk in `delta.patch` (an interaction finding: the delta broke unchanged code). Anything else is recorded `out_of_scope` with origin `pre_existing`, never blocks, and is listed for follow-up. In round 1 every introduced finding is in scope.

### 25.4 Findings and patterns

A Reviewer finishes with `posse signal done "<summary>" --report <file> --verdict <v> --findings <file>`. Under the loop `--findings` is required; a pass uses an empty `patterns` list. Schema:

```json
{
  "schema": "posse.review-findings.v1",
  "patterns": [{
    "key": "unchecked-error-return",
    "title": "Errors from store writes are dropped",
    "rule": "Every store write error reaches the caller",
    "root_cause": "New helpers call db.Exec without checking err",
    "fix_guidance": "Fix every call site of db.Exec in internal/app added by this change; rg 'db.Exec(' finds them",
    "severity": "P1",
    "origin": "introduced",
    "instances": [{
      "repository": "posse", "path": "internal/app/x.go", "line": 42,
      "symbol": "func saveRound", "excerpt": "db.Exec(ctx, q)",
      "description": "error ignored", "cause": null,
      "matches": null, "regresses": null
    }]
  }],
  "resolutions": [{"finding": "F-3", "status": "resolved", "note": "checked at x.go:40"}]
}
```

Rules, applied in the Signal transaction:

1. **Validation.** Unknown schema or malformed JSON refuses the Signal (`review_findings_invalid`). Each instance's `excerpt` must occur in `path` at `H` after whitespace normalization, else `review_finding_unanchored`. `line` is informational.
2. **Fail-closed defaults.** A missing or unknown `severity` is `unclassified`; a missing `origin` is `introduced`; a missing `key` places the instance in its own pattern `unclassified-<fingerprint prefix>`.
3. **Pattern keys** are lowercased, with runs of non-alphanumerics collapsed to `-`. Patterns with the same key within one Change Task merge into one pattern. A key must name a rule or cause; Lead may merge patterns later (25.6).
4. **Fingerprint** = SHA-256 of `key \x00 repository \x00 path \x00 symbol \x00 normalized excerpt`.
5. **Deduplication** against the ledger, in order. (a) A fingerprint already in the ledger in any state is dropped and counted as `suppressed_repeats`, except rule 6. (b) A `matches: F-n` claim naming an existing finding is dropped the same way. (c) Otherwise the instance becomes a new finding `F-<n>`. If its key equals an existing pattern, it joins that pattern as a `recurrence`.
6. **Regression.** An instance whose fingerprint matches, or whose `regresses: F-n` names, a `fixed` finding and that is in scope records a `regressed` event on that finding instead of a new finding, and raises `review_regression`. A `regresses` claim on a finding that is not `fixed` or not in scope is treated as a new instance.
7. **Resolutions.** For every finding claimed `fixed` by the last fix round, the Reviewer answers `resolved` or `unresolved`. `resolved` moves it to `fixed`, and `unresolved` keeps it open with an event. A missing answer marks it `unverified`. Resolutions never create findings.
8. **Scope classification** per 25.3.
9. **Verdict.** Posse derives `pass` when no finding is blocking (25.7) after rules 1-8, otherwise `changes_requested`. A Reviewer `pass` or `changes_requested` that differs from the derived verdict refuses the Signal (`review_verdict_inconsistent`). `inconclusive` is recorded as given and never passes.

The existing verdict row (section 13) is written as today; the round, findings, patterns and events commit in the same transaction.

### 25.5 Fix rounds

`posse review fix <change> [--pattern P-<n>]...` (or Posse, after a `changes_requested` verdict under `autonomy.review = "lead"`) queues one instruction to the Change Worker through the normal message path (Task → `working`, `gated_sha` cleared). Without `--pattern` it selects every pattern with an open, unresolved, unverified or regressed blocking finding, plus non-blocking patterns the Lead marked `fix`. The instruction quotes the Brief's User intent verbatim and lists each pattern's rule, root cause, fix guidance and instances, and asks the Worker to fix every instance of the class, including unlisted ones, then signal done with `--resolutions <file>`:

```json
{"schema": "posse.review-resolutions.v1",
 "patterns": [{"pattern": "P-2", "status": "fixed", "note": "also fixed y.go:88"},
              {"pattern": "P-4", "status": "disputed", "note": "the value is validated in caller z.go:12"}]}
```

In `full-pipeline`, fix instructions bind the expected private candidate head and cannot instruct publish-before-validation; submission of fixes resumes 25.1 before any push. In `quick`, fixes use the existing author branch/done path.

In a workspace, one instruction carries every selected pattern across Members and binds one expected head per changed Member: the active private candidate of a `full-pipeline` Member, otherwise the Member's Task branch head. The answering done Signal needs no promotion. Each bound candidate must still be the candidate the instruction named, clean, and descend from its expected head; otherwise the Signal is refused (`candidate_missing`, `candidate_dirty` or `head_discontinuity`). Promotion follows the next Review Round and each Member's own test/docs/lint stages.

The Change done Signal is refused with `review_resolution_missing` until every pattern of the pending fix instruction has an answer. `fixed` marks its open findings `fix_claimed`, which the next round verifies (25.4 rule 7). `disputed` marks them `disputed`, which needs a Lead or User disposition (25.6). After the done Signal, Posse raises `review_round_due` if rounds remain, or `review_cap_reached` if none remain.

### 25.6 Dispositions

`posse review dispose <change> <F-n|P-n>... <action> [--severity P0|P1|P2|P3] [--issue <url>] [--reason <text>] [--user-approved <quote>]`, where `action` is `fix`, `accept`, `defer`, `withdraw` or `reclassify`. `posse review merge <change> <P-n> <P-n>...` merges patterns into the first. Each is a ledger event with actor and quote.

- Any action that leaves a blocking finding unfixed (`accept`, `defer`, `withdraw`, or a `reclassify` below `block_at`) needs a User quote under every Autonomy (`review_disposition_requires_user`).
- With `autonomy.review = "lead"`, the Lead may `fix`, `defer` (with `--issue`), `withdraw` (with `--reason`) or reclassify non-blocking findings. With `ask`, the Lead raises the existing `review` Decision with the round summary.
- `--issue` records the follow-up URL. The Lead files the issue; Posse never creates forge issues.

### 25.7 Severity and blocking

A finding blocks while its state is `open`, `fix_claimed`, `unverified`, `disputed` or `regressed`, its origin is `introduced`, it is in scope, and its severity is `unclassified` or at or above the frozen `block_at`. `pre_existing` and out-of-scope findings never block. Non-blocking findings stay `open` until deferred, fixed or withdrawn. `merge_ready` lists any still undisposed.

`posse merge` and `merge --execute` refuse with `review_findings_open` while a blocking finding exists, under every review policy, until it is fixed or accepted by the User. `full-pipeline` also blocks publication. Changing modes never erases known findings or manufactures acceptance.

### 25.8 Evidence and freshness

Under `defaults.review = "quick"` (the migrated name for `local`), the current head's review component qualifies when one of the following holds and no finding blocks:

1. a qualifying D01 `pass` targets it (section 13);
2. a `review_carries` row maps a passed head to it. Posse writes one when a new Change head `H` has the passed head `P` as an ancestor, `git merge-tree --write-tree P T` reports no conflicts, and its tree equals `H`'s tree, with `T` the newest frozen-target commit in `H`. The check runs when the Change Task signals done and before Merge. It never rebinds the verdict;
3. an `accept-head` disposition binds it.

Any other new commit needs a round or a `review_cap` Decision. ADR 0019 is unchanged: a round may review a behind head, and Merge still requires the current target. Carries let the target merges that freshness requires keep the existing pass. A live Task with a frozen `no-mistakes` review policy cannot Merge on this release (25.17).

For `full-pipeline`, this review evidence is necessary but not sufficient: test, docs (including no-comments and complete PR description), lint/local workflow jobs and applicable forge CI must also bind the exact final candidate, target and config. Review carries never carry test/docs/lint/CI results; a new commit reruns those stages and needs qualifying review or a visible exact-head User disposition. Ancestry alone cannot keep stage results current. Missing, disabled, not-applicable and User-accepted results remain distinct from passed.

### 25.9 Roles

Every round is a fresh Review Task subject to the independent Review identity rule (section 13). Consecutive rounds may use the same Review Profile. The Reviewer never edits; the Change Worker applies every fix, and fixes are reviewed as author code. The Lead dispatches rounds, selects fix rounds and records dispositions within its Autonomy. The User answers `review_cap` Decisions and accepts blocking risk.

### 25.10 State

```sql
review_rounds(change_task_id, round, review_task_id, repository, scope_kind,  -- full | delta | full_fallback
  scope_base_sha, head_sha, target_commit_sha, baseline_tree, delta_sha256, conflicted_paths_json,
  status, verdict, created_at,                                              -- status admitted | verdict | void
  PRIMARY KEY(change_task_id, review_task_id, repository))
review_patterns(id, change_task_id, seq, key, title, rule, root_cause, fix_guidance, merged_into, created_round)
review_findings(id, change_task_id, seq, pattern_id, fingerprint, round, repository, path, symbol, excerpt,
  line_at_report, head_sha, severity, origin, in_scope, state, follow_up_url, inherited_from,
  UNIQUE(change_task_id, fingerprint))
  -- state open | fix_claimed | unverified | fixed | disputed | regressed | accepted | deferred | withdrawn
review_finding_events(id, finding_id, round, event, actor, note, user_quote, at)   -- insert-only
review_carries(change_task_id, repository, from_head, to_head, target_commit_sha, tree, created_at)  -- insert-only
review_dispositions(id, change_task_id, head_sha, decision_id, user_quote, at)       -- insert-only
validation_fix_rounds(id, change_task_id, kind, seq, expected_base_head, dedupe_key, message_id, created_at, member_heads_json)
  -- kind ci | review | freshness; insert-only; fix rows count against the frozen budgets
  -- a workspace review row lists {repository, expected_base_head, candidate_id} per changed Member;
  -- expected_base_head is then the digest of that list
```

Finding IDs (`F-<seq>`) and pattern IDs (`P-<seq>`) are per Change Task and never reused. A finding's `state` is derived from its latest event and stored for queries. All rows are in Task snapshots and restored by rebuild.

Lowkey reports `review_cap_reached`, `review_regression`, `ci_fix_exhausted` and `head_discontinuity` to the User; the others follow the `task_done` rule.

### 25.12 Command Gates removed

Configurable command Gates and their automatic repair loop have been removed. PR Merge relies on forge CI at the exact `gated_sha`; local fast-forward Merge runs no automated verification, and the User is responsible for checking it. `ci_loop` remains for forge-reported CI failures on PRs.

### 25.13 CI loop

The PR watch (section 14) records each observation by head. For a loop-enabled Change Task in `done` or `merging`:

- **Cancelled checks.** When every failed required check on the current head reports a provider cancellation (GitHub `CANCELLED`, GitLab `canceled`), and the forge head equals `gated_sha`, Posse reruns those checks on the same head through the forge CLI (`gh run rerun --failed`, `glab ci retry`), up to `ci_loop.rerun_cancelled` per check name and head. It raises `ci_rerun_requested`. A changed head or exhausted budget treats the cancellation as a failure.
- **Fix rounds.** For any other failed required check on the current head, Posse fetches failed-log tails (`gh run view --log-failed`, bounded to 200 lines per check; GitLab job trace), then queues one fix instruction with check names, log URLs and tails, and raises `ci_fix_queued`. On GitHub, which reports a failed rollup as soon as one check fails, Posse waits until every check on the head has completed so the instruction names every failed check in the run. Instructions are deduplicated by the set of failing check names per head, so a repeated observation does not queue twice. Each queued instruction consumes one CI fix round. When none remain, Posse raises `ci_fix_exhausted` (in addition to `pr_checks_failed`), and the Lead decides.
- Stale observations (section 14) never start a fix round. A behind head gets the freshness instruction instead.
- Under `full-pipeline`, a CI fix creates a new private candidate and re-enters freshness -> review -> test (intent proof) -> docs -> lint before any republish. Existing CI failure-set dedupe, budgets and coalescing remain; a CI repair never resets the three-round review cap. Exhaustion returns the applicable Decision/blocker, not permission to push. Cancellation reruns change no code and consume no code-fix round.

### 25.14 Head continuity

Every automatic instruction (freshness, CI, review fix) records `expected_base_head`, the head it was issued for. The Worker's next done Signal must have a Task branch tip that descends from it. Otherwise Posse refuses the Signal with `head_discontinuity`, naming both heads, and raises the Notice; the Lead decides. `posse publish` already refuses non-fast-forward pushes. At PR Merge, the recorded `gated_sha`, the review evidence head (pass, carry or `accept-head`), the newest green observation and the forge head must all be the same commit (D03 plus 25.8), and the merge stays pinned to it.

Full-pipeline requires more than ancestry continuity. Before every publication entry point (Worker publish, legacy Merge push, retry and all repairs), durable local-stage results must cover candidate `H`, frozen target tip `T` and config digest. Persist submitted author head, candidate, expected remote head, lane custody and stage head bindings. Refuse concurrent author/candidate movement instead of silently promoting a validator's changes over it. Recheck target freshness before publication and again before Merge; a target race invalidates readiness and requires revalidation. All changed workspace Members require their own applicable evidence; partial publication/merge stays visible and is never described as rollback or aggregate success.

### 25.15 PR evidence

Posse renders a `Validation` block inside its tokenized PR/MR body span (section 14) whenever evidence changes: the head SHA, review rounds used and remaining with the latest verdict, finding counts by state, carries, and CI state. Posse refreshes it during publish and when the watch records new evidence, using the stored marker token. The block sits between `<!-- posse:validation:start -->` and `<!-- posse:validation:end -->` inside the span; a watch refresh rewrites only that block (adding it before the span end when absent) and only when its digest differs from the last write, so human text and the rest of the span are untouched. For `full-pipeline`, also show submitted/candidate/published heads, frozen target, lane custody, each local stage's head/config binding, local-validated versus forge-ready, local workflow-job coverage/gaps, stale evidence and explicit skips/not-applicable/User exceptions. The complete PR description is prepared in Docs before push. The block is a report, not authority; publication and Merge read native durable evidence only from SQLite.

### 25.16 Target branch

Scope, freshness, carries, CI and Merge use the Task's frozen target (section 4: Brief `target:`, `repositories.<member>.target_branch`, `defaults.target_branch`), per Member for workspaces. Nothing in this section reads the repository default branch.

### 25.17 Removing no-mistakes

- **Review-name migration.** On update, automatically rewrite review config `local` to `quick` in global/Project `defaults.review`, supported Project scalar forms and `repositories.<member>.review`, preserving unrelated config and comments and saving the original bytes as a `.v015` backup. Keep no alias: after migration, explicit `review = "local"` in config or new Briefs is rejected with `quick` as its replacement. This is a semantics-preserving name migration, not consent to stronger/lighter review. Do not rename `merge_mode = "local"`, rewrite immutable plans or historical evidence, or change live Tasks to `full-pipeline`; historical `local` review keeps its original semantics when read. A failed migration must leave the prior usable config intact and report the file/key.
- **Removal (V15, #305).** `no-mistakes` in `merge_mode` (including the Project scalar form), `repositories.<member>.merge_mode`, `defaults.review` or `repositories.<member>.review` fails every config load and `posse config set` with `config_migration_required`. The message names the file and key; the help gives copyable `posse config set` commands for the replacement V14 recommended: `pr` for a Merge Mode, `full-pipeline` for review with `quick` and `none` as lighter choices, and keeping no-mistakes `commands.test`/`commands.lint` in the repository CI workflow. `posse doctor` reports it as a failing `config <project>` check with the same help. Posse never writes config for this migration; full-pipeline is not production-ready (25.1), so the User chooses. Briefs naming `no-mistakes` are refused before admission. The automatic vocabulary rename still runs on such a file (for example v0.14 `landing_mode = "no-mistakes"`, with its backup), so the error and the repair name the canonical key.
- **Update refusal.** `posse update` runs `_update-preflight` from the downloaded release; it refuses with `no_mistakes_tasks_live`, naming each `<project> t<n>`, while any live Task (`spawning` through `merging`) has a frozen `no-mistakes` Merge Mode or review policy, including a workspace Member's. `--force` does not override it. Finish or merge those Tasks on the current release, or cancel them with `posse teardown <task> --discard --user-approved "<User's words>"`.
- **History.** Plans frozen before plan version 6 still decode with `no-mistakes` delivery or review, and `review_receipts` stay readable in `posse show` and Task snapshots, including after `posse recover --rebuild`. Posse no longer queries or records receipts. A Task admitted under `no-mistakes` that is still live on this release fails closed: `posse signal done`, `posse merge` and `posse relaunch` refuse with `no_mistakes_removed`; branch and Sandbox cleanup of such Tasks follows `pr` rules.

## 26. Native research children

A Lead or Worker may delegate bounded read-only research to a native child of its harness. Posse registers every child as a research attempt before accepting any result ([ADR 0029](adr/0029-tracked-read-only-native-research.md)). Children are not Workers: they create no Task, do not count against `defaults.max_workers`, never claim a Task or adopt a worktree, and are not review evidence or a Report by implication.

- **Attempt.** Each attempt records its parent (the Lead or one Task), parent harness session and process instance, harness and verified version, native child identity, agent type, model, tools, `read-only` access, scope, prompt digest, state, resumability, session reference, runner and child process instances, usage, and a result pointer with byte size, digest and truncation. States are `registered`, `running`, `completed`, `interrupted`, `cancelled`, `failed` and `refused`. Refusals are recorded. At most `research.max_active` attempts per parent are registered or running.
- **Files.** Prompts, bounded `events.jsonl` logs, results and Pi sessions live under `projects/<name>/research/r<id>/` in the Posse home; runner logs live under `research-runs/`. Nothing is written to the checkout.
- **Reconcile.** Every `posse research` command reconciles active attempts. A Claude attempt whose parent process instance exited becomes `interrupted`, resumable only by the same parent session when the child transcript exists. A Codex or Pi attempt whose runner and child exited becomes `interrupted`, resumable when a Codex thread or persisted Pi session exists. Nothing is relaunched automatically.
- **Cancel.** `posse research cancel` records `cancelled` before signalling, so later output is discarded. It signals only the recorded runner and child instances after pidfd verification, plus the child's own process group.
- **Claude.** With `research.native = "tracked"`, Claude Lead and Worker launches add `--plugin-dir projects/<name>/claude-research`, whose PreToolUse, SubagentStart and SubagentStop hooks call `posse _research-hook claude`. Launching never runs the Claude binary; the hook probes the parent Claude executable's version only when an Agent call needs admission and caches it per executable file under `research-versions/`. An Agent call is admitted only for Explore, Plan or a project or user definition with an explicit read-only tool list (Bash allowed) and no bypass or accept-edits permission mode, MCP servers or isolation. Same-named overriding definitions are checked, not trusted. General and plugin agents, isolation worktrees, named teammates, an unknown or pre-2.1.0 Claude, a scope outside the parent's checkout, an exhausted budget, and a second unbound child of the same type in one session are refused. SubagentStart binds the agent ID. Inside the child, write tools, nested agents and shell commands the read-only parser does not accept are refused regardless of permission mode, and unregistered children are refused all tools. The shell parser admits `gh` only as `issue list|view`, `pr list|view|diff|checks`, `run list|view` (without `--web`) and `api` with one REST endpoint, GET and no body flags; every other `gh` command and `gh api graphql` is refused. SubagentStop stores the bounded final message and transcript usage. A completed child resumed by its own parent session returns to `running` under the same attempt when the active budget allows, and its next SubagentStop replaces the stored result; a foreign session or an exhausted budget is refused. A cancelled child's next tool call is refused.
- **Codex.** `posse research start --harness codex` runs `codex exec --json --sandbox read-only -c sandbox_mode="read-only" -c approval_policy="never" --cd <scope>` from a detached `posse _research-run` supervisor; follow-ups use `codex exec resume` with the same settings and thread ID. Posse never passes the parent's launch arguments. It reads the sandbox policy recorded for each child turn in the thread's rollout under `CODEX_HOME`; a thread that ran with another sandbox or recorded none is stopped and `refused`. Codex before 0.160.0 or without a readable version is refused before launch.
- **Pi.** `posse research start --harness pi` runs `pi --mode json -p --no-extensions --no-skills --no-prompt-templates --no-mcp --no-approve --offline --tools read,grep,find,ls` with `--session-dir` under the attempt and a Posse-chosen `--session-id`. A child announcing another session is `refused`. A follow-up opens the recorded session file and is `completed` only when Pi appended to it; otherwise it is `interrupted` with an unverified resume. Pi before 1.2.0 or without a readable version is refused. The Pi Lead extension's `posse_research` tool requires an explicit scope, keys each start by session and tool call ID, and cancels exactly its own attempts on abort or session shutdown.
- **Bounds.** `--scope` is required and must resolve inside the Lead's Project root or Task Sandboxes, or the Worker's own Sandbox. Prompts are at most 64 KiB. A process-launched child is stopped when its event stream exceeds `research.max_output_bytes` or it runs past `research.timeout`. Results beyond `research.max_result_bytes` are truncated and marked. The child's environment drops Herdr and parent-session bindings and is marked as a Worker of the Posse home.
- **Limits.** These checks are cooperative same-user hardening, not a sandbox. Mutating native execution is unsupported.
