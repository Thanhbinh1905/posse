# posse v1 spec

Terms are defined in [CONTEXT.md](../CONTEXT.md). The architectural shape is recorded in [ADR 0001](adr/0001-cli-owns-mechanics-on-herdr-without-daemon.md).

## 1. Scope

The User talks to one Lead per Project. The Lead writes Briefs, dispatches Workers, reviews their results and asks the User only for decisions that are the User's. Everything mechanical is done by the `posse` CLI.

In v1:

- Runtime: Herdr only (protocol 22 or newer).
- Workers: any agent kind Herdr recognizes. Built-in kind defaults ship for `claude`, `codex` and `pi`; other kinds run with User-supplied kind config.
- Task types: ship, scout, review (a review is a Scout Task on a Ship Task's branch).
- Landing Modes: `local`, `pr`, `no-mistakes`.
- Implementation: Go, shipped as one static binary `posse` ([ADR 0002](adr/0002-go-single-binary.md)).

Out of v1: other runtimes, remote machines, coordination across Projects, automatic Task queueing, quota-based routing, per-Worker-type Identity, `paths` matching in Dispatch Rules.

`Worker` is the internal/domain name for a delegated agent; **Rider** is its visible role label in Posse message envelopes, CLI prose and agent-facing role labels. Herdr child workspace labels show repository Riders; Workspace Project tabs show the Rider name. The display alias does not rename Go types, persisted Task identity, database fields or protocol keys.

## 2. Components

```
 User ──chat──► Lead (agent in a Herdr pane)
                  │ calls
                  ▼
 ┌──────────────────────── posse CLI (Go, TOON) ─────────────────────────┐
 │ config · dispatch · state machine · reconcile · landing · notices     │
 │ herdr adapter (the only module that talks to Herdr)                   │
 └──────┬───────────────────────────┬──────────────────────────┬─────────┘
        │ ~/.posse/posse.db         │ Herdr socket API         │ git, gh, no-mistakes
        │ (SQLite WAL)              ▼                          │
        │               Herdr server ── plugin event hook ──► posse _ingest
        │                           │
        │                           ▼
        │          Worker panes (one tab of the Lead's workspace + worktree per Task)
        │                           │ calls
        └────────── posse holler ◄──┘
```

- **`posse` CLI**: every command is short-lived. Each call opens the DB, runs a cheap reconcile for the Project it touches, does its work and exits.
- **Herdr adapter**: the single module that calls Herdr. It checks protocol compatibility once per process and maps Herdr errors to `posse` error codes.
- **Herdr plugin** (`posse-herdr`): a manifest whose `[[events]]` hooks run `posse _ingest` for `pane.agent_status_changed`, `pane.exited`, `pane.closed` and `pane.focused`. It holds no state and never runs long.
- **Lead instructions**: composed once for `posse lead` and Lead startup/restart. Bundled workflow guidance and User/Project preferences precede generated runtime obligations; Identity applies to User communication only.
- **Rider protocol**: generated by `posse ride` and prepended to every Brief, followed by the frozen Rider preferences.
- **Worker guard**: a `PreToolUse` hook (Claude Code, Codex) and a pi extension, installed by `posse setup`, that run `posse _guard` before every shell command an agent runs (section 13).

## 3. Home layout

`POSSE_HOME` defaults to `~/.posse`. Nothing is written into Project repositories.

```
~/.posse/
  config.toml                 global config
  projects.md                 generated fleet view for the User; never edited
  posse.db                    all Projects' state
  preferences/
    lead.md                   User Lead preferences (optional)
    rider.md                  User Rider preferences (optional)
  playbook/                   deprecated, still-read compatibility paths
    lead.md
    rider.md
  remuda/<name>/mount-<n>/      the Project's Remuda (section 12)
  projects/<name>/
    config.toml               Project override
    preferences/
      lead.md                 Project Lead preferences (optional)
      rider.md                Project Rider preferences (optional)
    playbook/                 deprecated, still-read compatibility paths
      lead.md
      rider.md
    tasks/<task-id>/
      brief.md                as written by the Lead
      launch.md               Rider protocol + Brief, as delivered
      report.md               Scout/Review Report (copied in by posse)
      findings.toon           latest no-mistakes or review findings, when any
```

`projects.md` is regenerated after every state-changing command. It starts with `<!-- generated by posse; edit config.toml instead -->` and has one section per Project: name, path, Landing Mode, Autonomy, Lead status, open Tasks by state, open Notices, last activity.

**Preferences (ADR 0013).** The optional Markdown files above are empty by default. For each role, Posse loads User sources before Project sources with visible path headers; a Project preference can refine or replace default/User workflow advice. New files under `preferences/` load after their legacy `playbook/` counterpart. Legacy content is never moved or overwritten implicitly. Preferences can change judgment-only workflow advice, but cannot grant authority, bypass evidence or override generated runtime obligations. Rider preferences remain subordinate to the Brief and Rider protocol. A Workspace Project uses its Project layer for the whole Workspace. `posse preferences show [--project <name>]` prints effective content and sources; `posse preferences path <lead|rider> [--project <name>]` prints canonical and legacy paths; `posse preferences set <lead|rider> --file <file> [--project <name>]` writes the canonical path atomically. `posse preferences move <lead|rider> [--project <name>]` explicitly moves a legacy file and refuses to overwrite an existing destination. A Lead write requires `--user-approved "<User's words>"` after explicit User consent, which Posse records; Riders cannot write preferences. Without `--project`, the current registered Project is selected when applicable, otherwise the User layer is used. `posse playbook show|path|set` remains as a deprecated alias and warns with the replacement command; it does not move legacy files. `posse doctor` warns when effective preference content exceeds approximately 4 KiB. There is no preference-specific hard limit; Lead startup still refuses complete instructions above the existing 30,000-byte budget without truncation.

```toml
# ~/.posse/projects/<name>/config.toml
landing_mode = "no-mistakes"
gate = ["just test"]

[defaults]
forge = "gitlab"             # optional explicit override for this Project

[repositories.worker]        # workspace Projects only: one table per member (section 24)
landing_mode = "local"       # local | pr; default local without an origin, else the Project landing_mode
gate = ["make test"]         # replaces gate for this member; User-only
forge = "github"             # optional per-member override

[autonomy]
yolo = false                 # shorthand: sets review = "lead" and land = "auto"
review = "ask"               # ask | lead
land = "ask"                 # ask | auto
```

Rules:

- **Identity is presentation toward the User, nothing else.** It shapes only (a) what the Lead says to the User and (b) display-only Herdr metadata the User sees (pane title, `display_agent`). Everything another agent reads or writes is canonical and Identity-free: Briefs, `launch.md`, the Rider protocol, `posse send` messages, Signal notes, Reports, Notices, all CLI output, agent names, pane labels, branch names, commits and PR text. Those are written in English in a neutral voice. The one exception is the User's own words quoted verbatim in a Brief's intent section. Changing any `[identity.*]` value must leave every such artifact byte for byte unchanged.
- `autonomy` is valid only in a Project file. In the global file it is a config error.
- A Brief may tighten Landing Mode (`local` < `pr` < `no-mistakes`) or Autonomy, never loosen them.
- `posse` validates the effective config on every call and refuses with `config_invalid` naming the file, key and reason.
- The built-in kind defaults above can be overridden but not removed; an unknown kind with no `[kinds.<kind>]` table runs with no extra args and `steer = false`.
- The Lead workspace label is `Lead:<project>`. Repository Riders are unfocused, labeled linked worktree child workspaces under the Lead; their tab label stays at Herdr's default. Workspace Project Riders remain plain `<name>` tabs in the Lead workspace. Existing tab-layout Tasks continue to reconcile by pane label and Teardown by tab. Posse never renames a User tab or workspace ([ADR 0012](adr/0012-group-repository-riders-under-lead.md)).
- A Profile's `model` and `effort` reach the agent only through the kind's `model_args` and `effort_args` templates; a kind without a template for a set value is a `config_invalid` error naming the Profile.
- `gate`, `[remuda] setup`, `kinds.<kind>.lead_auto_approve` and `[autonomy]` are User-only keys: `posse config set|unset` refuses them with `user_only` from the Lead pane unless passed `--user-approved "<User's words>"` with a non-blank quote. The Lead records the quote, key, action, set value and Project ID in `config_approvals` (global changes are attributed to the Lead's Project). A Worker cannot set or unset any key, even with the flag (section 13). Any other caller (the User's shell, or an agent the User runs for setup) counts as the User and needs no quote.
- Config is written through `posse config set|unset` and `posse lowkey on|off`, which validate against the schema, write atomically and keep comments. `posse config schema` prints every key with its type, allowed values, default, meaning and whether it is `user_only`.
- Claude, codex and OpenCode Leads get their kind's `auto_approve_args` by default, including after restart. Set `kinds.<kind>.lead_auto_approve = false` to keep that harness's approval prompts; Profile `args` may still add flags. This changes only harness permissions, not Posse autonomy: review and landing decisions remain governed by `[autonomy]`. Pi is unchanged because it has no permission system. A Lead also gets `lead_args`: codex's default `workspace-write` sandbox cannot write the posse home (SQLite in WAL mode needs write access even to read), the Mounts or the agents' trust files, so it also runs with `--sandbox danger-full-access`.
- `notice_delivery = "lookout"` requires `background_commands = true`.
- `[lowkey] lead = true` enables lowkey mode for the Lead (default `false`). `posse lowkey on|off|status` persists the Project setting from a Project checkout, or the global setting elsewhere. It is a reporting and Lead presentation preference, not an autonomy grant, and Leads may toggle it. Every `posse` and `posse lookout` response carries its current state and reporting rule, so a running Lead switches without restarting. In a Pi Lead, lowkey hides expanded thinking and collapsed `Thinking...` labels, all built-in and custom tool-execution rows (call and result), and assistant text from steps that call tools, including existing rows. The User's request and final reply remain visible; replies after tools stream normally, while first-step text waits until Pi knows it is not a tool preamble. These presentation filters preserve reasoning, tool calls and text in model context, session storage and exports. They leave the thinking level and Pi's `hideThinkingBlock` setting unchanged. While lowkey is on and a run is active, the Pi Lead replaces its stock working row with a one-row Slab animation above the composer; when the run settles or lowkey turns off, it restores the stock row. Lowkey off restores the hidden rows. The generated Pi Lead extension offers `/lowkey` to toggle and `/lowkey on|off|status` to persist or inspect the same setting without a transcript row; failed writes leave the choice unchanged. A Claude Code Lead uses a process-local function-hooks plugin when `posse up` starts it, with `CLAUDE_CODE_ENABLE_FUNCTION_HOOKS=1` and `--plugin-dir`; Posse does not alter the User's Claude settings. Its `/lowkey [on|off|status]` reads and writes the same Project `lowkey.lead` preference as the CLI and Pi extension, falling back to the global preference when the Project key is absent. Claude Code's tool calls, results, folded tool groups and assistant text from steps that call tools draw at zero height; the User's messages and final replies stay visible. Posse -> Lead Notice envelopes draw at zero height only when an exact matching Posse delivery record exists, not merely when User text contains `[posse |` (section 9). A one-row Slab animation replaces the stock spinner while working. Toggling redraws existing rows, and `claude --continue` reclassifies stored tool-step text. Hidden content remains in model context, session storage and exports. The function-hook API is early access: unavailable seams fall back to stock rendering; if the Notice records directory is absent, only Notice hiding falls back to stock while tools and the Slab remain lowkey. `posse doctor` warns when the installed Claude Code version has not been verified.

## 5. State (SQLite)

WAL mode, `busy_timeout = 5000`. Every state transition is one transaction that checks the expected prior state (compare and set) and inserts a `transitions` row.

```sql
projects(
  id INTEGER PRIMARY KEY, name TEXT UNIQUE, root TEXT UNIQUE,      -- git top-level, or the workspace folder
  default_branch TEXT,               -- repo Projects; empty for a workspace
  kind TEXT,                         -- repo | workspace (section 24)
  herdr_workspace_id TEXT,
  lead_pane_id TEXT, lead_label TEXT, lead_launches INTEGER,
  status TEXT,                                                    -- active | missing (repository moved)
  down_at INTEGER,                                                -- set by `posse down`, cleared by `posse up` (section 16)
  created_at INTEGER, last_activity_at INTEGER)

tasks(
  id INTEGER PRIMARY KEY, project_id INTEGER, seq INTEGER,          -- display id t<seq>
  type TEXT,                         -- ship | scout | review
  reviews_task_id INTEGER,           -- review only
  title TEXT, state TEXT, profile TEXT, dispatch_rule TEXT,
  landing_mode TEXT, autonomy_review TEXT, autonomy_land TEXT,
  branch TEXT, base_ref TEXT, worktree_path TEXT, mount_id INTEGER,
  launches INTEGER,                  -- agent launches, for unique agent names
  gated_sha TEXT,                    -- commit the Gate passed; the only commit --merge may land
  idle_since INTEGER,                -- when Herdr last reported this Worker idle without a Signal
  herdr_workspace_id TEXT, pane_id TEXT, pane_label TEXT, agent_name TEXT,
  agent_session TEXT,                -- from Herdr, for resume
  pr_url TEXT, landed_ref TEXT,
  last_output_hash TEXT, last_progress_at INTEGER,
  created_at INTEGER, updated_at INTEGER,
  UNIQUE(project_id, seq))

task_launch_identities(
  task_id INTEGER, launch_number INTEGER, profile_name TEXT,
  configured_model TEXT, model_known BOOLEAN,
  PRIMARY KEY(task_id, launch_number))
  -- one immutable configured launch identity per Task launch; missing rows mean unknown history

mounts(
  id INTEGER PRIMARY KEY, project_id INTEGER, n INTEGER, path TEXT UNIQUE,
  state TEXT,                        -- idle | held | releasing | broken
  task_id INTEGER, acquired_at INTEGER, released_at INTEGER,
  UNIQUE(project_id, n))

intents(id, task_id, command, step, data_json, started_at, updated_at)
  -- one row per multi-step command in flight (ride, land --merge, unsaddle, relaunch); section 17

transitions(id, task_id, from_state, to_state, source, note, at)
  -- source: worker | herdr | cli | lead | user

signals(id, task_id, verb, note, data_json, at)
notices(id, project_id, task_id, kind, summary, data_json,
        created_at, delivered_at, acked_at)
notice_delivery_receipts(delivery_id, batch_id, project_id, notice_ids_json,
        destination, generation, state, owner_token, claimed_at, lease_until,
        accepted_at, created_at, updated_at)
decisions(id, project_id, task_id, origin, question, options_json,
          answer, user_quote, created_at, answered_at, kind, task_launches, obsolete_at, obsolete_reason)
  -- unique(project_id, origin); at most one pending recovery Decision per Task
decision_notice_cursors(project_id, last_notice_id)  -- Notices evaluated for Decisions
messages(id, task_id, body, created_at, delivered_at, status)   -- Lead → Worker
events(id, received_at, kind, pane_id, data_json)               -- raw ingest journal
approvals(id, task_id, action, user_quote, at)                  -- merges and discards
config_approvals(id, project_id, key, action, value, user_quote, at)  -- Lead's quoted User approvals for config set/unset; value null on unset
pr_observations(id, task_id, repo, pr_url, head_sha, state, checks, review, mergeable, observed_at)
project_repos(id, project_id, name, path, default_branch, status, origin_host)  -- saved workspace members; status active | missing
task_repos(id, task_id, repo, worktree_path, base_ref, landing_mode, state, gated_sha, pr_url, landed_ref)
  -- one row per member a workspace Task touches; state open | unchanged | gated | landing | landed
pr_body_markers(task_id, repo, pr_url, marker_token, updated_at)
  -- one current cryptographically random description token per Task/member PR
repo_watch_state(project_id, repo, root_behind_head, checkout_checked_at, checkout_status, checkout_reason)  -- per-member checkout status and root_behind dedupe
```

Retention: `events` rows older than 7 days are deleted on ingest. Nothing else is deleted automatically.

## 6. Task lifecycle

```
spawning ─► working ─┬─► done ─► landing ─► landed ─► torn-down      (ship)
                     │     └──► reported ─────────────► torn-down     (scout, review)
                     ├─► needs-decision ─► working   (after posse send)
                     ├─► blocked ─► working          (Herdr: approval dialog)
                     ├─► stalled ─► working          (progress resumes, a Signal, or relaunch)
                     └─► failed
   done ─► working                                   (Lead sends a fix after a failed Gate or needs_rebase)
   landing ─► working                                (Lead sends a follow-up to a landing Ship Task)
   spawning, working, needs-decision, blocked, stalled, failed, lost ─► landed (forge reports the PR merged)
   spawning, working, needs-decision, blocked, stalled ─► lost   (Worker gone, not resumable)
```

| Transition | Source | Trigger |
|---|---|---|
| spawning → working | cli | agent started and brief prompt accepted |
| working → done / needs-decision / failed | worker | `posse holler` |
| working ↔ blocked | herdr | agent status `blocked`, then any non-blocked status |
| working → stalled | cli | stall rule (section 10) |
| stalled → working | cli / worker | new output or worktree change, any `posse holler` (applied before the Signal), or `posse relaunch` |
| needs-decision → working | lead | `posse send` starts durable submission |
| done → working | lead | `posse send` starts durable submission to a `done` Ship Task; clears `gated_sha` |
| done → landing | cli | `posse land` started (gate passed, PR opened or ready to merge) |
| landing → working | lead | `posse send` starts durable submission to a landing Ship Task; clears `gated_sha` and keeps its branch and PR |
| any non-landed PR Task → landed | cli | forge reports the Task's verified PR head merged; records the merge commit without passing through `done` |
| done → reported | cli | scout/review: `report.md` copied in |
| spawning (with a pane), working, needs-decision, blocked, stalled → lost | cli | reconcile: pane gone and no resumable session |
| landed / reported → torn-down | cli | `posse unsaddle` |
| lost / failed / stalled → working | lead | `posse relaunch` (section 17) |
| spawning → failed | cli | reconcile: a `ride` intent older than 5 minutes with no pane; its Mount is released |
| failed / lost / stalled → torn-down | user | `posse unsaddle --discard --user-approved "<quote>"` |

A Worker shell that exits closes its pane: Herdr emits `pane.exited` and the pane id stops resolving.

Live states: spawning, working, needs-decision, blocked, stalled, done, landing.

`done` and `landing` are never marked `lost`: their work is committed and the Worker is no longer needed. If their pane disappears, reconcile records a `worker_exited` Notice once and leaves the state alone.

Every Signal is one transaction: the `signals` row, the resulting transition(s) (including `done → reported` for scout and review) and the Notice commit together. When a Task enters `reported`, `failed`, `lost`, `landed` or `torn-down`, queued and claimed messages are atomically marked `undeliverable`; one `queued_message_undeliverable` Notice names their IDs and gives a supported resend step. A message still `submitting` remains governed by the uncertain-delivery protocol below. Migration 26 also repairs existing orphaned queues on terminal Tasks.

## 7. Reconcile

Runs during Project preparation (all Projects for `posse roster --all`), using one `session.snapshot` call. The complete runtime pass has a 3 second budget, including generation persistence and stall evaluation. Each admitted Task and Project observation gets a fresh bounded context and a SQLite lock wait of at most 250 ms. Work that cannot fit is deferred; later passes prefer stale Task observations instead of reusing expired contexts.

A reconcile that loses a compare-and-set race on a Task skips that Task (another process already moved it); it never fails the command. One Project's failure (missing repository, invalid config) is reported for that Project and does not stop commands for other Projects. Store contention and deferred reconciliation return retryable `store_busy`; `posse roster` instead shows its last recorded Task state with a deferral message when every reconciliation failure is transient contention. Mixed or persistent failures remain visible. The Lead Lookout logs and retries pure transient contention in preparation and Project-watch work without exiting or raising a Notice; mixed failures still raise a Notice containing their non-contention causes. Mount-state and repository-fetch flock acquisition stop after 3 seconds, even if the holder is stopped, and never steal or unlink its lock.

`posse holler` validates and atomically records its own Task's Signal, transition and Notice before any whole-Project preparation. Subsequent Project maintenance, Notice delivery and snapshot regeneration are best-effort within a separate 3 second budget; failures do not reject the committed Signal. Non-contention failures emit diagnostics; when an error aggregate also contains transient store contention, only its non-contention causes are shown. Pure transient store contention is deferred silently to the Rider; the Lookout logs the deferral and retries maintenance. Contention in the Signal's own transaction remains a retryable failure.

For each live Task:

0. **`spawning` with no pane id yet**: skip; spawn owns it until it records the pane.

1. **Pane present and the agent is the foreground process**: refresh `agent_session` only from a plain session ID or an absolute path inside that harness's session directory; map Herdr status (`blocked` → blocked; leaving `blocked` → working).
2. **Pane id missing**: look for a pane whose `label` equals `pane_label` (labels survive a Herdr restart; pane ids may too). If found, adopt its new pane id.
3. **Pane present but the agent exited**: if `agent_session` is known and Herdr native resume is enabled, leave it to Herdr (resume happens on client attach) and mark nothing; after 2 minutes without an agent **and** no resumable session (no `agent_session`, or native resume disabled), mark `lost`.
4. **No pane and no label match**: mark `lost`. The worktree and branch are never touched.

Herdr idle is never evidence of completion. Only a Worker Signal moves a Task to `done`.

The Lead is reconciled the same way through `lead_pane_id` and `lead_label`. A snapshot from a different Herdr server generation cannot update pane identities or stalls. Launch-capable Project commands and plugin events check the live server: a changed generation runs bounded recovery inline before reconciliation. A delayed snapshot from the old server is discarded and retried. `lead`, `show`, `ack` and `lookout` observe state without relaunching Riders, retrying launch Briefs or waiting for an active recovery claim; a pending generation leaves pane identities untouched.

## 8. Event ingest

`posse _ingest` reads `HERDR_PLUGIN_EVENT_JSON`, writes one `events` row, and for panes that belong to a Task or a Lead does the follow-ups below. Calling back into Herdr from inside a plugin hook is safe: verified on Herdr 0.9.0, a hook's `pane list` returned in about 3 ms and its `agent prompt` reached the target pane in about 300 ms. Follow-ups never hold a SQLite transaction open across a Herdr call.

- `pane.agent_status_changed`: apply the blocked mapping from section 7; if a Worker ends a turn, inspect the end of its output for a known model error for that harness before delivering queued `messages`; a Pi stream disconnect gets at most three `continue` nudges with exponential backoff, while a provider refusal is never retried. Each episode and retry is persisted in Task history. Automatic nudges use the existing focused-pane guard; unsafe or exhausted episodes raise a specific Notice. If the pane is a Worker becoming idle, done or working and it has queued `messages`, deliver eligible messages; if the pane is a Lead going idle or done, run Notice delivery.
- `pane.exited` / `pane.closed`: run reconcile for that Task.
- `pane.focused`: retry queued Worker messages and run Notice delivery after focus changes.
- Every call also evaluates stalls for that Project (section 10).

It exits 0 even on internal errors (logged to the `events` row) so Herdr never retries or blocks. Missed events are harmless: reconcile is the source of truth.

## 9. Notices and waking the Lead

Notice kinds: `task_done`, `needs_decision`, `task_failed`, `worker_blocked`, `worker_exited`, `task_lost`, `stalled`, `gate_failed`, `message_delivery_uncertain`, `notice_delivery_uncertain`, `queued_message_undeliverable` (terminal Task transition stranded queued messages), `model_stream_error` (bounded automatic recovery exhausted or was withheld), `model_refused` (provider refusal, never retried), `land_ready` (a `local` Task is ready to merge, or a PR is ready to merge), the PR Notices of section 14 (`pr_opened`, `pr_checks_failed`, `pr_changes_requested`, `pr_conflict`, `pr_merged`, `pr_closed`, `pr_watch_failing`), and `root_behind` when a new upstream head cannot be synced safely.

Not Notices: `working`/`idle` flips, `working` Signals, Herdr `done` without a Signal.

A Decision is a question only the User answers. Posse raises one from `land_ready` under `autonomy.land=ask`, review findings under `autonomy.review=ask`, and failed/lost Tasks. `posse ask <task> "<question>" --option <choice> --option <choice>` raises a Rider question. `posse decisions` lists pending questions; `--all` includes answered and obsolete ones. `posse decide <id> <option> --user-approved "<User's words>"` records an answer once and raises a `decision_answered` Notice. `posse apply <id>` carries out answered `recovery`, `review`, `leftover` and `pr_closed` Decisions: recovery relaunches or tears down with recorded discard approval; review queues the User's chosen response for the reviewed Ship Task or the no-mistakes Rider (ignore takes no Rider action); discard removes the Leftover ref or tears down a closed Task with its recorded User quote; open-task prints the command to start a new Ship Task with `posse ride --brief <file> --name <title-slug> --from-leftover <id>`; the new Task replays only the diff from the merged head to the saved snapshot onto the current default branch, without replaying squash-merged commits; reopen-relaunch reopens the PR and relaunches its Rider. The User's shell needs no approval flag: the typed option is its quote. When a Task Lands, relaunches or tears down before a Decision is answered, the pending Decision becomes obsolete with a reason, never an answer. Notice evaluation advances a per-Project cursor so unrelated and already evaluated Notices are not rescanned.

Store callers use `DB.RaiseDecision(ctx, store.DecisionRequest{ProjectID, TaskID, Kind, Origin, Question, Options})`. `Kind` is explicit: `land_ready`, `recovery`, `review`, `rider_question`, `leftover` or `pr_closed`. `Origin` is only a stable Project-unique idempotency key (for example `leftover:<branch>`); reuse with a different kind is refused. `DB.AnswerDecision(ctx, projectID, id, option, userQuote)` atomically records the answer and Notice. Neither call performs the chosen action.

Delivery, run after any Notice is created and on the triggers in section 8:

1. If no Notice is undelivered, stop.
2. If a delivery happened in the last 20 seconds, stop (the next trigger batches it).
3. `notification.show` once per batch with the count, and set the Project workspace token `posse=<n>` for the sidebar.
4. If the Lead's kind has `notice_delivery = "codex-queue"` and Herdr reports its session: run `codex queue --thread <session> --message <wake>` and mark those Notices delivered. codex holds the message until its current turn ends and never touches the composer, so this works while the pane is focused or busy. On failure, continue with step 5.
5. If the Lead's agent status is `idle` or `done` **and** the Lead pane is not focused: `agent.prompt` the Lead with the same line and mark those Notices delivered.
6. Otherwise leave the Notices undelivered.

Delivery contract: `posse send` and Notice wakes use `[posse | <origin> -> <recipient> <task> | <type> #<ids>]` followed by `body: <JSON string>`. For example, an instruction is labeled `[posse | Lead -> Rider t12 | instruction #7]`; the `body:` value remains the original message as one JSON-quoted inline string; routine messages do not get separate Markdown files. Long Scout and Review results remain Report files. Only the header is routing metadata. JSON quoting makes newlines, control characters and forged headers in a Lead instruction or Notice digest reversible body data, not new metadata. Message bodies remain unchanged in storage. Non-Pi harnesses see the textual envelope; Pi Notice wakes have `customType: "posse-notices"` and structured `details.origin: "posse"`, so the UI can show a compact header without marking the wake as User chat. A text prefix alone is not an authentication mechanism; never classify User input as a Notice by its words. A Claude Lead records the exact prompt before a typed Notice delivery; the lowkey renderer requires both a complete valid envelope and its matching record. A verbatim copy of a still-recorded Notice is indistinguishable from the original in Claude Code's drawing API and will also hide. This does not change Notice kinds or acknowledgment.

Worker instruction delivery atomically changes the message to `submitting` and reopens a `needs-decision` Task or completed/landing Ship Task immediately before `agent.prompt`. A Ship fix also clears `gated_sha`. The transaction commits before the instruction becomes visible, so an immediate Rider Signal sees the authorized state and no late delivery transition overwrites it. If Herdr's result is ambiguous, Posse raises one `message_delivery_uncertain` Notice immediately; after a crash, recovery raises the same Notice when the submission claim expires. The Notice identifies the Task and message, includes the instruction, and directs the Lead to inspect the Rider before sending a replacement. `posse show <task> --full` also exposes uncertain instructions. Posse never retries a `submitting` message automatically, so a crash before Herdr accepts the prompt can leave it unsent. Migration 21 makes legacy `claimed` messages uncertain rather than retryable. `posse show <task>` lists messages still queued or claimed and messages marked `undeliverable`; the latter remain inspectable after the terminal-state Notice. Queue insertion and submission both verify that the Task can still receive instructions, closing races with terminal transitions.

`posse lookout` blocks until an undelivered Notice exists. Its legacy path prints the digest and marks Notices delivered. The Pi and OpenCode adapters use `lookout --handoff --destination <adapter:session>` instead: Posse records a stable batch ID, exact Notice IDs, destination, Herdr generation, owner token and lease before printing. Printing changes the receipt to `printed`, not delivered. The adapter queries its persisted session before injection and reports `accepted`, `rejected` or `uncertain` through the receipt operation. Acceptance marks the batch delivered. A known rejection releases the same exact IDs for retry under the same stable batch ID. A Pi follow-up remains printed while queued and is reconciled at `agent_settled`, after its session entry is persisted. An ambiguous or unsupported session query holds the batch, creates a `notice_delivery_uncertain` Notice and prevents blind retry. Receipt leases prevent concurrent owners; after expiry, a retry to the same destination retains the batch identity and exact IDs, even when the Lead already acknowledged a Notice in that printed batch. Acceptance preserves those acknowledgments. A replacement session cannot claim another session's printed or uncertain batch: it holds the batch for receipt reconciliation. OpenCode checks the prior session history and resolves a recorded receipt as accepted or a confirmed absence as rejected; unsupported or ambiguous history remains uncertain. Pi accepts a matching stable receipt already present in its current session and surfaces uncertainty when it cannot confirm one. Receipt resolution is scoped to the active Project. Project snapshots preserve receipts, Notice state, ownership and leases for rebuild, including the receipt claim on an acknowledged printed or uncertain Notice. Receipt snapshots are associated with Project snapshots by stable Project UUID, so stale names and roots, or an old-name snapshot left by a Project rename, do not prevent rebuild. Rebuild refuses a receipt snapshot whose UUID matches no recovered Project. When receipt and Project snapshots contain the same Notice, the newer captured state wins for delivery and acknowledgment timestamps, and an accepted receipt keeps its Notice delivered. This is not an exactly-once guarantee: an adapter or receiver must use stable IDs to avoid repeating a recorded effect.

`posse ack` and `posse lookout --ack <ids>` commit only the requested acknowledgements without first running unrelated Project maintenance; selected completed Tasks still follow the `auto_unsaddle` policy. Unrelated automatic Teardown cannot prevent the acknowledgement commit. A Lead may acknowledge a Notice while its matching receipt is printed and the adapter is still completing the turn; later receipt acceptance preserves that acknowledgement, while a confirmed rejection reopens the Notice. If Lookout maintenance fails, it creates a separate retryable `pr_watch_failing` Notice and delivers it instead of aborting before the acknowledgement. Retrying an already acknowledged id is safe. A `lookout` Lead (claude) keeps one running as a background command. While a live Lead-side lookout for that Project exists, Posse leaves its Notices undelivered for that lookout even when the Lead pane is idle and unfocused; the dedicated `--poll-only` Lookout tab is not a Lead-side lookout. Posse types a Notice into an idle, unfocused Lead pane only when no Lead-side lookout process is live, including after it exits or crashes. Process liveness is checked on each delivery attempt rather than stored as a claim, so a dead lookout cannot block the fallback. A `pi-extension` Lead (pi) is started with a posse-generated extension that uses the handoff receipt, acknowledges safe `pr_opened` Notices without a turn when lowkey is on, and queues remaining batches as `posse-notices` custom messages with `pi.sendMessage(..., {triggerTurn: true, deliverAs: "followUp"})`. Its receipt query searches the Pi session entries for the stable delivery or batch ID before injection. A busy-session follow-up stays printed while queued; at `agent_settled`, the extension accepts it only after the matching custom-message entry is persisted, otherwise it surfaces uncertainty. The Pi extension hides the custom message while lowkey is on and shows it otherwise, and applies the lookout's lowkey state to the Pi transcript without restarting. An `opencode-plugin` Lead uses a process-local plugin appended through `OPENCODE_CONFIG_CONTENT`, preserving existing inline and file-based plugin config. It appends `lead.md` through `experimental.chat.system.transform` on every model turn and uses the handoff receipt. After a `session.idle` event, it submits actionable batches through `session.prompt` rather than writing to the TUI composer, then queries the session messages for the stable delivery or batch ID before reporting a receipt. If a replacement session finds an older printed batch, it checks the named prior session history and resolves a recorded receipt as accepted or a confirmed absence as rejected; unsupported history stays uncertain. OpenCode displays these turns in its transcript even in lowkey mode. ADR 0005 records the harness research behind these modes.

With lowkey mode on, typed and queued wake messages carry bounded, one-line Notice summaries and ids (for example `[posse | Posse -> Lead t12,t9 | notice #7,8]` with a quoted digest body), the current state and the reporting rule. The Lead does not run `posse` merely to learn what arrived. It messages the User only for `needs_decision`, `message_delivery_uncertain`, `notice_delivery_uncertain`, `land_ready` under `autonomy.land=ask`, failed/lost, `pr_closed`, persistent `pr_watch_failing`, and completed outcomes (`task_done` after review, `pr_merged`). Routine Notices (`pr_opened`, working notes, first `pr_watch_failing`, restarts) are acknowledged silently or grouped in one short line. Lowkey mode off retains the existing reporting behavior. This applies to claude, codex and pi Leads.

Notices stay open until the Lead runs `posse ack <id...|all>`. `posse --full` lists open Notices and the full dashboard; `posse --json` retains the complete structured dashboard. Plain `posse` shows active Task ids and states, undelivered Notice count and the next action.

## 10. Stall detection

A Task in `working` is stalled when all hold for `stall_after`:

- Herdr status is `working`.
- The hash of the last 200 lines of `pane.read --source recent-unwrapped` is unchanged.
- The worktree `HEAD` and `git status --porcelain` output are unchanged.

`last_output_hash` and `last_progress_at` are updated whenever an evaluation sees a change, and reset whenever a Task enters `working` or an evaluation is skipped because the Task is not `working` in Herdr. Resetting the stall clock does not clear the separate idle-without-Signal clock. A `stalled` Task whose output or worktree changes returns to `working`. Evaluation runs on every `posse` call and ingest for the Project, and every 60 seconds inside `posse lookout`. A stall creates a `stalled` Notice; nothing is killed automatically.

**Idle without a Signal.** A Task in `working` whose agent Herdr reports `idle` or `done` for `idle_after` with no new Signal creates one `worker_idle` Notice (the state stays `working`; the Lead decides: `posse peek`, `posse send`, or `posse relaunch`). This catches an agent resumed after a restart, or one that simply stopped without reporting. A recognized Pi model-error result requires a standalone `Error:` line, a known provider signature and Pi's fixed `/bug` help line; only terminal footer content may follow. Matching text inside Pi's bordered tool-result panels, including `$ command` shell output, is ignored, so copied tool output cannot trigger recovery. A recognized model-error episode suppresses this delayed generic Notice while a retry is pending, in favor of immediate bounded recovery or a specific model-error Notice. Pi stream-disconnect retries are limited to three per episode with 250 ms, 500 ms and 1 s backoff; a repeated screen on a new failed turn consumes the same episode budget after Herdr reports the Rider working again, even if normal reconciliation already recorded idle. Duplicate idle events before that transition are ignored. An active episode with no pending attempt retains the delayed `worker_idle` fallback if its end-of-turn hook is missed. Before submission, Posse rechecks the Task state, launch, pane ownership, episode, queued messages and focus/block safety. A `needs-decision` or terminal Signal blocks any pending episode. A charged attempt still incomplete after its backoff deadline plus a five-second submission lease is marked interrupted and produces a specific Notice rather than being replayed with uncertain delivery. The episode, attempts and outcome appear in `posse show` and its full Task signals. Refusals are never retried. No automatic prompt is sent to a focused or blocked Rider, and a queued Lead instruction takes precedence ([ADR 0015](adr/0015-bounded-model-error-recovery.md)).

## 11. Dispatch

`posse ride --brief <file> --name <slug> [--profile <name>]` resolves a Profile. `posse dispatch --brief <file> [--profile <name>]` returns the title-derived slug to pass as `--name`, even when it cannot choose among matching Profiles. An invalid `--name`, including one longer than 24 characters, reports the expected slug. A retry of the same Brief after a failed, lost or discarded Task may add a short suffix to that slug without rewriting the title; unrelated names are refused:

1. `--profile` given: use it if it exists, else `profile_unknown`.
2. Otherwise, if any rule has an exact `type` match, consider only those rules. If none match, consider rules with no `type`; their `when` text is descriptive and does not filter structurally.
3. When exact-type rules contain exactly one rule with no `when`, use it as the default for that Task type despite any typed `when` alternatives. Untyped rules, including global rules merged behind project rules, do not compete when an exact-type rule exists. The resolver does not evaluate `when`; the Lead can select a conditional alternative with `--profile` when its judgment applies.
4. Otherwise, exactly one matching rule with no `when`: use it.
5. Otherwise refuse with `profile_required`, listing the matching rules' `when` text and Profiles, so the Lead chooses by judgment.
6. No rule matches: use `dispatch.default.use` when configured.
7. With no Dispatch Rules at all and no default, use an implicit Profile of the running Lead's kind, with no model or effort arguments. Configured but unmatched rules still require a Profile.

The Task records the Profile and the rule used. Implicit resolutions report `implicit: lead kind` and store `implicit:<kind>` as the Profile reference, so relaunch and recovery retain that kind without a named Profile. This writes no config; explicit Profiles and defaults retain precedence. Model and effort come only from the Profile.

`posse dispatch --brief <file> [--profile <name>]` prints the same resolution without spawning; if Profile selection is ambiguous, `profile_required` includes the slug and candidate Profiles in help.

## 12. Remuda

Each Project has a Remuda of reusable worktrees (Mounts) under `~/.posse/remuda/<project>/mount-<n>`, created with `git worktree add --detach --lock --reason "posse: held by t<n>"` from the Project root. A Mount is held by exactly one Task from spawn to Teardown. The point of reuse is warmth: dependencies, build caches and other ignored files survive between Tasks.

**Acquire** (in `posse ride`):

1. Lock the lowest-numbered `idle` repository Mount before atomically claiming it as `held` for the Task; if none exists, claim the next path and create its checkout with Git's atomic `--lock`. A stale Posse lock can be replaced only after checking that its former Task no longer holds the Mount; foreign locks are never replaced.
2. `git fetch origin` in the Project root when an `origin` remote exists (skip otherwise). Reconcile restores a missing lock on every held repository Mount, including those owned by failed or lost Tasks, and raises a `mount_missing` Notice instead of rebuilding a vanished held checkout.
3. In the Mount: `git checkout --detach refs/remotes/origin/<default>` (or `refs/heads/<default>` without a remote), `git reset --hard`, then `git clean -fd` (`warm`) or `git clean -fdx` (`pristine`).
4. Verify `git status --porcelain` is empty; otherwise mark the Mount `broken`, create a `mount_broken` Notice, and try the next Mount.
5. Create the Task branch, then run `[remuda] setup` commands in the Mount; a failing setup fails the spawn (`mount_setup_failed`) and releases the Mount.

**Release** (in `posse unsaddle`, and when a spawn fails before the agent starts):

1. Stop leftover processes whose cwd is inside the Mount (`/proc/<pid>/cwd`): SIGTERM, wait 5 seconds, then SIGKILL. Never touch a process outside that Mount. List them in the output.
2. Detach at the last fetched default-branch ref, `git reset --hard`, make untracked paths writable inside the Mount, clean per `[remuda] clean`, then mark it `releasing` before unlocking the repository Mount. Teardown never fetches; it uses the last fetched default ref or the local default branch if no remote-tracking ref exists, and the next Mount acquisition refreshes origin first. Finalize it as `idle` after unlock. Reconcile completes an interrupted `releasing` Mount without making it reusable before cleanup; an interrupted held Mount remains locked.

A Mount is never released while its Task holds unlanded work, except through an approved discard.

A workspace Project's Mounts differ as section 24 describes: a Mount is a folder that mirrors the workspace root, with one warm worktree per member.

**Prune**: `posse remuda prune [--yes]` is a dry run by default. For repository Mounts it removes idle Mounts beyond `keep_idle` (highest numbers first), clean `broken` Mounts, and `broken` Mounts whose tracked files are clean and remaining untracked paths are read-only. With `--yes`, it restores write permission to untracked paths inside the Mount, removes untracked content from a broken Mount, unlocks a stale Posse lock, then runs `git worktree remove`. Workspace Mounts are removed member by member. `posse remuda` (no subcommand) lists the Project's Mounts with state, Task and path.

## 13. Brief and Rider protocol

Brief file, written by the Lead anywhere and copied into the home by `posse ride`:

```markdown
---
type: ship                  # ship | scout | review
title: Fix flaky login test
done_when: login spec passes 20 consecutive runs in CI mode
landing_mode: pr            # optional, tighten only
# review_of: t12            # review only
# repos: [backend, worker]  # workspace Projects: the members to check out (section 24)
ticket: 12                 # optional: the one issue this Ship Task should close
# issues: [12]              # legacy singleton alias for ticket:
refs: [18]                  # optional: issues this Task refers to without closing
# Workspace Projects scope issue references to a member: ticket: worker#12
autonomy: { land: ask }     # optional, tighten only
---
<body: goal, context, constraints, User's intent in their words>
```

A Ship Brief may name one closing issue with `ticket: 12`; a standalone Ship Task may omit it. During compatibility, `issues: [12]` is accepted as the same singleton, and if both fields appear they must name the same issue. New Ship Briefs reject multiple `issues` before a Mount is acquired. Existing multi-issue Tasks remain historical and their Briefs are not rewritten. Workspace Projects qualify the ticket and each `refs` entry with its owning member, such as `ticket: worker#12` and `refs: [worker#18]`. A ticket cannot also appear in `refs`. `ticket` closes only that issue when a PR/MR Lands; `refs` never closes issues. `posse dispatch` warns when a listed issue does not exist or is already closed, and says when it cannot verify one. `posse show` and `posse roster --full` display the ticket and references.

`posse ride`:

1. Validates the required `--name` format, then the Brief. For Ship Tasks, the title uses conventional-commit form `type[(scope)][!]: description` (for example, `feat(app): enable outcome-first runs`) and remains the forge pull request title unchanged, without an id or slug prefix. The branch slug is derived from the first three meaningful title words (lowercase kebab-case, at most 24 characters; common connecting words omitted). Hyphenated compounds stay together and consecutive duplicate words are removed. `--name` must equal that slug, except a retry after a failed, lost or discarded Task may append a short suffix. An unrelated or invalid name gets `name_invalid` with the expected slug.
2. Checks `max_workers` (`worker_limit`).
3. Resolves the Profile.
4. Checks that `posse/<short>` has not been used by another Task and does not exist locally or on origin in any Project repository (otherwise `branch_exists` tells the Lead to choose another `--name` before Task creation), then inserts the Task (`spawning`, `pane_label` already set, the title-derived slug recorded) with its `seq` allocated in the same transaction (a `seq` is never reused: allocation skips any number whose `tasks/t<n>/` directory exists, independently of Git branch names), writes a `ride` intent, acquires a Mount (section 12), checks out a new branch `posse/<short>` with `git checkout -b` (never `-B`; an existing branch is a `branch_exists` error) from the fresh default branch (review: from the reviewed Task's branch), and opens a repository Mount with `worktree.open` (`workspace_id` = the Lead workspace, `path` = the Mount, `label` = `<short>`, `focus=false`), or a Workspace Project Mount with `tab.create` in the Lead workspace. Posse reports pane `display_agent` using the resolved harness, then labels the pane with its Task identity ([ADR 0012](adr/0012-group-repository-riders-under-lead.md)). The Lead's workspace comes from a fresh snapshot: the one holding the Lead's labeled pane, or the recorded one if it is still labeled `Lead:<project>`; otherwise `lead_missing`. It does not create a top-level Rider workspace or a Git checkout. The Rider child workspace cwd remains the Mount path.
5. Runs the kind's `prepare` step, if any (below).
6. Labels the root pane `posse:<project>:t<seq>`, writes `brief.md` and `launch.md`, then starts the agent with `agent.start` (name `posse-<project>-t<seq>-<launch>`, cut to 32 chars and never derived from Identity, where `<launch>` counts launches of this Task so a relaunch never collides with a name Herdr has not released yet; args = kind `auto_approve_args` + `model_args`/`effort_args` filled from the Profile + Profile `args`). The canonical pane label and all internal identifiers remain unchanged. `launches` and its Launch Identity Record (Task id, launch number, Profile name, configured model value and whether that value is determinable) are committed together before each `agent.start`; relaunches append records and never replace earlier identities.
7. Codex and OpenCode receive `Read <launch.md path> and follow it.` as an opening turn in their start arguments, without typing into the composer. Other kinds receive it through `agent.prompt`. If their pane becomes focused before delivery, the Task stays `spawning`; a focus event or lookout reconciliation retries after it is unfocused. Focus alone never fails the Task. After two minutes without delivery, one `spawn_waiting` Notice is raised. A failed spawn with a written Brief keeps its initialized Mount for `posse relaunch` on the same branch.
8. Refreshes the Rider's pane metadata after launch and relaunch. `display_agent` is set to the resolved harness (`pi`, `codex` or `claude`) before `agent.start` and the detected harness afterward, never the unique internal agent name. Herdr's grouped Agents panel renders flat rows in workspace order. Posse uses `workspace.move_block` to place identified repository Rider workspaces directly after their Lead, preserving other workspace labels and relative order; reconciliation restores this after launch, relaunch, Teardown and recovery. Priority sorting and custom agent views remain User choices. Repository Riders keep `posse_row` empty so the optional Posse layout does not repeat their native workspace name. The Lead (`Lead:shop`) and repository Rider labels render with the harness on the next line. Workspace Project Riders retain the plain tab labels of ADR 0009. `identity.worker.display_prefix` remains accepted for compatibility but does not affect Herdr labels. The full Task title, visible Rider name and Mount path are submitted as the pane title, but Herdr truncates long titles and token values. Metadata tokens `posse_title` and `posse_branch` preserve the title and visible Rider name within Herdr's limits; `posse_mount` holds only the Mount basename to avoid a misleading mid-path truncation. The full Mount path remains in the pane cwd and Task record. This does not change pane cwd, the canonical pane label (`posse:<project>:t<seq>`), agent name or Task ID.
9. Displays the title-derived slug in `posse`, `posse roster` and `posse show`; Notice rows and wake bodies lead with the full Task title. Tasks without a recorded slug display their title. Internal Task ids remain available to agents for commands and canonical pane labels.

**Local Review identity.** A local Review Task is a fresh Task and starts a new agent session, not the Ship Task's session. Before launch, Posse compares the Review Profile name and configured model value with every recorded launch of the reviewed Ship Task. Both must differ from every author launch. An absent/unconfigured model, an additional model-setting argument, an argument Posse cannot classify for that harness, a missing author launch record, or a same-Profile/model match refuses the Review launch with the compared identities and reason. Posse parses the argument vector for the launch being recorded, including rendered resume arguments; a model-setting override or unclassified argument records the model as unknown. Profile changes on a Ship Task retain earlier launch records. `posse show <review>` reports the comparison; `posse show <task> --full` lists its Launch Identity Records. Posse does not infer provider identity from harness names.

A Review launch refuses session selectors in Profile arguments and any launch argument Posse cannot classify. On relaunch, only one explicit `{session}` selector in the kind's resume arguments may select the Review Task's own recorded session; extra selectors, model overrides and unclassified arguments are refused. This does not detect an agent switching sessions after launch.

A Launch Identity Record proves only the Profile and model value configured for that launch. It does not attest runtime model identity, detect an in-session switch, or prove that differently named configurations use distinct underlying models. No provider attestation or sandbox is added.

**Prepare steps.** A fresh worktree is a folder the agent has never seen, and some agents stop at an interactive trust dialog before reading anything; auto-approve flags do not skip it (Claude Code shows "Do you trust this folder?" even with `--dangerously-skip-permissions`). Built-in steps:

- `claude-trust`: before launch, set `hasTrustDialogAccepted` on the Mount's entry and on the primary checkout's entry in `${CLAUDE_CONFIG_DIR:-~}/.claude.json`. Only keys that are absent are set: a recorded `false` anywhere is never overwritten, and the Mount's own recorded import answers are kept. Carry the external `CLAUDE.md` import approval to the Mount only when the primary checkout already has it. Running Claude processes rewrite this file, so write it with a temp file and rename, then re-read and retry (up to 3 times) until the entries are present.
- `codex-trust`: append a `[projects."<mount>"]` block with `trust_level = "trusted"` to `${CODEX_HOME:-~/.codex}/config.toml` as text when no block for that path exists. The rest of the file, including comments and order, is never rewritten.

A kind without a prepare step that still stops at a dialog surfaces as `blocked` with a `worker_blocked` Notice.

`launch.md` = Rider protocol + Brief body + the effective Rider preferences. At dispatch, Posse copies legacy and canonical User sources first and then legacy and canonical Project sources, with source headers, into `launch.md`. This snapshot does not change when source files are edited; `posse relaunch` rereads the existing `launch.md`, so the admitted Rider instructions survive relaunch. Workspace Tasks use the Workspace Project preferences, not a member-specific layer. Preferences are supplemental and cannot override the Brief, protocol or runtime boundaries. The protocol says:

- Work only inside this worktree. Read anything, write nothing outside it.
- Run any Herdr or posse experiment against an isolated Herdr server and a `POSSE_HOME` under a temp dir (unset every `HERDR_*` variable, then point `XDG_CONFIG_HOME` and `POSSE_HOME` there); never touch panes, tabs or workspaces you did not create.
- Commit on your branch. For a repository `pr` Ship Task, run `posse publish "<summary>" [--verify "<command> -> <result>"] [--proof "<markdown>"] [--risk "<markdown>"]` to push only your Task branch and open or adopt its PR, then report the URL with `posse holler done "<summary>" --pr <url>`. For a workspace, add `--repo <member>` for every changed PR member and report done without `--pr`; Posse verifies each recorded member PR. Supply verification commands and results, screenshots/images for UI proof or test/log evidence otherwise, and risk plus rollback details. Never push directly, force-push, delete branches, change the default branch, or merge. In `no-mistakes` mode, deliver only through `no-mistakes axi run --intent <from brief>`; in `local` mode, do not push or open a PR.
- Report with `posse holler`:
  - `posse holler working "<note>"` for rare progress notes.
  - `posse holler needs-decision "<question>" [--findings <file>]` when you need an answer.
  - `posse holler done "<summary>"` (ship; `posse` checks the branch has commits ahead of base and the worktree is clean), with `--pr <url>` in repository `pr` and `no-mistakes` modes. For workspace Ship Tasks, Posse checks every changed PR member's recorded URL. Each PR's source repository, Task branch, target branch, open state, remote head and local commit must match.
  - `posse holler done "<summary>" --report <file-in-worktree>` for scout and review. Non-ignored untracked and edited Member files, plus committed changes beyond each selected Member's Task base or an unrequested Member's Mount-acquisition commit, are preserved beside `report.md` at their worktree-relative paths during Teardown. Workspace Scouts and Reviews also preserve new or edited shared-root files against a per-Task snapshot of the Mount before launch, including tracked and non-ignored untracked files in nested Git repositories. Later changes to the live Project do not alter that baseline; unchanged Project copies and `.git` metadata are not attached. If a required baseline or Git enumeration fails, a repair-or-discard Decision blocks Teardown and keeps the Mount. Repeatable `--attach <file-or-directory>` includes ignored Member evidence or unchanged shared-root files at Signal time. The Report should reference saved paths; `posse show <task>` lists attachments.
  - `posse holler failed "<why>"`.
- Answers and new instructions arrive as normal prompts.
- Waiting: for kinds with `background_commands`, run long commands (full test suites, e2e, builds) as background commands and never poll them; do other work or end the turn. For every kind: do not wait for PR CI after `posse holler done`, because posse watches the PR and the Lead sends fix instructions.

`posse holler` finds its Task from `HERDR_PANE_ID` (matching only Tasks that are not torn down), falling back to the Mount path. Lead-only commands run only from the Lead's pane: inside Herdr, a missing `HERDR_PANE_ID`, a pane that is not the Project's recorded Lead pane, or a cwd inside any Mount refuses with `lead_only`.

**Worker isolation** ([ADR 0007](adr/0007-isolate-workers-from-the-user-session.md)). Herdr gives every pane the full API of the User's session and has no per-pane scope, so posse enforces the protocol's isolation rule itself:

- **Worker mode.** A process is a Worker of a posse home when it or any process it descends from was started with `POSSE_WORKER_HOME` naming that home or runs inside one of its Mounts, or when its `HERDR_PANE_ID` is a Task's pane there. Ancestors are read from `/proc` (Linux; elsewhere only the process itself is checked), so `env -u`, `cd` and subshells do not shed the identity. Against that home a Worker may run only `posse brief`, `posse holler`, `posse publish`, `posse _context` and `posse config show|schema`; every other command refuses with `worker_forbidden` before doing anything. A Worker experimenting under another `POSSE_HOME` is not a Worker of it. Only a working `pr` Ship Worker (or the Worker of a workspace Task with a PR-mode member named by `--repo`) may use `posse publish`; it takes no refspec or merge flags and pushes only that repository's recorded `refs/heads/posse/<short>` without force.
- **Worker guard.** `posse _guard` reads a `PreToolUse` hook payload (`tool_input.command`, a string or an argv array, and `cwd`). Outside a Worker it exits 0. In a Worker it parses the command as bash and follows `export`, `unset`, `cd`, `env [-i] [-u NAME] [-C DIR] [-S STRING] [NAME=VALUE]`, inline assignments, wrappers (`command`, `exec`, `nohup`, `time`, `timeout`, `nice`, `setsid`, `sudo`, `doas`, `stdbuf`, `xargs`, `flock`, `watch`, `script -c`, `find -exec`), `sh -c`, `eval`, `source`, shell script files and executables with a shell shebang (read up to 1 MiB, six levels deep), heredocs, here-strings and piped stdin. It resolves the Herdr socket each `herdr` call reaches the way the herdr CLI does (`HERDR_SOCKET_PATH`, then `HERDR_CONFIG_PATH`, `XDG_CONFIG_HOME`, `HOME`, `HERDR_SESSION`). A `herdr` call aimed at the session the Worker runs in is refused unless it only reads: `--help` or `--version` before `--`, `status`, `api schema|snapshot`, or a `list`, `get`, `read`, `status`, `explain` or `wait-output` subcommand. An unknown target (`--session`, `--remote`, an unresolvable expansion or a conditional socket assignment) is refused too. Socket identity checks catch existing hard-link aliases; direct `ln` attempts to alias the session socket are refused. Code posse cannot follow is refused when it mentions `herdr`, `herdr.sock`, `HERDR_SOCKET_PATH` or `HERDR_BIN_PATH`, unless its environment resolves Herdr to another socket and the code does not name the Worker's socket. An unresolved or dynamically assembled socket target is refused as unknown, never treated as proof of isolation. Ordinary command data, such as an `rg` pattern or file path, does not trigger Herdr detection by itself. The only interpreter exceptions are narrowly matched, single-purpose Python inspections invoked with exactly `-c <literal-program>` and no extra arguments, redirected or piped stdin, or interpreter startup overrides (`PYTHONINSPECT`, `PYTHONSTARTUP`, `PYTHONPATH`, `PYTHONHOME` or `PYTHONUSERBASE`): `print(<literal>)`, `Path(<literal>).read_text()`, `importlib.metadata.version(<literal>)` and `sys.version` queries in a simple `print` expression. Other Python modes and interpreter programs remain opaque, including code that combines an inspection with another operation. This covers interpreters (python, node, deno, bun, perl, ruby, php, lua, awk and others; inline code, script files, heredocs, stdin), socket tools (`socat`, `nc`, `ncat`, `curl`, `websocat`), non-literal program names and unparseable commands. A recognized posse executable other than the one running the guard (`posse*`, renamed Go builds identified by build metadata, `go run ./cmd/posse`) is refused when its `POSSE_HOME` is the Worker's home. The demonstrated shell scripts and Make recipes written by redirection and run in the same command are refused when the command visibly names Herdr. The guard also refuses a Rider's direct `git push`; use `posse publish` for the recorded Task branch. A refusal exits 2 with the reason on stderr, which Claude Code and Codex show the agent; the pi extension returns it as `block`.
- Herdr's own agent integrations talk to the socket directly and are unaffected.
- The boundary is in ADR 0007: the guard sees only supported agent shell-tool calls. It is not a sandbox for compiled code, computed or encoded generated code, socket paths computed at runtime, or foreign binaries without recognizable build metadata. The tested redirection-and-execution cases are blocked when they visibly name Herdr, but arbitrary generated code cannot be inspected before execution. Older builds can bypass schema protections when run outside the hook; durable isolation needs server and filesystem permissions.

## 14. Landing

`posse land <task>` for a `done` ship Task:

| Mode | `posse land` does | Merge step |
|---|---|---|
| `local` | require a clean Mount; record the branch tip as `gated_sha`; run gate in the Mount; check fast-forward onto default branch; Task → landing; Notice `land_ready` | `posse land <task> --merge` fast-forwards the default branch to exactly `gated_sha`: `git merge --ff-only <gated_sha>` in the root checkout if it is on the default branch and clean, `git fetch . <gated_sha>:refs/heads/<default>` if the default branch is not checked out, else `land_target_busy`. If the branch tip is no longer `gated_sha`, refuse with `branch_moved` (help: run `posse land` again to re-gate) |
| `pr` | verify the Worker-reported open PR and remote head; run the configured gate; verify again; Task → landing and emit `pr_opened`. Legacy completed Tasks without a PR URL still push and open a PR at Land. | `posse land <task> --merge` uses the repository's forge CLI and pins the gated head SHA |
| `no-mistakes` | the Worker already delivered; record `pr_url`; Task → landing | same as `pr` |

- `posse publish [--repo <member>] [--refresh] "<summary>" [--verify "<command> -> <result>"]... [--proof "<markdown>"]... [--risk "<markdown>"]...` validates a clean, committed PR-mode Mount on its own Task branch, pushes only that ref without force, and creates or refreshes the forge PR/MR using the Brief title. Repeated `--verify`, `--proof` and `--risk` values are retained in order; verification values render as separate checked items, while proof and risk values are separated by blank lines. Every new body uses the shared seven-section template, in order: `Summary` from the supplied summary; `Issue Link` with `Closes #N` only for the canonical ticket and `Refs #N` for references; `Changes` from `git log <base>..HEAD`; `Verification`, rendering each supplied line as a checked `<command> -> <result>` item or `- [ ] Not run; reason: not supplied`; `Proof`, using supplied Markdown or `_No proof supplied._`; `Risk And Rollback`, using supplied Markdown or `Risk: not stated` plus `Rollback: revert this PR`; and the static unchecked `Documentation` checklist. Posse wraps the template in start/end markers containing a per-Task/member cryptographically random token persisted with the PR/MR URL in SQLite and the Task snapshot. A refresh replaces only one complete span whose markers contain that exact stored token; duplicate or incomplete matching markers conflict without edits, and all other marker-like text remains human-authored content. The Brief title is the PR/MR title. Before pushing, publish persists the origin's current Task ref under the Task and member, then associates it with the open request when the forge reports that head; this durable retry evidence is not a verified PR head. If an existing request reports that pre-push SHA or a previously verified Task head, Posse polls with exponential backoff for up to 30 seconds; another SHA fails with non-retryable `branch_moved`. If the forge still reports the prior SHA at timeout, publish returns retryable `pr_head_lag_timeout` before editing request metadata. An existing PR/MR is validated against its repository, source branch, target, state and pushed head before metadata changes. An unmarked legacy Posse description is not changed unless `--refresh` is supplied; explicit refresh preserves the entire existing description byte-for-byte and appends a tokenized Posse section. If a PR/MR has a tokenized Posse section but its token is absent from SQLite, publish returns a retryable `pr_body_marker_missing` error without forge edits; `posse recover --rebuild` restores the token from the Task snapshot before retrying. If the snapshot also lacks the token, restore a POSSE_HOME backup rather than editing the PR/MR markers. An unstructured human description or ambiguous matching markers are reported as conflicts and left unchanged. Metadata updates are safe to retry after interruption. `.github/pull_request_template.md` presents the same structure for human-created PRs. Workspace issue references are emitted only in the PR/MR for their named member. `posse holler done --pr` repeats URL and head checks; the Lead gates and verifies again before starting the watch. A workspace Rider adds `--repo <member>` to publish each changed PR member; `posse holler done` checks each recorded member PR without `--pr`. The Worker does not run the gate or merge.
- A failed gate creates `gate_failed` with the output tail; the Task stays `done` and the Lead decides whether to `posse send` a fix.
- A non-fast-forwardable `local` Task refuses with `needs_rebase`.
- `--merge` requires `autonomy.land = "auto"` or `--user-approved "<User's words>"`, stored in `approvals`. Otherwise `land_approval_required`, checked before any state change or Notice. A PR/MR merge also requires the latest observation for that request to match `gated_sha`, have checks `SUCCESS`, a review other than `CHANGES_REQUESTED` or `REVIEW_REQUIRED`, and mergeability `MERGEABLE`; otherwise refuse with `checks_not_green` and wait for `land_ready`. This check applies even with User approval or `autonomy.land = "auto"`.
- Git refs are always passed fully qualified (`refs/heads/posse/<short>`), so a tag of the same name can never be merged.
- `landing → landed` is observed by reconcile: the local merge result, or the PR watch below.

**Lookout tab.** `posse up` opens one unfocused `posse:<project>:lookout` shell tab in the Lead workspace for every Lead kind. It runs the absolute Posse executable with the Project's `POSSE_HOME` as `posse lookout --poll-only`, which reconciles PRs and tears down landed Tasks but never claims or acknowledges Notices. `posse up`, Lead recovery and the Lead's ordinary lookout ticks restart a dead Lookout process even when its restored pane still has the label. A newly created or first-observed labelled pane gets a five-second startup grace so slow login shells are not closed before `--poll-only` starts. Repeated failed starts retry with exponential backoff capped at one minute; recovery state persists across Lead re-arms, and after three failed starts the Lead receives one visible `pr_watch_failing` Notice for that episode. The grace is enforced by watcher ticks, so it does not delay `--timeout` or SIGTERM. A manually closed tab is recreated immediately, and replacement never types into an uncertain shell. Pure transient store contention leaves the Lookout running and logs a deferral without raising a Notice. Other reconcile or watch failures raise a visible `pr_watch_failing` Notice; mixed failures retain their non-contention causes.

**PR/MR watch.** Every Task with a `pr_url` is watched in every state until the forge reports it merged or closed, including `working`, `needs-decision`, `blocked`, `stalled`, `failed` and `lost`. A merged head is trusted when it remains on the Mount's Task branch or was recorded by `posse publish`; otherwise a deduplicated `pr_watch_failing` Notice names the reason and the next tick retries. An invalid PR URL that points at an issue instead raises one `pr_closed` Decision to replace the URL or discard the Task, not an endless `pr_watch_failing`. A failed observation never silently drops the Task. The forge watch uses its repository's forge. Workspace forge-discovery and PR-query failures are recorded with the affected Task and Member. Lookout polls each Member independently with a durable per-Member claim and at most one active forge query per Member. A stalled Member query or fetch does not join the Lookout tick or delay healthy Members' next poll cycle. Lookout runs checkout sync and landed-Task Teardown while PR polling is in progress. A newly landed Task triggers Teardown independently of the checkout join, so one blackholed Member fetch cannot delay healthy cleanup. A phase failure does not suppress the others. GitHub and GitLab adapters read each Task's request state, merge commit, head SHA, mergeability, reviews or approvals, and required checks from that Member's forge. It runs during reconcile when the last poll of that Project is older than `defaults.pr_poll` (default `2m`), and every `defaults.pr_poll` inside `posse lookout`. Pollers atomically claim a Project poll and each workspace Member's poll in SQLite before contacting the forge; duplicate pollers skip active claims, and abandoned claims expire. Each observed change is recorded in `pr_observations` and turned into at most one Notice per change:

| Observed | Notice | Task effect |
|---|---|---|
| PR reported by the Worker (or created by legacy `posse land`) | `pr_opened` | stays `landing` |
| required checks fail on the current head | `pr_checks_failed`, with failing check names and log URLs | stays `landing`; the Lead may `posse send` a fix (Task → `working`) |
| all required checks pass and reviews allow merging | `land_ready` | stays `landing` |
| review requests changes | `pr_changes_requested`, with the review summary | stays `landing` |
| merge conflict with the base | `pr_conflict` | stays `landing`; the Lead tells the Worker to merge `origin/<default>` into its branch, resolve conflicts, and report done again; never rebase a pushed PR branch |
| merged (by posse, by the User on the forge, or by anyone) | `pr_merged` | any non-landed state → `landed`; `landed_ref` is the merge commit; the Rider is interrupted during Teardown |
| closed without merging | `pr_closed` | keeps its state and branch; raises a `pr_closed` Decision to reopen and relaunch or discard; polling stops for this PR |

Before `posse send` delivers or queues a message to a PR-mode Task, it refreshes the PR watch. If the forge reports a merge, `send` refuses with `pr_merged` and the Task Lands. A landing Ship Task accepts a follow-up `posse send <task> <message>` even before `pr_checks_failed`, `pr_changes_requested` or `pr_conflict`. When durable submission begins, the Task returns to `working`, clears `gated_sha`, and keeps its branch and PR; after the next done Signal, the Lead runs `posse land` again. If a `land --merge` intent is still running, `posse send` refuses with `intent_active` and help rather than interrupting the merge.

The forge is selected from the repository's `origin` host (`github.com`, `gitlab.com`, or a configured enterprise host); `defaults.forge` overrides it per Project, and `repositories.<repository>.forge` overrides it per member repository. GitLab merge uses `glab mr merge --sha <gated_sha> --auto-merge=false` with squash or merge-commit. GitLab rejects `merge_method = "rebase"` before pushing or merging, since server-side rebase changes the pushed source branch; use squash or merge. A new commit pushed after a fix resets the check status to pending, so a later failure or pass on the new head produces a fresh Notice. `posse show <task>` includes a `pr{url,state,checks,review,mergeable,updated}` row, and home shows the PR state in the Task row. A forge CLI failure (network, auth) raises one per-Task `pr_watch_failing` Notice (and per Member for workspace Tasks) on the first failed observation and is retried at the next poll; three consecutive polling failures also raise one Project-level `pr_watch_failing` Notice.
- `posse up` refuses to set `no-mistakes` mode on a repo where `no-mistakes` is not initialized (`no_mistakes_uninitialized`, help: `no-mistakes init`).

**Keeping the Project checkout current.** The User never has to leave the Lead to `git pull`. After any Land (a local merge, or `pr_merged` from the PR watch), and during reconcile when the last fetch of the Project is older than `defaults.pr_poll`, posse runs `git fetch origin` in the Project root and brings the local default branch up to `origin/<default>` by fast-forward only:

- the root checkout is on the default branch with no tracked local changes: `git merge --ff-only refs/remotes/origin/<default>`. Untracked and ignored files do not block the fast-forward unless an incoming path overlaps them;
- when that root checkout is on the default branch, a tracked local change blocks the fast-forward even when it does not overlap incoming changes. An untracked or ignored path that an incoming change would overwrite also blocks it. In either case, posse leaves the checkout untouched and names the blocking paths in the `root_behind` Notice;
- the default branch is not checked out: `git fetch origin <default>:refs/heads/<default>` (no `+`, so it can only fast-forward);
- otherwise (another branch checked out, or local commits that are not on `origin`): posse changes nothing and raises one `root_behind` Notice per new upstream head, saying how many commits behind and why it could not update. `posse sync` retries the same rules once the User is ready.

posse never merges, rebases, stashes or resets in the Project root; the User's own work there is never touched.

Review findings (from `no-mistakes` `ask-user` gates or a Review Task's Report): with `autonomy.review = "lead"` the Lead decides and reports its decisions to the User as a summary; with `ask` the Lead asks the User.

Never allowed under any Autonomy: force-push, deleting a branch or worktree that has not Landed, touching secrets, acting outside the Brief.

## 15. Teardown

`posse unsaddle <task>`:

- Allowed for `landed` and `reported` Tasks. For `failed`, `lost` and `stalled` only with `--discard --user-approved "<quote>"`. Otherwise `teardown_refused` naming the state.
- Closes exactly the Task's own panes, and nothing else (below). It never uses `worktree.remove`, which would delete the Mount.
- Deletes the branch only after `git merge-base --is-ancestor <branch> <default>` holds, with `git update-ref -d refs/heads/<branch> <sha>`, except when discarding.
- Releases the Mount (section 12). Before resetting a discarded Task's Mount, record its branch tip SHA in the `approvals` row, so the discarded commits stay recoverable by SHA until Git garbage-collects them.
- Is idempotent: every step tolerates having already happened (tab or pane gone, branch gone, Mount already idle), so rerunning `posse unsaddle` after a crash finishes the job.

**Which panes are the Task's.** From one fresh snapshot, the Task's tabs are those holding a pane labeled with the Task's `pane_label`. A pane belongs to the Task when it carries that label, or it is an unlabeled pane in one of the Task's tabs **and** its cwd (symlinks resolved) is inside the Task's Mount. A linked Rider child is recognized by both its worktree checkout path and a labeled Task pane. A live agent in a candidate must be one of the Task's launches (`agentName`). Recorded pane, tab and workspace ids are never trusted alone: Herdr renumbers them when it restores a session and reuses workspace ids. Any other pane in the Task's tabs is a **foreign pane** (for example one the User split off to look around); panes in other tabs, including the Lead's and sibling Riders', are neither.

**Closing.** A linked Rider child with no foreign panes closes by `workspace.close` without `close_group`, never `worktree.remove`. A Task tab whose panes are all the Task's closes with `tab.close`; in a tab or child with a foreign pane, only Task panes close and foreign panes remain, listed in the output. Legacy Rider workspaces disappear with their last tab. If the User was focused on a closed Task pane, focus returns to the Lead. Then take a fresh snapshot and verify none of the closed pane ids and no pane with the Task's label remain. Every approved discard checks Herdr's process identity for live foreground agents in the held Mount before closing panes and again before releasing the Mount, whether or not project preparation attempted a Lead prompt. If an agent is not proven to be one of the Task's launches, stop before signalling or resetting the Mount. Release the Mount, which stops its remaining processes, and verify no process with a cwd in the Mount survives. A failed verification stops before the branch step, keeps the Task in its state, and creates an `unsaddle_incomplete` Notice naming what is left.

**Automatic Teardown.** A merged PR triggers automatic Teardown regardless of `auto_unsaddle`. Concurrent attempts do not raise an `unsaddle_incomplete` Notice for an active Teardown intent. A CLI reconciling while another process tears down a landed Task waits for the intent to finish, then reports `teardown_in_progress` if it still runs instead of presenting a half-torn-down Task as ready. Local `land --merge` succeeds only when Teardown completes; it accepts a Task already in `torn-down` without repeating Teardown, and returns an error if a competing attempt ends while the Task remains `landed`. After interrupting the Rider, Posse snapshots commits beyond the merged head and tracked or non-ignored untracked edits as one commit on `posse/<name>-leftover`, then releases the Mount and raises a `leftover` Decision: open a new Task from that branch or discard it. Ignored artifacts are not snapshotted. Mount processes stop before the snapshot. Committed member work not merged into that Member's default branch is also a Leftover, even if its worktree is clean. An unrecoverable snapshot failure raises a `leftover` Decision to repair the Mount or approve discarding its work. A failed attempt raises one `unsaddle_incomplete` reason and is retried on each reconcile tick even if that Notice remains unacknowledged. The Task never returns to `working`. With `auto_unsaddle = "finished"` (default), posse unsaddles other Tasks by itself as soon as they are `landed`, or `reported` and the Lead has acked its `task_done` Notice (the Report lives on in the home). `landed` limits it to landed Tasks; `never` leaves every Teardown to the Lead. `failed`, `lost` and `stalled` Tasks are never unsaddled automatically: their work is unlanded, and their panes stay for inspection until an approved discard.

**Orphan panes.** Reconcile also looks for panes labeled `posse:<project>:t<n>` whose Task is `torn-down` or unknown to the DB. Those of a `torn-down` Task pass the same ownership checks and are closed automatically. Unknown ones are never closed automatically: they raise one `orphan_pane` Notice, and `posse sweep [--yes]` (a dry run without `--yes`) closes them after the ownership checks.
- Keeps `brief.md`, `launch.md`, `report.md` and all DB rows.

## 16. Lead lifecycle

`posse up [--<kind>] [--replace] [--name <n>] [--yes]` from a shell pane inside a registered Project, a Git repository, or a folder whose direct subfolders are repositories, inside Herdr (`HERDR_ENV=1`, else `not_in_herdr`); never from inside a Mount (`lead_only`):

1. Registers the Project if needed: it detects the folder's shape (section 24), prints what it found and asks one `[Y/n]` in the terminal before saving. Without a terminal it refuses with `confirmation_required` (help: `posse up --yes`); `--yes` saves without asking; `n` refuses with `registration_declined`. The question comes after the kind, config and Herdr checks, so a refusal for another reason never asks first.
2. Chooses the kind: a `--<kind>` flag (`--claude`, `--codex`, `--pi`, one flag per kind Herdr recognizes; at most one), else the Project's `lead.kind`, else the global `lead.kind`, else the sole available kind (Herdr manifests first, configured kinds on PATH as fallback). With zero or several, return `lead_kind_required` listing available kinds. Output includes `kind` and `kind_source`; the automatic selection is not saved to config. The Profile is `lead.profiles.<kind>` when set, else the bare kind with no model or effort args.
3. If a live Lead exists: without `--replace`, refuse with `lead_running` (naming its kind and pane; help: `posse up --replace`). With `--replace`, stop its agent, keep its pane open as a shell, and clear its Lead label and metadata. The Lead holds no state, so only its conversation is lost; the output says so.
4. Make the calling pane the Lead pane and label it `posse:<project>:lead`. Clear that label from every other pane.
5. `agent.start` requires an available shell, but `posse up` is still running in the caller pane. One composer builds the complete Lead instructions for both `posse lead` and startup/restart: bundled default workflow guidance, User and Project preferences with source headers, then generated runtime obligations. The same composed text is printed and injected; preferences may change default workflow advice but cannot grant authority or override runtime obligations. Before writing or constructing system-prompt arguments, startup checks the complete injected instruction, including preferences and workspace guidance, against a 7,500-token budget measured as 4 bytes per token (30,000 bytes), not a model tokenizer. Oversized instructions fail with a stable error that names their byte size; Posse does not truncate them or start the agent. After printing its result, the CLI replaces itself with the configured agent process and its full arguments: the kind's `auto_approve_args` when `lead_auto_approve` is true, its `lead_args`, the Lead instructions through `system_prompt_args` when the kind has them, and the Lead Profile's arguments. `lead_auto_approve` defaults to true for claude, codex and OpenCode; set it false per kind to preserve approval prompts. Pi has no permission system. Restart uses this same launch path. A `pi-extension` kind also gets `--extension <home>/projects/<p>/lead-pi-extension.ts`, regenerated on every start. OpenCode gets a regenerated Lead-only plugin at `<home>/projects/<p>/lead-opencode-plugin.js`, injected through the process's `OPENCODE_CONFIG_CONTENT`; no User config file or global plugin is changed. Its `--prompt` opening turn creates a session for the plugin without typing into the pane (verified with OpenCode 1.18.32 TUI and isolated session storage). Herdr has no `agent.start` environment parameter, so a restarted Lead exports the inline config in its own shell before starting OpenCode. A `codex-queue` kind also gets an opening prompt as its start argument, because codex creates the session that `codex queue` needs only on its first turn. Herdr detects and tracks that process; a short detached Posse finalizer assigns the canonical name `posse-<project>-lead-<lead_launches>`, delivers the fallback `Run \`posse lead\` and follow it.` prompt for a kind without `system_prompt_args`, and redelivers eligible Notices.
6. Record the calling pane and its workspace as the Project Lead location.

A registered workspace Lead uses the saved Member list and does not rescan Member repositories during startup. Registered Project startup reconciles local Task and Mount state without fetching Git data, invoking forge CLIs or checking GitHub for an update. An interactive `posse up` from a versioned binary offers an update only from a fresh local cache; `posse update --check` performs the explicit release lookup. Interrupted PR-creation recovery stays durable until the Lead agent runs, then Lookout retries it. Mount Teardown resets to the last fetched default-branch ref without fetching; acquisition refreshes origin before starting new work. Lookout performs checkout and PR maintenance in the background. `posse project show` reports each Member's last checkout status, check time and reason, including an offline or otherwise unreachable Member. `posse project scan` is the explicit operation that refreshes workspace membership and saved repository facts.

There is at most one Lead per Project. Its pane title is `Lead: <project>` and its sidebar token is `posse_row=Lead:<project>`; `display_agent` shows the resolved harness before startup and the detected harness afterward, including recovery and reconciliation of existing sessions. Identity does not affect these fields. The Lead rebuilds its picture from `posse` after any restart.

**First outcome.** The Lead chooses the lightest workflow that can verify the outcome. A clear implementation request can go straight to one Ship Brief; Scouts, specifications, tickets and separate review Tasks are optional, not prerequisites. Before writing a Brief, startup instructions and `posse lead` guide the Lead to discuss substantive intent, scope, trade-offs and acceptance only when an unresolved choice could change the work, following User and Project preferences. The Lead investigates repository facts before asking, bundles consequential questions, treats tentative ideas as suggestions rather than permission, and resolves mechanics silently. It proposes Gate commands discovered in repository files but runs no discovered command as a Gate or Mount setup step without an explicit yes. Accepted Gates are saved for the Project through `--user-approved`; declining a Gate leaves work possible with no pre-Landing checks. One-off permission never becomes standing Autonomy. Before the first Ride, the Lead briefly states the deliverable, verification, permitted effects and return conditions. Identity, Profiles, Dispatch Rules, timing and Remuda tuning remain optional and are not prerequisites to the first outcome; the Lead offers personalization at most once afterward, using conversation history, and follows the User's language when `identity.lead.language` is unset. An explicit language, including `en`, wins; the schema default remains unchanged.

**Readiness.** Effective config and read-only checks produce an ordered `readiness` list: `forge_auth` for missing or unverifiable PR forge authentication, `gate_empty` for an empty effective Project or Member Gate, informational `autonomy_ask`, `no_mistakes_uninitialized`, then `machine_setup` for pending setup changes. Each gap has a stable code, consequence, key, `user_only`, fix and informational marker; startup context and status (including compact output) recompute the projection on every read and omit it when no gaps remain. Readiness never probes forge CLIs or resolves workspace remotes: it uses fresh cached auth results and reports unresolved forge/auth state as informational. Explicit `posse doctor` performs live forge checks, deduplicated by host, concurrent, and bounded by a separate 500 ms budget; results are cached for five seconds by effective config and CLI environment. Explicit `defaults.forge` and `repositories.<member>.forge` skip auto-detection. Doctor keeps its legacy checks, ordering, help and exit behavior and reports current authentication state. There is no first-run flag or new table. Readiness does not grant authority or hide decisions in lowkey mode.

**Stopping an agent.** Herdr has no call that stops an agent, so posse reads `pane.process_info` and, when the foreground process group is not the pane's shell, sends that group SIGTERM, waits up to 5 seconds for the shell to return to the foreground, then sends SIGKILL and waits 2 more seconds. If the agent is still running, the command fails with a retryable `agent_stop_failed`. `relaunch` uses this; the Lead paths (`up --replace`, the Lead restart in `recover`) stop the Lead with keys and its exit command so its pane stays a shell.

`posse project add [--name <n>]` registers the current repository or workspace folder the same way, without the question and without starting a Lead, so setup can configure it first. `posse project scan [<name>]` re-detects a workspace Project's members.

`posse project remove <name> [--yes]` unregisters a Project registered by mistake. It is a dry run without `--yes`. Only a Project that never had a Task or a Mount can be removed (`project_not_empty` otherwise), and not while its Lead is live (`lead_running`). It deletes the Project's rows and `~/.posse/projects/<name>/`, and never touches the repository.

`posse lead` prints the exact composed instruction text injected at Lead startup: bundled default workflow guidance, layered User and Project preferences, then runtime obligations generated from the current Project and harness. A clear implementation may go directly to one Ship; Scouts, specifications, tickets and separate review Tasks are optional. Preferences may change workflow advice, but cannot grant authority, bypass evidence or override runtime obligations. The generated text includes Identity (name, persona, language, form of address) scoped to User messages; neutral English is used for Briefs, `posse send` messages, reviews and decision records, and User words are quoted verbatim only as intent. Runtime obligations preserve the Lead delegation rule until its execution path changes, User-only Decisions and settings, Rider Signal completion, approval for Landing/discard, command mechanics, Notice handling, and safe recovery. The Lead uses the title-derived name returned by `posse dispatch` with `posse ride --name <short>`. Preferences cannot make unsupported in-place execution or review modes work; the Lead explains the limitation instead. The Notice rule matches the kind's `notice_delivery`; it includes the lowkey reporting contract and directs the Lead to use its harness delivery mechanism without polling. The command loop describes optional Brief fields `ticket:` and `refs:` for forge issue links: `ticket:` names the one issue a Ship Task closes when its PR Lands, and `refs:` adds non-closing references. During compatibility, `issues: [<one issue>]` is accepted as the same ticket; multiple closing issues are rejected. Workspace issue numbers include the owning member name (section 13). It also explains that `posse send --queue` waits for Rider idle instead of steering mid-turn.

`posse down`, run by the User in the Project folder, stops the Project without unregistering it. It refuses with `tasks_open` while a Task is running (`spawning` through `landing`) and with `user_only` from a Rider or a live Lead pane; a Lead pane whose agent has exited is a User shell. It records the Project down first, so the close events it causes do not recover it, then stops the Lead agent, closes the Lead and Lookout tabs (only those panes when a tab holds foreign ones; the caller's own pane stays open, unlabeled) and stops the Project's Lookout processes. A down Project is never restarted by the startup hook, plugin events or other commands; `posse up` clears it.

A moved repository makes its Project `missing`; `posse project move <name> <new-root>` fixes it, preserving the Project's stable UUID and refreshing its Task snapshots so database rebuilds remain valid.

## 17. Recovery

Work is never lost to a crash: commits live on the recorded `posse/<short>` branch, uncommitted work in the Mount, and the Brief in the home. This section makes sure a crash is also **noticed** and **resumable with one command**.

**Relaunch.** `posse relaunch <task> [--profile <name>]` restarts a Worker in the same Mount and branch. `--profile` must name a configured Profile, as with `posse ride`:

1. Allowed from `working`, `stalled`, `lost` and `failed` (a `failed` Task only if its Mount is still held). Writes a `relaunch` intent.
2. Finds the Task's pane (by id, then label); if none, reopens the Mount in a new workspace exactly as `posse ride` does and labels the new pane.
3. Uses the Task's current Profile unless `--profile` is given. If the kind is unchanged, the new model and effort arguments are used with the recorded session resume arguments. If the kind changes, it starts a fresh session without passing the old session and runs the new kind's `prepare` step for the Mount. A Profile change is recorded in state history with the old and new names, and becomes the Profile shown by `posse show` and `posse roster`.
4. Stops any live agent in the pane (see Stopping an agent in section 16), increments `launches`, and starts the agent with the full Profile arguments (`auto_approve_args`, `model_args`, `effort_args`, `args`).
5. Clears stale Git state in the Mount: removes `index.lock` only when no git process runs in the Mount, and reports an in-progress merge, rebase or cherry-pick instead of touching it.
6. Prompts one line pointing at a generated `relaunch.md`: re-read `launch.md`; inspect `git status` and `git log`; continue the Task; report with `posse holler`. It includes delivered Lead messages sent after the Brief in order, bounded to the most recent 32 messages and 1,200 bytes per message; later messages supersede earlier ones. Then moves the Task to `working`.

**After a Herdr or machine restart.** Herdr's own resume reruns agents with only their session argument, so Workers lose their auto-approve flags and the Lead loses its instructions. The plugin therefore declares a `[[startup]]` hook that runs `posse recover --all` (by the absolute path recorded at `posse setup`). For every Project it reconciles, relaunches each live Worker through the relaunch path above (with full arguments and `resume_args`), restarts the Lead in its recorded pane (or a new tab if that pane is gone), and delivers one digest Notice to the Lead listing what was recovered. `posse recover [--all]` can also be run by hand. If the startup hook does not run, the next launch-capable Project command (such as `roster`) or plugin event detects the changed generation and runs the same recovery inline; concurrent attempts use the recovery claim so they do not relaunch twice. If the previous generation was never recorded, `recover --all` still checks the Lookout process and replaces a restored shell-only tab.

**Bounded Rider recovery.** Each Rider has a persistent retry episode. `defaults.recovery_attempts` limits automatic relaunch attempts (default 3); the budget is charged before launch, including attempts interrupted by a crash. Failed attempts wait `defaults.recovery_backoff` (default 5 seconds), doubling up to one minute. Plugin events and launch-capable commands retry only after that delay. `posse up` still starts the Lead while an automatic Rider retry waits for backoff, then settles any interrupted explicit launch intent. A pending or exhausted episode keeps its budget across Herdr generation changes. A completed recovery is trusted only while its Rider pane remains live; a group close can reuse the same recovery generation, so a missing Rider is retried instead of being treated as recovered. Successful Riders are not relaunched again while another Rider retries. Exhaustion raises one `recovery_failed` Notice with the error and an explicit `posse relaunch <task>` escape hatch; acknowledgement does not re-arm it. Successful explicit relaunch resets the episode. `posse show` exposes its status, attempt count, next retry and last error. The Project generation remains pending while Riders retry, then advances even if a Rider exhausted its budget.

**Held recovery.** A Project that is down (section 16) or has `defaults.auto_recover = false` is held: `recover --all` skips it and lists it under `held_projects`, and plugin events and other commands leave its recorded panes untouched instead of recovering it or marking its Riders lost. The next `posse up` in its folder recovers it. When no Lead workspace is left, `posse up` first makes the caller's workspace the Lead workspace, so recovered Riders open beside the new Lead.

**Interrupted commands.** `ride`, `land --merge`, `unsaddle` and `relaunch` record their progress in `intents` before each step with a side effect. Reconcile finishes or undoes an abandoned intent (older than its command's timeout, with no live process holding it): a `ride` without a pane fails the Task and releases its Mount; a `land --merge` whose default branch already contains `gated_sha` moves the Task to `landed`; an `unsaddle` is simply rerun. The intent row is deleted when the command completes.

**While Herdr is down.** Read-only commands (`posse`, `roster`, `show`, `remuda`, `config show`) and `posse holler` work from the DB and disk alone and say that Herdr is unavailable; commands that need Herdr fail with a retryable `herdr_unavailable`.

**Losing the database.** Every Task state change writes `~/.posse/projects/<p>/tasks/t<n>/task.toml` atomically (temp file, fsync, rename) with its type, state, branch, Mount, Profile, `gated_sha`, pane label and Launch Identity Records. `~/.posse/projects/<p>/project.toml` records the Project, Mounts, Decisions, Notices and Decision Notice cursor. Task state, Project state, Decision creation and answers, Notice changes and cursor advancement refresh the snapshots. `posse recover --rebuild` (User-only) restores Projects, Tasks, Mounts, Decisions, Notices and cursors from the snapshots, along with legacy `posse/t*` orphan branches and Mount directories. It preserves Project stop state and Lead launch counts, matches Projects by their stable UUID (with a legacy name/creation-time fallback), and refuses identity conflicts instead of reassigning Tasks. Project moves preserve the UUID and refresh Task snapshots. If the database file is missing, orphaned WAL/SHM sidecars are preserved under timestamped `.orphaned-*` names before creating a replacement database. For a legacy Workspace without `project.toml`, it uses Members from the newest Task snapshot. Missing or incomplete launch records remain unknown; rebuild never derives them from current config. `posse` backs up the DB once a day with `VACUUM INTO ~/.posse/backup/posse-<date>.db`, keeping 7.

**Durability of files and deliveries.** `brief.md`, `launch.md`, `relaunch.md` and `report.md` are written atomically. Legacy `posse lookout` prints its digest before marking Notices delivered. Receipt-backed handoffs persist the exact batch and owner before printing, and mark it delivered only after the adapter reports acceptance. A crash after printing leaves the batch recoverable under the same stable ID. Ambiguous outcomes remain held and raise `notice_delivery_uncertain`; Posse makes no exactly-once claim. Receipt state and related Notices are snapshotted under each Project for rebuild.

## 18. Setup, skills and hooks

Once per machine, `install.sh` installs the `posse` binary and runs `posse setup` with the User's go-ahead (`--yes` applies it without asking, no TTY keeps the safe default of not applying, `--no-setup` skips it). `posse setup` needs neither a Herdr pane nor a running Herdr server: it talks to Herdr only through the `herdr` CLI. It is idempotent, prints its plan and what it changed, and records its managed installations in `~/.posse/setup.json`. Posse does not modify the User's Herdr sidebar configuration:

1. Checks prerequisites: `git`, `herdr`; optional `gh` and `no-mistakes`; lists available agent kinds (the kinds `herdr integration status` knows).
2. Installs the Herdr integrations for the kinds it finds (`herdr integration install <kind>`), which Herdr needs to resume their sessions.
3. Links the `posse-herdr` plugin into the User's Herdr (`herdr plugin link`; a running server picks it up immediately).
4. Creates an empty `~/.posse/config.toml` when missing; schema defaults apply without persisting detected kinds, Profiles or Identity preferences. Existing config is preserved.
5. Installs the skills into `~/.agents/skills/posse` and `~/.agents/skills/posse-setup`, symlinked into `~/.claude/skills/`.
6. Merges a SessionStart hook running `posse _context` and a PreToolUse hook running `posse _guard` into `~/.claude/settings.json` and `~/.codex/hooks.json`, keeping every existing hook and the file's formatting, written atomically.
7. When pi's agent directory (`${PI_CODING_AGENT_DIR:-~/.pi/agent}`) exists, installs `extensions/posse-worker-guard.ts`, which runs `posse _guard` before every bash tool call.

The Claude Lead plugin is bundled in the binary and written under the Project's Posse home on Lead launch, not installed in the User's Claude settings or loaded for Riders. Its zero-height drawing, restored-row classification, redraw and animation packing are adapted from [firstmate-calm](https://github.com/kunchenguid/firstmate) (MIT, copyright 2026 Kun Chen); the plugin bundles `FIRSTMATE-LICENSE`. Posse's record-backed Notice recognition and Project preference handling are independent. Unit coverage runs through `claude plugin test internal/app/claude_lowkey`; the credentialed live TUI regression is `POSSE_CLAUDE_LOWKEY_LIVE_E2E=1 scripts/claude-lowkey-live-e2e.sh`. It uses an API key or a copied OAuth login in an isolated Claude config, and tests the collapsed `Ran 1 shell command` row on Claude Code 2.1.283.

`posse setup --check --exit-code` exits 3 when required setup would change the machine and 0 when nothing is pending, which is how `install.sh` decides whether to ask. `--human` only changes the display: a checklist for people instead of TOON (`+` pending, `✓` done, `-` unchanged, `!` manual, `✗` blocked), which `install.sh` shows. `posse setup --uninstall` removes exactly what `setup.json` lists and never touches `~/.posse` data. `posse doctor` reports skills or hooks older than the binary, a failing plugin hook (from Herdr's plugin log), missing integrations, group-close risks from other repository primaries and unverified Claude Code function-hook versions.

**`posse _context`** prints role context only when the pane is a posse Lead or Worker (which command to run next: `posse lead` or `posse brief`, and the Task id); anywhere else it prints nothing. It runs in under 20 ms. The hook fires on session start, resume and compaction, so an agent never loses its role.

**Skills** are thin: the CLI owns every instruction that must be exact, and the skills point to it.

- `posse` (agent-triggered): what posse is, how to tell the role from the pane (`posse _context`), and where to go next (`posse lead`, `posse brief`, `posse up`, `posse --help`).
- `posse-setup` (User-invoked `/posse-setup`): an optional full tour, beginning with the faster path of `posse up` and a first request. It interviews at three scopes: machine (verifies `posse setup --check` and applies pending changes), global config, then per Project (`posse project add`, `posse config set --project`), and ends with `posse doctor`. It reads `posse config schema`. For User-only keys, outside a Lead pane it gives the User the exact `! posse config set|unset ...` command; inside the Lead conversation it writes only after explicit consent with `--user-approved "<User's words>"`. Riders cannot write config.

Skills and the hook ship inside the binary and are versioned with it.

## 19. Updates and releases

**Releases.** Releases are manual: the User chooses whether and when to publish a version. After the intended changes land on `main`, publish a `vX.Y.Z` tag on a reviewed commit with passing CI. Before 1.0, `fix:` changes imply a patch bump and `feat:` changes imply a minor bump. Pushing a version tag starts `.github/workflows/release.yml`, which runs GoReleaser and publishes Linux and macOS archives for amd64 and arm64 plus `checksums.txt`. Ordinary pushes and merges to `main` run CI only; they do not create tags or release PRs. Branch protection on `main` must require pull-request reviews and the checks `lint`, `test`, `e2e`, `installer`, and `build`, and must prohibit force-push and deletion. Do not apply branch protection from posse.

**`posse update [--check] [--version vX.Y.Z] [--force] [--stop-lookouts]`**:

Installing requires a User terminal outside Herdr or a live Herdr shell pane with no agent and no Lead or Rider binding. Posse verifies the caller before downloading and installing; an unknown pane or unavailable Herdr state blocks installation.

1. Finds the latest (or requested) release on GitHub; `--check` prints the current and latest version with the changelog summary and stops.
2. Downloads the archive and `checksums.txt` and verifies the SHA-256.
3. Backs up the database with `VACUUM INTO ~/.posse/backup/posse-pre-<version>.db`.
4. Replaces the binary atomically (temp file, then rename). Running `posse` processes keep the old binary until they exit.
5. Runs `posse setup`, so skills, hooks and the plugin match the new version.
6. Database migrations run forward only, on the new binary's first command, and `posse setup` applies them right after installing. Every applied migration's SHA-256 is kept in `posse_migration_checksums`. Opening a database refuses `schema_unknown` when it has migrations the build does not know (an older build after an upgrade, or a branch build), and `schema_diverged` when a known migration was applied with different contents. Pending migrations on an existing database are applied only by the installed posse (the `binary` in `setup.json`), and never by a Worker for its own home (`migration_refused`). `POSSE_FORCE_MIGRATION=1` overrides every check but the Worker rule, for the User.
7. Mark migrations that cannot run with live Tasks with `-- posse: requires-no-live-tasks` in the SQL migration. The downloaded binary preflights those migrations before replacement; `posse update` refuses until no Task is live, or until `--force`, saying why. The migration gate enforces the same rule on first open.

`posse update` refuses with `lookouts_running` while any `posse lookout` for this `POSSE_HOME` is alive, including `--poll-only` Lookout tabs and Lead watchers. The error lists each PID, Project and kind. `--check` reports the same process list without stopping anything. `--stop-lookouts` sends SIGTERM, waits five seconds, then sends SIGKILL to remaining processes before replacing the binary; the result lists what stopped and who restarts it. The Lookout tab owner recreates its process on its next tick, a Claude Lead restarts its background lookout on its next wake, and the Pi/OpenCode Lead extension restarts its watcher automatically. A Lead-side lookout stopped by an update returns `state=stopped` and `reason=update` with restart guidance. Discovery uses `/proc` on Linux and `ps` plus the process's loaded executable on macOS. It verifies the Go build's main package is `github.com/thanhbinh1905/posse/cmd/posse` and rechecks the executable's file identity before signaling, so renamed Posse binaries remain supported while other main packages from the Posse module and unrelated commands are ignored.

**Update notice.** Automatic commands never perform a release lookup: `posse` and `posse doctor` use only a fresh local cache, and a successful unversioned `posse update --check` refreshes it. Cached releases drive `update{current,latest}`, the `help[]` entry and one `update_available` Notice per new version; an interactive `posse up` from a versioned binary also offers the cached release before registering a Project or starting a Lead, defaulting to No. Explicit consent verifies and installs it, then re-executes `up` with the original arguments and environment. `--yes` does not consent to updating; an empty or stale cache, non-interactive and declined offers continue without updating. Lead and Rider turns cannot install an update; a separate User shell pane can.

## 20. CLI

Every command prints TOON on stdout (JSON with `--json`), uses lowercase snake_case keys and ISO 8601 local timestamps, keeps lists compact with `--full` for more, prints explicit empty states, and ends with `help[]` next steps. Queued messages are retried on status or focus changes and reconciliation; when a Task enters `reported`, `failed`, `lost`, `landed` or `torn-down`, queued and claimed messages become terminal `undeliverable` rows and one Notice names each message ID and a follow-up. `posse show <task>` lists queued, claimed and undeliverable messages with their instruction text. Ambiguous `submitting` messages are not retried and instead raise a Notice after claim expiry. Blocked Workers create a `worker_blocked` Notice and the command points the Lead to `posse peek` and `posse keys`. FIFO ordering and focus-safe delivery semantics are unchanged. Every message is stored with its wait-for-idle policy (including across restarts); the response reports `delivered` or `queued` with a reason. Queued messages already in the database before the migration keep wait-for-idle semantics.

Example home output:

```text

notices[2]{id,task,name,kind,summary}:
  7,t12,remove-legacy-auth,needs_decision,"Keep v1 endpoint or remove it?"
  8,t9,add-dark-mode,task_done,"Dark mode toggle, 4 commits"
tasks[3]{id,type,state,title,name}:
  t9,ship,done,"Add dark mode",add-dark-mode
  t12,ship,needs-decision,"Remove legacy auth",remove-legacy-auth
  t13,scout,working,"Why is CI slow",why-ci-slow
needs_you: []
help[3]:
  Run `posse show t12` to read the question
  Run `posse land t9` to gate and watch its PR
```

## 21. Invariants

Each has an automated test.

1. Work that has not Landed is never deleted without a recorded User approval.
2. Only a Worker Signal moves a Task to `done`; Herdr idle never does.
3. A Task is marked `lost` only when its pane is gone by id and by label, or its agent has been absent for 2 minutes with no resumable session.
4. Nothing is typed into a focused pane.
5. PR merging needs `autonomy.land = "auto"` or a recorded User approval, plus a latest observation of the gated head with `checks=SUCCESS`, an allowing review and `mergeable=MERGEABLE`.
6. Workers push only through `posse publish` on their own PR-mode Ship Task or through `no-mistakes` delivery; they cannot force-push, delete branches, change the default branch, or merge.
7. Every state change has a `transitions` row with its source.
8. A Brief cannot loosen Landing Mode or Autonomy.
9. At most one live Lead per Project.
10. A missed Herdr event changes nothing that the next reconcile cannot restore.
11. `--merge` lands exactly the commit the Gate passed.
12. A Mount is held by at most one Task, and a released Mount has a clean worktree and no leftover processes.
13. A Worker cannot run Lead-only commands, from its pane or after leaving it, and cannot run any state-changing command against its own posse home.
14. Identity never reaches an inter-agent artifact: changing every `[identity.*]` value leaves `launch.md`, the Rider protocol, agent names, pane labels, Notices and CLI output unchanged.
15. Every interrupted Task (dead agent, idle agent without a Signal, Herdr or machine restart) produces a Notice and resumes with one command (`posse relaunch`, or `posse recover` after a restart), in the same Mount and branch.
16. A multi-step command killed at any step is finished or undone by the next reconcile or by rerunning it.
17. A Task number and its branch are never reused, even after the database is lost.
18. Teardown closes every pane of the Task and no other pane, and verifies both before the Mount is reused.
19. Posse Teardown closes only the verified Rider child workspace, without `close_group`, or a legacy/Workspace Project tab. Group close of another primary can close the Lead and Riders; plugin events and reconcile recover their saved sessions and raise a Notice (ADR 0012).
20. In a Worker, the guard refuses the demonstrated shell-tool mutations of its Herdr session: direct calls, conditional socket assignments, hard-link aliases, `-- --help` operands, and visible generated shell and Make recipes, while allowing isolated server experiments. The boundary is in ADR 0007.
21. A Worker's descendants are Workers too: removing environment variables or changing directory never lets a Worker change its posse home.
22. This version of posse migrates an existing database only from the installed binary, and refuses a schema it does not know unless the User forces it. Older binaries lack these checks.

## 22. Testing

- **Unit**: config merge and validation, dispatch resolution, state machine, reconcile, stall rule, landing decisions, against an in-memory fake of the Herdr adapter.
- **E2E**: an isolated Herdr server, a temp git repo with a bare remote, and a fake agent. Covers spawn to teardown for each Landing Mode, blocked, stall, Worker death, Herdr server restart and Lead replacement. CI pins Herdr 0.9.1. On Linux, Riders can download the same release binary into a temporary tools directory, verify it, and make it executable before running the suite:
  ```sh
  tool_dir=$(mktemp -d /tmp/posse-e2e-tools.XXXXXX)
  herdr="$tool_dir/herdr"
  curl -fsSL \
    https://github.com/herdrdev/herdr/releases/download/v0.9.1/herdr-linux-x86_64 \
    -o "$herdr"
  printf '%s  %s\n' \
    2a02fed16beb651ef006e1d43f048f652ca4dc58ad053cd2d44450563d5c54b7 \
    "$herdr" | sha256sum --check
  chmod 755 "$herdr"
  export PATH="$tool_dir:$PATH"
  ```
  Downloading or copying the binary does not contact a Herdr server. Herdr commands are allowed only when their resolved socket differs from the User's session. To run the suite, isolate Herdr by starting `herdr server` with `XDG_CONFIG_HOME` pointing at a test dir, with every inherited `HERDR_*` variable unset. `HOME`, `POSSE_HOME`, `CLAUDE_CONFIG_DIR`, `CODEX_HOME` and `PI_CODING_AGENT_DIR` point into the same dir. This separates the socket, `plugins.json` and session state from the User's live Herdr, so the test plugin never sees real panes. Keep that path short: the socket path must fit `sun_path` (about 108 bytes).
  - In the test `config.toml`, set `[terminal] default_shell = "/bin/sh"` so panes keep the server's `PATH`, and point `[worktrees] directory` into the test dir.
  - The fake agent is an executable named after a known kind (for example `claude`) placed first on the server's `PATH`. `agent.start` launches it, and `agent.prompt` only accepts panes whose foreground process Herdr identifies as a known kind. It reports its own state with `herdr pane report-agent "$HERDR_PANE_ID" --source posse.fake --agent claude --state idle|working|blocked`, which fires the plugin's `pane.agent_status_changed` hook the same way a real agent does.
- **Smoke**: manual runs with real `claude` and `codex` Workers before each release.

## 23. Open risks

- **Timers need a caller**: stall and idle rules run on `posse` calls, plugin events and inside `posse lookout`. A codex or `prompt` Lead that is idle, with silent Workers that emit no Herdr events, gets no Notice until the next call. Revisit with an optional timer if it bites.
- **Focus as the typing guard**: it assumes a User cannot type into an unfocused pane. Herdr's `focused` is layout focus, not client attachment; multi-client setups may break the assumption.
- **The Worker guard is not a sandbox**: it sees supported agent shell-tool commands, not every program's effects. `git rebase -x` and `git submodule foreach` can run arbitrary commands that the guard does not inspect. Generated or compiled code and agents without intact hooks can bypass it. Full Herdr enforcement needs server-side per-pane API permissions.
- **Herdr API churn**: protocol moved from 16 to 22 in months. The adapter is the only place to change; `posse doctor` reports incompatibility.
- **Plugin command limit**: Herdr allows 32 plugin commands in flight; `_ingest` must stay fast (target under 200 ms).

## 24. Workspace Projects

A workspace Project is a folder that is not inside a Git repository and holds several repositories of one stack, recorded in [ADR 0008](adr/0008-workspace-projects-span-member-repositories.md). Its members are the direct subfolders that are the top level of their own repository; hidden folders and linked worktrees (such as those under `.worktrees/`) are skipped. The Lead runs at the workspace root and sees every member.

**Registration.** `posse up` shows the detection before it asks:

```text
detected:
  project: sample-stack
  kind: workspace
  root: /home/user/projects/sample-stack
repos[3]{name,default_branch,remote,landing_mode}:
  backend,main,git.example.com,pr
  worker,main,git.example.com,pr
  e2e-tool,main,none,local
Register /home/user/projects/sample-stack as a workspace Project? [Y/n]
```

Inside one member of an unregistered workspace, `posse up` registers that repository alone and its detection carries a `hint` to run `posse up` in the parent folder instead. Commands resolve their Project from any folder: a repo Project by its Git top level, else the nearest registered workspace that contains the folder, else the Task whose Mount contains it. A member name is its folder name made safe (`[a-z0-9_-]`, 32 characters); two folders that map to one name refuse with `repo_name_conflict`.

**Members.** Each member keeps its own default branch (detected like a repo Project's), saved origin host and Landing Mode: `repositories.<repo>.landing_mode`, else `local` without an `origin`, else the Project's `landing_mode`. `no-mistakes` is refused for workspace Projects. `repositories.<repo>.gate` replaces `gate` for that member and runs in its worktree. `posse project show` lists the members and their last checkout status; `posse project scan` adds new ones, refreshes their saved repository facts and marks vanished ones `missing`; `posse sync` fast-forwards each member separately, and a `root_behind` Notice names the member.

**Briefs.** `repos:` lists the members a Task works on (`[a, b]` or `a, b`). A Ship Brief must list at least one; a Scout Brief may list none and reads the members at the workspace root; a Review Brief defaults to the reviewed Task's members and may name only those. A Brief's `landing_mode` tightens each member separately and is refused where it would loosen one or ask for `pr` on a member without an `origin`.

**Mounts.** `~/.posse/remuda/<project>/mount-<n>` is a folder. Acquire refreshes it with a copy of the workspace root's shared files, skipping member folders and any folder that is a repository or worktree, and refusing above 64 MiB (`mount_shared_too_large`, naming the largest files). Each requested member gets a worktree at its own path in the Mount, created on first use with `git worktree add --detach` from the member and kept afterwards, reset like a repo Mount and put on the recorded `posse/<short>` branch from `refs/remotes/origin/<default>` (or `refs/heads/<default>` without an `origin`). Members already in the Mount but not requested are reset without a fetch as reference checkouts. `[remuda] setup` runs at the Mount root. Before a Rider starts, Posse records a per-Task fingerprint snapshot of shared-root files and each present member's `HEAD` in the Mount. Scout/Review Teardown compares selected Members against their Task base and unrequested Members against those captured commits, and compares shared-root files against the snapshot rather than the mutable live Project. It enumerates nested Git repositories through Git, recognizes nested repository directory entries, excludes `.git` metadata and ignored untracked files, and refuses Teardown if a required baseline or repository listing is unavailable. Release resets every member worktree and removes the shared copies; prune removes each member worktree with `git worktree remove`, then the folder. A Workspace Project Mount opens as a tab of the Lead's workspace, unlike repository Mounts, which open as Herdr worktree children. A Workspace Project root is not a Git worktree. `claude-trust` trusts the Mount folder after checking each member worktree belongs to its member.

**Rider protocol.** `launch.md` adds a Workspace section: shared files are copies isolated from the Project; Scout/Review Teardown saves selected Member changes against their Task bases and unrequested Member commits against the prelaunch Mount snapshot. It saves new or edited shared-root files against that snapshot, including tracked and non-ignored untracked files in nested Git repositories. Later edits to the live Project do not alter the shared-root baseline. Other Task types discard shared-root edits. It also lists which members are on the Task branch with their Landing Mode and default branch, and tells the Rider to commit inside each member it changes and leave every other folder unchanged. Each changed PR member must be published with `posse publish --repo <member> "<summary>" [--verify "<command> -> <result>"] [--proof "<markdown>"] [--risk "<markdown>"]`; verification lists commands and results, proof uses screenshots/images for UI changes or test/log evidence otherwise, and risk includes rollback details. `posse holler done` requires every requested member clean, at least one with commits ahead of its base, every changed PR member to have a validated open PR, and every other member worktree in the Mount clean and detached.

**Landing.** `posse land <task>` on a `done` workspace Task, for each member with commits (the others become `unchanged`): `local` requires a fast-forward and a clean worktree, runs the member's gate and records the gated commit (`gated`); `pr` verifies the Worker's reported pull request and remote head, runs the gate, verifies again and starts watching (`landing`, `pr_opened`) through the member's forge. Older completed Tasks without a member PR still push and open one at Land. The Task enters `landing` once every changed member is ready, with one `land_ready` naming the local members. `--merge` (approval rules of section 14) fast-forwards each gated member to exactly its gated commit and merges each member pull request or merge request pinned to its gated head. The watch reads each member through its forge (`gh` or `glab`) and applies the Notices of section 14 with the member named in the summary and `repo` in the data; a merged request lands that member. The Task becomes `landed`, with `landed_ref` listing `repo@commit` per member, only when every changed member has Landed. A moved member branch (`branch_moved`) sends the Task back to `done` and that member to `open`; members already landed stay landed. A Member pull request closed without merging raises one `pr_closed` Decision to reopen and relaunch or discard, with its Task and other Members unchanged. A merged Member is recorded as landed even if the Task is `working`, `blocked`, `stalled`, `failed` or `lost`; the Task Lands once every changed Member has Landed. A Worker fix after `posse send` re-gates every member not landing through an open pull request. Teardown deletes the recorded Task branch in each member where it is merged into the member's default branch; an approved discard records every member's branch tip as `repo=sha` pairs first. An interrupted `land --workspace` intent is settled by reconcile: a gated member whose commit reached its default branch becomes landed.
