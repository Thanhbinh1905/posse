# 34. Quota fallback relaunches in the same Sandbox

On 2026-10-25 several Claude Code Workers sat for about two hours at `You've hit your session limit · resets 7pm`. Herdr still reported them working, the screen never changed, and the Lead ran on the same exhausted account, so nothing acted until the limit reset.

A Profile may name `fallback = "<profile>"`. When a Worker's harness reports an exhausted quota or usage limit, Posse relaunches it with the fallback through the normal relaunch path: same Sandbox, same branch, the next launch number, and a fresh session when the harness kind changes. The Worker's commits and uncommitted work carry over. A routine `quota_fallback` Notice records the switch. With no fallback, or when the fallback relaunch fails, Posse raises `quota_exhausted` and a `quota` Decision (`relaunch` with the same Profile, or `discard`).

Detection reads the Worker's pane, as model-error recovery does ([ADR 0015](0015-bounded-model-error-recovery.md)), but cannot rely on an end-of-turn event: a harness at its limit may leave Herdr reporting `working` with no further events. Ingest events, launch-capable commands and every Project Watch pass therefore check live Tasks. The Watch otherwise only observes; starting this relaunch is its one launch, because the Lead may be unable to act when its own account shares the limit. A message counts only as the last thing the Worker reported: per-harness phrases at the start of a line within the final 12 non-blank lines, with no later assistant output or Posse launch prompt, and Pi's only as a recognized error result. While Herdr reports the agent working, the screen must also be unchanged for 30 seconds or the Task `stalled`. A launch-scoped record, claimed in one transaction, makes exactly one observer act; a dead claimant's record passes to the next observer. The previous launch's message stays on the same screen, so it must never be attributed to the new launch: a relaunch or Teardown intent in flight suppresses detection, a later launch cannot be claimed while an earlier launch's handler is alive, a fallback relaunch that fails after advancing the launch records its outcome for the new launch as well, and after a successful relaunch the new launch's prompt below the old message ends the scan.

A limit that resets is treated like a hard quota: Posse falls back immediately and does not wait for the reset. A five-hour session limit can leave a Task idle for hours, and a weekly limit for days, while a configured fallback can continue now. Posse records the harness's reset text (`7pm (Asia/Bangkok)`, `in 2 hours 13 minutes`) in the Notice, the audit Signal and, when no fallback remains, the Decision question, so the User can answer `relaunch` after the reset; relaunch resumes the same harness session. Posse does not parse reset times or schedule automatic resumption: reset texts are localized, harness-specific and sometimes relative, and an unattended retry before the reset would only hit the limit again.

The fallback is read from the current config for the Task's current Profile, not from the admitted plan, so the User can add or repair a fallback while Tasks run. Config validation rejects an unknown fallback and any chain that returns to its starting Profile, so each exhaustion advances one link and a chain always ends in a Decision.
