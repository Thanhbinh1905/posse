# Steer unfocused Workers when the harness accepts mid-turn input

A correction that waits for Worker idle can arrive after obsolete work is finished. `posse send` now submits to an unfocused working Worker for `claude`, `codex` and `pi`; `--queue` persists a wait-for-idle instruction, and unknown kinds default to waiting. Focused or blocked panes never receive automatic input. This trades immediate processing for earlier submission: steering takes effect at a harness-defined boundary, not necessarily before a running tool completes.

## Evidence

- [Claude Code interactive mode](https://code.claude.com/docs/en/interactive-mode#queue-messages-while-claude-works): `Enter` while working queues plain text; ordinary messages enter context after current tool calls, within the turn if possible, or after the turn. `Ctrl+Enter`/`Ctrl+X Ctrl+S` interrupts to send queued messages immediately; `Esc` interrupts but preserves the queue. We do not send either interrupt key. Permission prompts and dialogs give keys different meanings, so `agent.prompt` is not safe there.
- [Codex composer](https://github.com/openai/codex/blob/9a8730f3/docs/tui-chat-composer.md#submission-flow-entertab): with steer enabled, `Enter` submits while working and `Tab` queues for the next turn; popup key handlers run before submission. Codex v0.156.1 in the experiment showed `Messages to be submitted after next tool call`. We use `agent.prompt` (which submits paste plus Enter), not raw `send_keys` or `Tab`.
- [Pi usage](https://github.com/badlogic/pi-mono/blob/main/packages/coding-agent/docs/usage.md#change-direction): `Enter` while working is a steering message after the current response and its tools; `Alt+Enter` is a follow-up after all work. `agent.prompt` uses Enter, not Alt+Enter.
- Herdr's `agent.prompt` atomically submits text and encoded Enter with bracketed paste awareness (Herdr `agent` CLI help/skill). In a real Herdr session on 2026-09-24, independent unfocused panes ran claude (Claude Code), codex (0.156.1), and pi; each was `working` while executing `sleep 20` or `sleep 25`. `agent.prompt` returned without waiting, the Unicode probe `STEER <KIND> marker Δ漢字` appeared intact in the input/queue, and each agent acknowledged it before saying `INITIAL COMPLETE`. Claude queued its input, then answered it while its background shell remained active; Codex submitted after the next tool call; pi steered after its tool finished. Multiline Unicode probes were also submitted intact: pi and codex received them while working, and Claude received one after its tool was backgrounded (already `done`). These observations establish delivery and submission in ordinary working TUI states, not a guarantee of interruption or response latency.

A separate Claude `/model` experiment exposed a subtle unsafe state: while its menu was open, Herdr `agent.get` still reported `done`, but `agent.explain` classified the live screen as `unknown` with the `model_picker_menu` rule and `screen_detection_skipped = false`. Submitting Enter there could select a model rather than send a message. We did not type into this menu, a permission/trust dialog, or an active user draft. Pi's `/model` experiment exposed another gap: its native status and explanation stayed `idle` with screen detection skipped while the picker showed `Enter to select · Escape/Ctrl+C to cancel`. Before delivery, posse checks focus, `blocked` status and Herdr's live explanation. When screen detection is skipped, it also checks the current detection snapshot for menu key hints. Unknown UI or visible menus stay queued. A second snapshot guards immediately before prompting. The `--queue` bit is stored on each message so later reconciliation does not accidentally steer it. Existing queued messages retain their former wait-for-idle behavior on upgrade. The Lead sees `blocked` and a `worker_blocked` Notice, and can inspect/answer the dialog separately.
