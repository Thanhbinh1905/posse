# Workspace Projects span member repositories

A Project used to be exactly one Git repository, so `posse up` refused a plain folder that holds a stack of repositories (`not_in_git_repository`), and every other entry point refused an unregistered folder with `project_unknown`. A Project is now either a repository (kind `repo`) or a workspace: a folder that is not inside a repository, whose direct child repositories are its members. One Lead works from the workspace root and sees every member; one Task may change several members and Lands only when every changed member has Landed.

## Decisions

- **Detection, then one confirmation.** `posse up` in an unregistered folder detects its shape, prints what it found (name, kind, and per member the default branch, `origin` host and Landing Mode) and asks one `[Y/n]` in the terminal before it saves anything. Without a terminal it refuses with `confirmation_required`; `--yes` registers without asking. `posse project add` registers the same way without the question, because the command is itself the request. `posse project scan` re-detects members and refreshes their saved repository facts; a member that disappears is kept as `missing`, since Tasks may still reference it.
- **Members are direct child repositories only.** Hidden folders and linked worktrees are skipped: a linked worktree (such as one under `.worktrees/`) is another checkout of a member, not a member. Nested scanning would turn build outputs and vendored repositories into members.
- **Per-member facts live in the database; per-member policy in config.** Name, path, default branch and origin host are detected facts (`project_repos`). The Landing Mode is `repositories.<repo>.landing_mode`, else `local` when the member has no `origin`, else the Project's `landing_mode`. `repositories.<repo>.gate` replaces `defaults.gate` for that member. `no-mistakes` is not available to members: its delivery runs inside the Worker, one repository at a time.
- **A Brief names the members.** `repos: [backend, worker]`. A Ship Brief in a workspace must list them; a Scout Brief may; a Review Brief inherits the reviewed Task's members. A Brief's `landing_mode` tightens each member separately.
- **The Mount mirrors the workspace.** A workspace Mount is a folder with a copy of the shared root files (such as `CLAUDE.md`, `docs/`, `.claude/`) and one worktree per requested member at its own relative path, on branch `posse/t<n>`. The copy is refreshed at every acquire and removed at release, after new or edited shared-root Report attachments are saved for Scout/Review Tasks. Before launch, Posse fingerprints the shared-root files actually present in that Task's Mount; Teardown compares against that recorded snapshot rather than the live Project. Nested Git repositories are enumerated through Git, preserving tracked and non-ignored untracked files while excluding `.git` metadata. Missing baselines or failed enumeration block Teardown and keep the Mount. Copying was chosen over symlinks: a Worker's edit to a shared file cannot reach the User's real file, an `.env` is never writable through the Mount, and a copy cannot dangle when a Mount moves between Tasks. Folders that are repositories or worktrees are never copied, and the copy refuses above 64 MiB (`mount_shared_too_large`) rather than filling the disk; worktree folders such as `.worktrees/` are excluded.
- **Remuda stays warm per member.** A member worktree is created in a Mount the first time a Task requests it and kept afterwards; later Tasks reset it like any Mount worktree. Unrequested members already in a Mount are reset without a fetch and serve as read-only reference checkouts; `posse holler done` refuses if one of them changed.
- **Mounts open in separate Herdr workspaces.** Herdr's `worktree.open` needs its anchor workspace to be inside a Git work tree (`not_git_worktree` on a workspace root); moreover, closing a grouped worktree workspace can close the User's Lead and other Workers. Both repository and workspace Mounts open with `workspace.create` at the Mount path. The Task keeps its pane label, ownership checks and Teardown. *Amended by [ADR 0009](0009-riders-open-as-tabs-of-the-lead-workspace.md) and [ADR 0012](0012-group-repository-riders-under-lead.md): Workspace Project Mounts still open as Lead tabs; repository Mounts open as linked worktree children.*
- **Landing is per member.** For every changed `pr` member, the Worker runs `posse publish --repo <member> "<summary>"`, which pushes only that member's Task branch and creates or adopts its GitHub pull request or GitLab merge request. Its URL lives in `task_repos`; `posse holler done` verifies every changed PR member. `posse land` gates each member with commits (members without commits become `unchanged`): a `local` member records its gated commit, a `pr` member verifies the Worker's PR again before and after the Gate. Legacy completed Tasks without a member PR still use Land to push and open it. The Task enters `landing` once every changed member is ready. `--merge` fast-forwards local members to exactly their gated commit and merges pull requests pinned to theirs. The Task is `landed` only when every changed member has Landed; a closed member pull request or a moved member branch sends it back to `done`. Member pull requests and merge requests are watched one by one behind the same observation and Notice rules as a repository Project. Each open, merge and observation resolves the forge from that member's own origin and `repositories.<repo>.forge` override.
- **Everything names the member.** Notices, errors and `posse show` carry the member name (`worker: Task branch moved after the Gate passed`), and Notice data includes `repo`.

## Consequences

- A repository Project behaves exactly as before; every workspace path branches on the Project kind.
- The Task's own `landing_mode` is the strictest member mode and is informational; `task_repos` holds each member's mode, base ref, gated commit, pull request and landed ref, and `task.toml` snapshots carry them for `posse recover --rebuild`.
- Branch allocation checks `posse/t<n>` in every member, so a Task number is never reused in any of them.
